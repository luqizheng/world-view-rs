| # | 问题 | 用户答复 |
|---|---|---|
| Q1 | 农历精度 | **只做公历换算**——公历（含闰年）是唯一计算历法；农历/年号只是公历日期的手填写法，工具不实现农历算法/表 |
| Q2 | 历法作用域 | **工程级唯一**——全工程一套历法 |
| Q3 | i64 容量 | **支持到 10 万年，超限报警** |
| Q4 | 公历参照系 | **真实公元纪年**——真实格里高利闰年规则、真实公元年号 |

**关键推论（必须内化，两轮共用）**：`year` / `month` / `day` 全部由 `counter` + `Calendar` **唯一决定**，**它们不是独立自由度**。因此它们**不能**作为存盘字段、也不能作为 DTO 字段——否则会造出"counter 说 10、YAML 说 12"的二义态。

**本轮新增的关键推论**：**历法是"显示层"，不是"运算层"的重定义**。换历法 = 换一副眼镜，引擎里那个 `counter` 永远是同一个数。**一旦历法渗进运算层，上一轮刚砍掉的复杂度（多纪元 / 可配天数）会全部长回来。**

## 1. 设计篇（来源：游有方 · 创意总监）

### 1.1 核心立场

> **"把地理、时间、人物、事件放进同一个工程，让它们互相校验——你再也不会写出'三天从北境到南疆'。"**

**体验北极星**：从"作者意识到矛盾"到"作者完成修改"的**路径长度**。任何让作者需要离开工具、打开另一个文件、手算时间的设计，都是体验失败。

### 1.2 核心创作循环（螺旋上升，非线性）

```
建工程 → 建世界 → 圈地理 → 立时间 → 摆事件 → 看校验 → 改设定 → 回到任一环
```

**硬性体验要求**：允许**任意环节进入、任意环节返回**，未完成维度**不阻塞**其他维度（允许"空地图上先摆事件"）。

### 1.3 四维校验的体验设计

| 状态 | 颜色 | 形状/线型 | 面板文案要点 |
|---|---|---|---|
| Reachable 可达 | 绿 | 实心圆点 / 实线 | 到达时间 + 耗时（人话："耗时 1 天 6 小时 20 分"） |
| ArrivesLate 迟到 | 黄 | 三角警告 / 虚线 + 迟到徽标 | **必须反算"最早出发时间"**，让作者一次点击即可采纳 |
| Unreachable 不可达 | 红 | 叉 / 断裂线 | 给出具体缺失原因（缺哪个工具、哪个前置条件） |
| **Unknown 信息不足**（第 4 态） | 灰 | 问号 / 点线 | 「未声明路径，无法计算」 |

> **本轮补充（重要）**：**「故事」不进四维校验。** 混用会让作者对校验结论失去信任（"我明明写了一个故事，为什么工具说角色不可达？"）。见 §1.12。

**无障碍硬要求**：三态不能仅靠色相区分，必须叠加形状与线型差异（色盲友好）。

### 1.4 对 §5.4「移动由事件声明」的立场

> **强烈支持。** 它是"作者主权"哲学的核心，且实质**减轻**作者心理负担。

净负担变轻的理由：作者在实践中**本来就必须知道角色走哪条路**（这是小说作者的职业本能）。工具只是把"本来就在脑中的信息"落到纸面。真正的负担来自**声明动作的摩擦**——必须用三条体验要求兜住：边推荐列表、复制上一条、**未声明 ≠ 不可达**。

**唯一翻车点**：若不区分"不可达"与"未声明"，作者会困惑"我明明说了从 A 到 B，为什么说不可达？"

### 1.5 跨尺度时间轴（头号交互痛点，**已按两轮新模型重评**）

**跨度比 ≈ 2.6 亿 : 1**（500 年 vs 1 分钟），单条线性轨道不可能同时表达。第二轮又叠加"10 万年"新尺度。

**两轮模型变更叠加后的净效果**：

| 维度 | v0.2 首稿 | 第一轮（计数器） | **第二轮（可插拔历法）** |
|---|---|---|---|
| 多纪元，`era` 参与排序 | 有 | **删** | 删（不变） |
| 纪元切换换算 | 复杂 | 概念消失 | 消失（不变） |
| 5 元组字典序排序 | 有 | 单键数值序 | 单键数值序（不变） |
| 可前溯（负年份） | 有 | 只起点、往前不存在 | 不变 |
| 历法 | 写死 360 天 | 写死 360 天 | **可插拔三历法（显示层）** |
| 最大可表达尺度 | 500 年 | 500 年 | **10 万年+** |

**新引入的痛点**：原「跨尺度」单难点，在 10 万年尺度下**连第一层导航都撑不住**。

**算账（1 天 = 1 格，1200px 屏）**：

| 场景 | 轴上格数 | 需要的横向滚动 |
|---|---|---|
| 500 年 × 360 天（上一轮） | 180,000 | **150×** |
| 14634 年 × 365 天 | 5,341,410 | **4,451×** |
| 10 万年 × 365 天 | 36,500,000 | **30,417×** |

**裁定方案：四层导航（**第二轮由三层升级为四层**）**

| 层 | 手段 | 适用尺度 | 解决什么 |
|---|---|---|---|
| **L1 全局条** | minimap + 滑动窗口 | **≤ 500 年** | 一眼看全貌（**本位保留，但仅在 ≤ 500 年时启用**） |
| **L4 纪元鸟瞰**（**新增**） | 按**世纪/千年聚合的柱状条**（1 柱 = 1 世纪或 1 千年，柱高 = 该段事件密度）；点柱 → 下钻到该世纪 | **500 年 ~ 10 万年** | **接住 L1 崩掉的那部分**：10 万年 = 1000 柱 = 可入一屏 |
| **L2 语义锚点** | 书签 + 关键事件标记 + 「跳到下一事件」 | 跨任意尺度 | 不靠滚动，靠"跳到有意思的点"（**跨尺度唯一实用手段**） |
| **L3 年月日跳转** | 输入框「跳到 → 40年3月」+ 微调箭头（**年份支持 5 位**） | 1 天 ~ 1 月 | 精确定位，绕开连续轴 |

**为什么 L1 会先崩**：一屏 1200px 装 3650 万天 → `1px = 3 万天 = 83 年`。滑动窗口的滑块宽度 = 视窗/全长 ≈ `1/30000 px`，**画不出来**。

**层切换阈值（给技术侧的判断依据，非实现）**：

| 轴跨度 | 启用的层组合 |
|---|---|
| ≤ 500 年 | L1 + L2 + L3 |
| 500 年 ~ 5 万年 | **L4 + L2 + L3**（L1 降为"下钻后局部条"） |
| > 5 万年 | L4（每千年 1 柱）+ L2 + L3 |

> **关键设计判断**：**不要给作者一个"层选择器"**。层的切换由**轴跨度自动决定**——作者只该会两件事：**跳到有意思的点（L2）** 和 **输入日期（L3）**。L1/L4 是**视觉背景**，不要求操作。
>
> **保留并强化**：**"下钻"与"缩放"不该是同一件事**。编辑语境（城市 vs 区域）的时间轴下钻仍必须独立于时间轴缩放。

### 1.6 地形双模式（调参数 vs 画线条）

> **作者应该是"先调参数得到 80 分，再用画笔修补最后 20 分"。**

**最高优先级体验要求**：**改参数不丢覆盖**。若调海平面会清空手改的海岸线，作者会**不敢调参数**，生成模式的价值归零。

### 1.8 「前缀」的创作语义

**作者写「无仙」时想的是什么？**
→ 他在给时间**命名**，不是**分段**。写「帝国历」时同理。在创作心理上，「无仙」（创世界名）与「帝国历」（王朝名）**是同一层级的东西**，区别只是世界观味道；**在引擎里，二者区别为零**。

**核心裁定：前缀 = 可承载世界观语义的第一个锚点，但运算上是纯标签。**

| 维度 | 前缀地位 | 说明 |
|---|---|---|
| **语义维度**（作者所见） | **重** | 世界观的第一个锚点，建立「时间质感」的入口 |
| **运算维度**（引擎所见） | **轻** | 纯字符串，不参与换算/排序/区间求值 |

> 大白话：前缀不是历法系统，是你给时间**起的名字**。像给主角取名——名字很重要，但不改身高体重。以后改叫「太初历」，所有事件时间点一个都不动，只是标签变了。

**前缀硬性契约**：工程级唯一（一工程一个 `prefix`）；自由字符串（建议 ≤16 字符）；**不参与运算**；可改且不触碰任何计数器；默认空 → 显示「第 N 天」兜底；与 `start_year` **平级独立**。

**「多层纪年」（创世 → 帝国 → 联邦）由事件文案消化，工具不提供多前缀。** 主动砍范围（K1）。

> **第二轮补充（关键区分）**：**「前缀」管的仍然是"这个名字"；「历法」管的是"这个数字怎么被翻译成年月日"。二者是两块不同的东西，第二轮只把后者做成了可插拔的。**
> - 旧误解风险：作者以为"换前缀 = 换历法"。**第二轮明确：换前缀什么都改不了（纯标签）；换历法改的是整条轴的日期显示（但不改任何数据）。**

### 1.9 「起点不可前溯」的体验评估（**已按第二轮补充引导式报错**）

**结论：是解放，但工具必须兜住，否则变创作事故。**

**为什么是解放**：旧模型「可前溯」实际给三种心理负担——① 每次写时间要先问正负；② 负年份 + 多纪元 → 排序规则复杂 → 作者不敢信任工具排序；③ 「纪元前」要求先定义纪元。新模型下所有时间正、递增、可心算。

**关键问题：作者想写「建国前 300 年的传说」怎么办？→ 三条正路**

- **方案 A（首选，成本 ≈ 0）：`start_year` 前移**
  把 `start_year` 从 20 改成 -280 → 「建国前 300 年」≈ 第 21 天。代价：作者要"往上顶一格"重新理解起点。收益：**轴永远正、递增、一条线**。
  → 这解释了**为何 `start_year` 允许任意 `i32`，而 `counter` 恒 ≥ 1**（V12）。

- **方案 B（推荐与 A 组合）：前史区**
  起点**左侧**留一条视觉不同的「前史区」（虚线/灰色/不可排期，仅承载叙事文本）。

```
┌─ 前史区（虚线 / 灰色 / 不可排期，仅承载叙事）───────────────┐
│  🌌 创世 · 上古神话 · 失落文明     ┊  正常时间轴（实线）      │
│  （自由文本，无 day_counter）      ┊  无仙20年1月1日 = 第1天  │
└────────────────────────────────────┊──────────────────────────┘
                                     ↑ 起点锚点（不可左移）
```

- **方案 C（本轮新增）：转成「故事」**（见 §1.12）——若这段内容根本**不需要精确日期**，它就不该是事件，而是故事。

**引导式报错（**本轮新增，C3 裁定**）**

**当前问题**：作者想写"建国前的战役"，填了轴外日期 → 工具说"日期非法" → **作者卡住，不知道正确解法**。

**裁定：报错必须"说出正确的另一条路"，而不是否定作者。** 报错是"岔路口的路牌"，不是"此路不通的墙"。

| 作者的真实意图（工具可推断） | 报错文案 | 一键动作 |
|---|---|---|
| **意图 A：我想让这个事件早点发生**（数值接近起点） | `这个日期在时间轴起点之前。如果你希望这段时间也能排期，请把「起点年份」前移（当前起点：公元 1840 年）。` | 按钮：**[把起点前移到 1839 年]**（自动改 `start_year` + 保留所有既有事件相对位置） |
| **意图 B：这是远古的叙事，不需要精确日期** | `如果是传说、神话、历史背景这类"没有确切日期"的内容，建议建为「故事」——它不排期，也不会和其他事件对时间。` | 按钮：**[转成故事]**（把当前内容搬进 `stories/`，清掉日期字段） |
| **意图 C：这是世界开始之前的事** | `如果你的世界在起点之前还有一段历史，可以放进「前史区」（起点左侧，只承载叙事，不参与排期）。` | 按钮：**[放进前史区]** |

```
┌─ 日期在时间轴起点之前 ──────────────────────────────┐
│  你填的：公元 1835-03-02                             │
│  时间轴起点：公元 1840-01-01（第 1 天）               │
│                                                      │
│  想写"起点之前的事"？有三种做法：                      │
│   ○ 把起点前移（让这段时间能排期）  [立即前移]        │
│   ○ 建为「故事」（不需要日期）      [转成故事]        │
│   ○ 放进「前史区」（起点左侧叙事）  [放进前史区]      │
│                                                      │
│                                   [取消]  [我知道了]  │
└──────────────────────────────────────────────────────┘
```

> **口径一致性**：✅「只有一个起点」= 主轴只有第 1 天不可左移；✅「往前不存在」= **可排期事件**往前不存在，**叙事文本**由前史区/故事承载；✅「所有运算基于这个年开始算起」= 方案 A 的 `start_year` 正是这个"年"。**零冲突。**

### 1.10 UI 呈现规则（**已按第二轮修订**）

**核心裁定：以年月日为主显，天数计数器为次显。格式由当前历法决定。**

| 显示位置 | 主显 | 次显 |
|---|---|---|
| 时间轴刻度 | `公元 1840-01-01`（公历）/ `无仙 20 年 1 月 1 日`（架空） | 无 |
| 事件卡 | `公元 1840-03-15` | 悬停显示 `第 75 天` |
| Inspector / 属性面板 | `1840-03-15` | 小字 `内部序号：第 75 天`（永不占主位） |
| 校验输出 | `公元 1840-01-03` | 耗时 `1 天 6 小时 20 分` |
| 开发者/诊断模式 | `#75` | 完整年月日（普通作者不可见） |

**显示规则（可执行规约）**：

- **S1 有历法且非架空**：`<prefix> <Y>-<M>-<D>`（公历式）或 `<prefix> <Y> 年 <M> 月 <D> 日`
- **S2 未选历法 / 前缀为空**：显示 `第 <counter> 天`，**不显示年月日**
- **S3 紧凑语境自适应缩写**：`1840年1月1日` → `1840/1/1` → `1840年`（LOD，不改变主显语义）
- **S4 逐日 +1 进位**（以 `Fixed360` 为例，作者唯一能心算验证的东西）：

```
第 1 天   → 无仙 20 年 1 月 1 日
第 2 天   → 无仙 20 年 1 月 2 日
第 30 天  → 无仙 20 年 1 月 30 日
第 31 天  → 无仙 20 年 2 月 1 日    ← 月进位
第 360 天 → 无仙 20 年 12 月 30 日
第 361 天 → 无仙 21 年 1 月 1 日    ← 年进位
```

**超长年份（5 位）排版规则（**本轮新增，C 组**）**：

| 尺度 | 刻度主标 | 例子 |
|---|---|---|
| 1~999 年 | 年份数字 | `146 年` `520 年` |
| 1000~9999 年 | 年份（4 位） | `1840 年` `9999 年` |
| **≥ 10000 年** | 年份（5 位）+ **刻度变稀**（按缩放自适应 5/10/50 年一格） | `14634 年` |

三条硬规则：① **刻度标签永不重叠**（自动降密度，**宁可少标不可叠字**）；② **年份数字等宽字体**；③ 超长年份在窄栏可换行、在时间轴刻度强制单行 + 省略号（`1463…`，悬停看全）。

### 1.11 三种显示扩展方式的作者体感（**本轮新增**）

**先钉一个前提（B0 纪律）**：

| 层 | 唯一内容 | 是否可插拔 |
|---|---|---|
| **运算层** | 内部 = **天数计数器**（整数，第 1 天起，每天 +1）；排序 = 计数器数值序 | ❌ **不可插拔**（永远一种） |
| **显示层** | 计数器 ⇄ 年月日的**换算与格式化** | ✅ **可插拔**（三种内置） |

| # | 名称（作者看到） | 规则 | 作者心里的例子 |
|---|---|---|---|
| 1 | **公历（真实，含闰年）** | 1 年 = 365/366 天，12 月，月长 28/29/30/31，真实公元纪年 | `1980-1-1` |
| 2 | **简化历（365 天）** | 1 年 = 365 天，**无闰年**，12 月，月长取公历非闰年值 | `第 3000 天 = 8 年 3 月 15 日` |
| 3 | **架空历（360 天 / 30 天月）** | 1 年 = 360 天，12 月 × 30 天，**无闰年** | 上表 S4 |

**默认 = 架空历（`Fixed360`）**，理由：本工具既有规格就是 360 天，且定位是**架空世界创作工具**。若默认公历，"架空作者每次新建工程都要改一次"——摩擦放错了地方。现实小说作者选**公历 + 年号对照**。

**作者怎么选、怎么知道自己选的是哪种（三级保险）**：

| 级 | 手段 | 呈现 |
|---|---|---|
| ① **必须** | **时间轴首尾刻度直接显示完整日期，含历法特征** | 公历见 `公元 1840-01-01`；架空见 `无仙 20 年 1 月 1 日`。**写法本身就在告诉作者** |
| ② **必须** | **Inspector 顶部常驻"历法徽标"**（不藏进设置） | `[日历图标] 公历（含闰年）· 公元纪年`，点击可换 |
| ③ 建议 | **新建工程向导**一屏选择（架空默认高亮） | 三张卡片 + "随时可改，改的是显示不改数据" |

**切换历法后的非模态提示条（必须出现一次）**：
> `显示历法已切换为「公历（含闰年）」。轴上所有事件位置未变，只是显示的日期文字变了。`

### 1.12 「故事」实体的创作语义（**本轮核心之一**）

#### 1.12.1 边界裁定：「故事」= 轴外的叙事卡；「事件」= 轴上的一格

| 作者在问自己… | 建 **事件** | 建 **故事** |
|---|---|---|
| 我能说清它"**发生在哪一天**"吗？ | ✅ 能 → 事件 | ❌ 不能 / 不重要 → 故事 |
| 它需要和其他东西**对时间**吗？ | ✅ 需要 → 事件 | ❌ 不需要 → 故事 |
| 它是**可被排期**的吗？ | ✅ 是 → 事件 | ❌ 不是 → 故事 |
| 典型例子 | 建城、战役、加冕、抵达、出生 | 创世神话、上古传说、世界观设定、家族史散文、地理志节选 |

**一句话口诀（可直接做成 UI tooltip）**：

> **"能排期 → 事件；只用来讲故事 → 故事。"**

> **为什么这条规则是硬的**：它是**工具能力边界**。事件进四维校验，故事不进——**混用会让作者对校验结论失去信任**。

#### 1.12.2 故事**没有 `day`** —— 四条独立理由

| # | 理由 | 说明 |
|---|---|---|
| 1 | **无 day 就没有"非法日期"这个错误类** | 用户要的"没必要检查"由**结构**满足，而不是由"校验开关"满足——开关会被忘记，结构不会 |
| 2 | **有 day 会污染排序与四维查询** | 一个"轴外 day"的故事，会让 `TimelineQuery::at(t)` / `in_range` 的边界语义变复杂（等于在轴上开一个洞） |
| 3 | **有 day 会让作者对"轴"失去心智模型** | 轴的契约是"第 1 天起、每天 +1、往前不存在"。轴上出现一个排在"第 0 天"的东西 → 契约立刻破 |
| 4 | **与「前史区」是同一件事的两种粒度** | 前史区 = 起点**之前**的无日期叙事；故事 = **任意位置**的无日期叙事。二者应**共用一套机制** |

> **给技术侧的边界明确**：故事**不是** `TimePoint`、**不是** `TimeSpan`、**不进** `TimelineQuery`、**不参与**排序。它是 `id + 标题 + 正文 +（可选）它想靠近的锚点`。

#### 1.12.3 存放与呈现

**存放位置裁定：放独立的 `stories/` 目录，不放 `timeline/`。**

```
world/
├── timeline/
│   ├── axis.yaml            # 历法 + timeline_range + anchors
│   ├── bookmarks.yaml
│   └── events/              # ← 只有"能排期"的东西
│       └── evt_*.yaml
├── stories/                 # ← 新增：轴外叙事
│   ├── story_creation.yaml      # 创世神话
│   └── story_ancient_war.yaml   # 上古战争传说
├── characters/
├── distances/
└── maps/
```

**为什么独立目录（三条）**：

| 理由 | 说明 |
|---|---|
| **目录即心智模型** | `timeline/` 下的东西作者会默认"它有日期"。故事放进去 = 用**目录结构撒谎** |
| **避免与 `events/` 的加载器混用** | 事件加载器做硬下界校验；故事加载器不做。同目录会让加载逻辑分叉 |
| **`前史区` 是它的视图，不是它的家** | 前史区应该**读 `stories/` 里带 `before_axis: true` 标记的那些**——避免第 3 个概念 |

**`placements` 字段的语义**：它**想靠近哪个轴上的锚点**。这是**纯导航提示**，不是时间语义。类型必须是 `Vec<AnchorId>`（**只能引用已有锚点，不能填裸数字**）——这样**结构上无法表达"一个精确但非法的日期"**。

**UI 呈现（侧栏便签方案）**：

```
┌───────────────┬──────────────────────────────────────────────────┐
│  侧栏 Stories │  时间轴（正常）                                    │
│  ───────────  │  ─────────────────────────────────────────────   │
│  📜 创世神话   │   [前史区] ┊ 无仙20年 ──●建城──●──● 无仙30年        │
│  📜 上古战争   │           ┊            ↑ 锚点                     │
│  📜 家族史     │           ┊       ┌──────┐                        │
│               │           ┊       │📜便签│← placements 指向"建城" │
└───────────────┴──────────────────────────────────────────────────┘
```

- **主视图是侧栏列表**（不是时间轴上的元素）——表达"它不在轴上"。
- **带 `placements` 的故事**在对应锚点旁显示**便签图标（📜，虚线边框）**，悬停/点击跳出侧注浮层。视觉上**必须**与事件卡（实线、有色块）明显区分。
- **禁止拖拽**：便签不能被拖到轴上的新位置（轴位置对它无意义）。

#### 1.12.4 「有 day」路径的备选说明（**不采纳，记录风险**）

| 解释 | 含义 | 引入的风险 |
|---|---|---|
| 解释①：**可以填轴外的日期** | 故事能排到第 1 天之前 | 直接摧毁「往前不存在」契约；为它开后门 = 整个时间模型出现**豁免区** |
| 解释②：**可以不填日期** | `day` 是 `Option` | 90% 情况下就是 `None`——**等价于无 day，只是多一个可空字段**。既然如此，不如诚实无 day |

### 1.13 年号对照（`1818-5-5 ↔ 嘉庆二十三年四月初一`）（**本轮新增**）

**裁定三条**：

| 议题 | 裁定 | 一句话理由 |
|---|---|---|
| **① 手填 vs 内置年号表** | **内置「年号表」作为"输入辅助"，作者必须逐条确认** | 只给**辅助**，不给**代填** |
| **② 是否校验自洽** | **校验，但分级**：**年份级** → 报错（红）；**月日级** → 仅警告（黄） | 年号年份错 = 作者真错；月日级换算工具不做（用户已明确"只做公历换算"） |
| **③ 哪种最能避免"以为自己填对了"** | **内置年号表 + 给出起止年 + 年份级硬校验** | 唯一能兜住"作者记错年号年份"的组合 |

**为什么"内置年号表"是必要的**：一个作者想写"嘉庆二十三年"，**他自己都得查**（嘉庆从哪年算）。工具**替他查**是**降低**负担。但工具**绝不能**替他**换算月日**——那要接农历算法（用户已否决）。

**校验分级判定表**：

| 作者填的内容 | 工具行为 | 文案 |
|---|---|---|
| 年号年**落在**该年号起止年内 | ✅ 绿，通过 | 无（或淡字"年份自洽"） |
| 年号年**超出**该年号起止年 | 🔴 **报错**（阻止保存） | "嘉庆只到二十五年（公元 1820）。你写的『嘉庆二十三年』对应的是 1818 年，不是 1820 年。" |
| 年号**不在**内置表 | 🟡 **提示**（不阻止） | "『XX 年号』不在内置表里。已按自定义处理，年份不做校验。" |
| 农历**月日**与公历对照是否吻合 | 🟡 **只警告** | "工具不推算农历月日。请自行确认『四月初一』是否对应 1818-05-05。" |

> **为什么不把月日级也做成报错**：用户明确"只做公历换算"，工具**没有**农历能力。它若对月日级报错，就是在**假装自己会**——这是最坏的情况（作者会信它）。**警告 + 明确声明"我不算农历"是诚实的设计。**

**年号表维护边界**：表**只覆盖到清**（封闭、不增长的史实集合）；**仅下拉候选、不自动填公历**；表**可以是外部数据文件**，作者可扩展，工具不背维护包袱。

### 1.14 风险与可砍项（设计侧）

**风险（按严重度）**：

| 严重度 | 风险 | 兜底 |
|---|---|---|
| 🔴 高 | **历法渗进运算层**（"反正只是显示"被误当成"顺手把天数和历法联动一下"） | §1.11 B0 纪律写进 ADR；§2.2 R6 修订明确"只有显示层分派" |
| 🔴 高 | **年号被工具"自动换算"** → 作者全盘信任一个不会农历的工具 | §1.13：月日级**只警告**、UI 明写"工具不推算农历" |
| 🔴 高 | **L1 minimap 在 10 万年下画不出滑块**（1/30000 px） | §1.5：补 L4；**按跨度自动切层**，不给作者层选择器 |
| 🟡 中 | 作者把故事误拖到轴上（以为能排期） | §1.12：便签**禁止拖拽** + 视觉强区分 |
| 🟡 中 | 5 位数年份刻度叠字 | §1.10：**自动降密度**（宁可少标） |
| 🟡 中 | "跨度太大"被写成"数值太大"（错误技术叙事） | §1.15：文案只说**导航**，不说**容量** |
| 🟡 中 | **作者看到"公元 0 年"→ 怀疑工具算错** | §1.16：运算用天文记年、显示/输入用历史纪年；作者不可输入 0 年 |
| 🟢 低 | 作者选错历法 | 切换**不丢数据**（§1.11 提示条）· 徽标常驻 |
| 🟢 低 | 前史需求无处安放 | 三条正路（§1.9：前移 / 前史区 / 转故事） |

**可砍项**：

| # | 可砍项 | 代价 | 何时砍 |
|---|---|---|---|
| K1 | 多前缀/多纪年系统 | 靠文案代偿 | **现在就砍**（用户已明确单轴单前缀）。**但"年号对照"作为显示层能力保留** |
| K2 | 天数 ⇄ 年月日双向换算输入框 | 作者需心算 | 🟡 **优先级上调为"阶段五必做"**——10 万年下是唯一能"精确跳到某天"的低成本手段（L3） |
| K3 | 双轨分屏 | 无法左右对比两远点 | **转待裁**（纪元消失后唯一强用例消失） |

| K7 | L4 纪元鸟瞰 | >500 年工程**无法导航** | **不可砍**（§1.5 的结论就是它必做） |
| K8 | 故事 `placements` 导航提示 | 故事只在侧栏，时间轴旁无便签 | 阶段五紧则砍（不影响语义） |

### 1.15 跨度预警的创作侧口径（**本轮新增**）

**裁定：不说"别写这么大"，说"这么大，建议开启某模式"。是引导，不是劝阻。**

**触发时机（三档，渐进式）**：

| 时机 | 触发条件 | 形态 | 文案 |
|---|---|---|---|
| **① 实时（软）** | 作者在年份框里**正在输入**、且当前值 ≥ 5 位数 | 输入框下方一行**灰字**（不打断） | `这是个超长跨度（14634 年 ≈ 534 万天）。时间轴会自动切到「纪元鸟瞰」显示。` |
| **② 保存时（中）** | 保存 `axis.yaml`、且轴跨度 > 1 万年 | **非模态提示条**（可一键忽略） | `轴跨度 10 万年。已为你启用「纪元鸟瞰」简化显示——按世纪聚合，仍可精确跳转到任意一天。` |
| **③ 门槛（硬）** | 轴跨度 > **20 万年** | **弹窗，需要作者确认** | `跨度已达 20 万年，时间轴上的每一天无法逐格显示。继续可以，但建议：① 拆成多工程 ② 接受「纪元鸟瞰」为唯一导航。` |

**明确不做的事**：

- ❌ **不在任何档位阻止作者保存**——一人开发的创作工具，**作者主权**优先。
- ❌ **不弹"i64 装不下"的报错**——用户已算过，**装得下**（10 万年占 i64 的 `4×10⁻¹²`）。**报"数值太大"是错误的技术叙事**。真正的限制是 **UI 导航**，文案必须说**导航**，不说**容量**。

**文案的唯一职责**：**把"技术瓶颈"翻译成"作者能做的动作"**。
- ❌ `跨度超出推荐值` → 作者不知道怎么办。
- ✅ `已启用纪元鸟瞰，你仍可跳到任意一天` → 作者知道"我的目标没被剥夺"。

> **⚠️ 与 §2.5 的阈值差异说明（本轮两侧独立取值，需主理人/用户统一）**：
> - **设计侧（本文 §1.15）** 从**创作体感**出发取"1 万年 / 20 万年"两档：1 万年是 L1 明显失效的直觉点，20 万年是"UI 无意义但引擎仍可容纳"的硬提示点。
> - **技术侧（§2.5）** 从**渲染预算**出发取"**100 万天（≈2738 年）**"单档：依据是上一轮 18 万格已是"可承受的痛点上限"，100 万格 = 其 5.56 倍。
> - **两者不冲突，是同一功能的不同档位**：技术侧的 100 万天（≈2738 年）可作**软预警触发点**，设计侧的 1 万年（≈365 万天）作**强制切 L4 点**，20 万年作**硬确认点**。**建议统一为三档（2738 年 / 1 万年 / 20 万年），列入 §4.1 N6 待拍板。**

### 1.16 `year = 0` 的纪年口径（**本轮新增，设计侧终裁**）

**裁定：运算层用天文记年（技术侧已实现，不动）；但"公元 0 年"四个字永远不许出现在作者眼前。**

| 层 | 口径 | 理由 |
|---|---|---|
| **运算层**（`is_leap_year`、换算、`i64` 计数器） | **天文记年**（`year = 0` 存在，是闰年；`-1` = 公元前 2 年） | 数学坐标系，不是给作者看的 |
| **显示层 / 输入层** | **历史纪年**（**没有公元 0 年**；`1` → "公元 1 年"，`-1` → "公元前 1 年"） | 现实小说作者的常识里**不存在公元 0 年**。若作者看到"公元 0 年"，会**怀疑工具算错了** |

**为什么必须做这层映射**：用户本轮原话的例子是"公元 1840 年""1818 年 5 月 5 日"——**作者是写现实/历史小说的人**。对这类作者，"公元前 1 年"的下一年就是"公元 1 年"，中间**没有 0**。让作者看到"公元 0 年"，等于要求作者学一套"天文年号"才能用工具，与北极星**直接冲突**。

**映射规则（一处转换，作者永不可见 0）**：

| 作者输入 | 运算层 `year` | 作者看到 |
|---|---|---|
| 公元 1 年 | `0` | 公元 1 年 |
| 公元 2 年 | `1` | 公元 2 年 |
| 公元前 1 年 | `-1` | 公元前 1 年 |
| 公元前 2 年 | `-2` | 公元前 2 年 |
| **（不存在）** | — | 作者**无法**输入"公元 0 年"（输入框直接拒绝） |

**关键边界（给技术侧的契约）**：

| # | 规则 |
|---|---|
| 1 | **映射只在"作者 ↔ 工具"的边界发生一次**（UI 输入解析 / 显示格式化各一处）。**运算层、`is_leap_year`、计数器一律用天文记年，不感知映射** |
| 2 | **闰年判定仍按天文年**（`is_leap_year(0) == true`）——不改，闰年周期是数学事实，与显示口径无关 |
| 3 | **作者不可输入"公元 0 年"**：输入框对"公元 0 年"直接拒绝并提示"纪年中没有公元 0 年，公元前 1 年之后就是公元 1 年" |
| 4 | **非公历历法（`Fixed360`/`Simple365`）不做此映射**：架空历里作者可能真有"第 0 年"的设定，是否映射由作者自定 |

> **一句话**：**"0 年"是引擎的内部数学，不是作者的日历。**

### 2.2 TimePoint 与历法（**第二轮重做，替换第一轮 §2.2.4**）

> **本节为就地覆盖。** 第一轮的 `const DAYS_PER_YEAR = 360` 硬编码历法与 `Calendar { prefix, start_year }` **作废**；`TimePoint` / `TimeSpan` / `TimelineQuery` **代码不变**。

#### 2.2.1 裁定总表（R 组）

| # | 议题 | 第一轮 | **第二轮裁定** | 理由 |
|---|---|---|---|---|
| **R1** | `TimePoint` 主表示 | newtype `TimePoint(i64)` | **不变**，且**更强**：三历法都只改"这个 i64 怎么显示"，**证明 R1 是对的**（若当初留 5 元组，换历法就要改数据） | 计数器 = 绝对物理天数 |
| **R2** | 「纪元」实体 | 全删 | **不变**（仍无） | S9 |
| **R3** | 负年份 / 纪元前 | 不存在，`counter >= 1` | **不变**，且**更强**：故事"无 day"是**这条约束的配套** | S8 |
| **R4** | 时分精度 | 阶段一删除 | **不变**（H4：刻度 = 1 天） | S7 |
| **R5** | 排序语义 | 天数计数器数值序 | **不变**：故事不进排序 | R1 的直接后果 |
| **R6** | 历法常量 | `const` 360/30（**硬约束**，C12） | **🔴 修订：取消全局 `const`，改为按 `CalendarRule` 分派**（360/30 vs 365/闰年 vs 公历）。原 R6 的"`const` 常量"是**基于"只有一种历法"**的裁定，**前提已变** | 用户要三种历法 |
| **R7** | 时间轴范围 | `DayRange{first_day, last_day: Option<i64>}` | **不变** | 纯整数 |
| **R8** | 起步语义 | `counter=1` 是逻辑起点，`start_year` 只影响显示 | **✅ 强化为通则**：改**任何**显示历法参数（含换历法）**都不迁移数据** | 历法 = 显示层的直接推论 |
| **R9** | 事件下界（**新增**） | `counter >= 1` | **事件 `from` 必须 `> 起点 0 时`，即 `>= 2`** | S11 用户原话 |
| **R10** | 故事实体（**新增**） | 不存在 | **新增 `story.rs`，独立模块，不与 event 合并** | S12；无日期 ⇒ 领域约束不同 |

> **R6 是本轮唯一必须动到 `wv-core` 语义的项**，且必须严格区分：
> - **运算层**：`TimePoint(i64)`、排序、区间、下界 → **一律不变**
> - **显示层**：`Calendar::civil()` / `day_counter()` / `format()` → **改为按 `CalendarRule` 分派**
>
> 若把历法分派做进运算层，上一轮砍掉的复杂度会**全部长回来**（§1.11 B0 纪律）。

#### 2.2.2 为什么用 `enum`（封闭三值）而非 `trait`

| # | 判据 | enum 胜出理由 |
|---|---|---|
| 1 | **集合封闭性** | 用户钦定"默认有 3 种"，是**封闭集合**。trait 的价值在"第三方可扩展"，这里**不预期扩展** |
| 2 | **穷尽匹配** | `match` 由编译器强制穷尽；加第四种历法时**所有未更新处编译报错**——正是我们要的"改动可见" |
| 3 | **零开销** | `enum` 是 `Copy`、栈上 1 字节、无 `Box`、无 vtable。trait 会把 `<R: CalendarRule>` 传染到**所有**上层结构 |
| 4 | **serde 友好** | `#[serde(rename_all="snake_case")]` 直接产出 `rule: gregorian`。trait 需 `typetag` 之类 |
| 5 | **可逆扩展** | 若真要开放，把 enum 包成 `Custom(Box<dyn ...>)` 一个变体即可——**非破坏性**。反之若现在选 trait，想收回成 enum 是**破坏性** |
| 6 | **可哈希/可比较** | `CalendarRule` 可 `derive(Hash, Eq)`，便于做换算缓存键 |

**何时该翻案（写清触发条件）**：出现以下**任一**，改抽 trait——
1. "作者自定义月表/月名"需求（如 13 个月、月长不等）；
2. "一个工程内多套历法并存"需求（与 H1 冲突）；
3. "第三方历法插件"需求。

**当前三者皆无。** 且"现实小说 = 公历 + 年号"由 `Gregorian + reign_aliases` 覆盖，**不需要独立 `custom` 变体**——为同一语义造两个概念是本项目反复砍的过度设计。

#### 2.2.3 最终 Rust 定义（`crates/wv-core/src/calendar.rs`，**新文件**）

> **验证状态**：以下代码已在 `rustc 1.97.1 / edition 2021` 下**实际编译并运行**，
> `cargo clippy --all-targets -- -D warnings` **零告警**，`cargo fmt --all -- --check` **干净**，
> 附带 **32 项测试全绿**（4 单元 + 28 集成，见 §2.5.3）。

```rust
//! 可插拔历法：`CalendarRule`（工程级唯一）+ 换算。
//!
//! 核心规格（用户确认，唯一权威）：
//! - 内部主表示 = **整数天数计数器**，第 1 天 = 游戏第一日；每天自动 +1。
//! - 历法是**可插拔的显示/解析规则**，不是运算主键；运算主键永远是 counter。
//! - 只有**一个起点**，往前不存在（无负数计数器）。
//! - 前缀（如 `无仙` / `帝国历`）只是**起点的命名标签**，不是可切换纪元。
//! - 农历/年号**只做显示（作者手填注释）**，不实现农历算法、不内置农历表。

use crate::error::CoreError;

/// 内置历法种类（封闭三值）。设计裁决见 §2.2.2：**enum 而非 trait**。
#[derive(
    Debug, Clone, Copy, PartialEq, Eq, Hash, serde::Serialize, serde::Deserialize, Default,
)]
#[serde(rename_all = "snake_case")]
pub enum CalendarRule {
    /// ① 公历（真实格里高利历，含闰年）。
    Gregorian,
    /// ② 简单 365 天历（无闰年，月长与公历非闰年一致）。
    #[serde(rename = "simple_365")]
    Simple365,
    /// ③ 360 天/年、30 天/月（奇幻默认，等价第一轮实现）。
    #[default]
    #[serde(rename = "fixed_360")]
    Fixed360,
}

// ⚠️ 两个显式 `rename` 是必须的：`rename_all="snake_case"` 对 `Fixed360`
//    会产出 `fixed360`（数字不产生词边界）。文档写 `fixed_360` 而实现产出
//    `fixed360` = 作者按文档写会解析失败。已由 `calendar_rule_serializes_snake_case` 钉死。

impl CalendarRule {
    /// 平年天数（非闰年基准）。
    pub const fn days_per_common_year(self) -> i64 {
        match self {
            CalendarRule::Gregorian | CalendarRule::Simple365 => 365,
            CalendarRule::Fixed360 => 360,
        }
    }

    pub const fn has_leap_year(self) -> bool {
        matches!(self, CalendarRule::Gregorian)
    }

    /// 某年的天数。
    pub fn days_in_year(self, year: i64) -> i64 {
        match self {
            CalendarRule::Gregorian if is_leap_year(year) => 366,
            _ => self.days_per_common_year(),
        }
    }

    /// 某年某月的天数。
    pub fn days_in_month(self, year: i64, month: i64) -> i64 {
        debug_assert!((1..=12).contains(&month));
        match self {
            CalendarRule::Fixed360 => 30,
            CalendarRule::Simple365 | CalendarRule::Gregorian => match month {
                1 | 3 | 5 | 7 | 8 | 10 | 12 => 31,
                4 | 6 | 9 | 11 => 30,
                2 => {
                    if self == CalendarRule::Gregorian && is_leap_year(year) {
                        29
                    } else {
                        28
                    }
                }
                _ => 30,
            },
        }
    }

    pub const fn months_per_year(self) -> i64 {
        12
    }
}

/// 格里高利闰年规则：**4 年一闰、百年不闰、四百年再闰**。
///
/// `year` 为真实公元纪年（可为 0 与负数，按天文记年；见 §1.16）。
pub fn is_leap_year(year: i64) -> bool {
    (year % 4 == 0 && year % 100 != 0) || year % 400 == 0
}

/// 时间轴坐标系：历法规则 + 起点命名 + 起点年 + 年号对照。
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct Calendar {
    #[serde(default)]
    pub prefix: String,
    pub start_year: i32,
    #[serde(default)]
    pub rule: CalendarRule,
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub reign_aliases: Vec<ReignAlias>,
}

/// 年号对照。**仅显示用**——不参与排序、不参与区间求值。
///
/// 七字段：前四为**内置静态史实**（支撑年份级硬校验），中二为**工具换算**的
/// 天数计数器区间，末一为**作者手填**、工具绝不解析。
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct ReignAlias {
    /// 【内置静态史实】年号名，如 `道光`。工具提供下拉候选，**不自动填公历**。
    pub era_name: String,
    /// 【内置静态史实】朝代，如 `清`。
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub dynasty: Option<String>,
    /// 【内置静态史实】该年号的公历起年（含），如 1821。用于年份级硬校验。
    pub gregorian_start: i32,
    /// 【内置静态史实】该年号的公历止年（含），如 1850。
    pub gregorian_end: i32,
    /// 【工具换算】本对照在时间轴上的天数计数器起点（含）。
    pub start: i64,
    /// 【工具换算】终点（不含）；省略 = 至今。
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub end: Option<i64>,
    /// 【作者手填】农历写法，如 `道光二十年正月初一`。**工具绝不解析此字段**。
    pub lunar_label: String,
}

impl ReignAlias {
    /// 年份级硬校验：作者填的公历年份是否落在年号期内。
    ///
    /// **不需要农历算法**——只是比较两个公历年份（`gregorian_start/end` 是静态史实）。
    pub fn is_year_consistent(&self, gregorian_year: i32) -> bool {
        (self.gregorian_start..=self.gregorian_end).contains(&gregorian_year)
    }
}

impl Calendar {
    pub fn new(prefix: impl Into<String>, start_year: i32, rule: CalendarRule) -> Self {
        Self { prefix: prefix.into(), start_year, rule, reign_aliases: Vec::new() }
    }

    /// 天数计数器 → 年月日。**不使用 `offset / 365` 近似**。
    ///
    /// 以 `start_year` 为锚，逐年减「该年真实天数」（365/366/360），
    /// 余下落入年内再逐月减。复杂度 O(年数 + 月数)。
    pub fn civil(&self, counter: i64) -> CivilDate {
        let mut offset = counter - 1;
        let mut year = self.start_year as i64;

        loop {
            let diy = self.rule.days_in_year(year);
            if offset < diy {
                break;
            }
            offset -= diy;
            year += 1;
        }

        let mut month = 1i64;
        loop {
            let dim = self.rule.days_in_month(year, month);
            if offset < dim {
                break;
            }
            offset -= dim;
            month += 1;
        }

        CivilDate { year, month, day: offset + 1 }
    }

    /// 年月日 → 天数计数器。**整年天数累加**，非近似。
    pub fn day_counter(&self, year: i64, month: i64, day: i64) -> Result<i64, CoreError> {
        if year < self.start_year as i64 {
            return Err(CoreError::BeforeTimelineStart { year, start_year: self.start_year });
        }
        let months = self.rule.months_per_year();
        if !(1..=months).contains(&month) {
            return Err(CoreError::InvalidMonth { month, max: months });
        }
        let dim = self.rule.days_in_month(year, month);
        if !(1..=dim).contains(&day) {
            return Err(CoreError::InvalidDay { day, max: dim });
        }

        let mut counter: i64 = 1;
        let mut y = self.start_year as i64;
        while y < year {
            counter += self.rule.days_in_year(y);
            y += 1;
        }
        let mut m = 1i64;
        while m < month {
            counter += self.rule.days_in_month(year, m);
            m += 1;
        }
        counter += day - 1;
        Ok(counter)
    }

    pub fn first_day(&self) -> i64 {
        1
    }

    /// 展示文本。`with_year = false` 时省略年份。
    pub fn format(&self, counter: i64, with_year: bool) -> String {
        let d = self.civil(counter);
        let core = if with_year {
            format!("{} {} 年 {} 月 {} 日", self.prefix, d.year, d.month, d.day)
        } else {
            format!("{} {} 月 {} 日", self.prefix, d.month, d.day)
        };
        // 年号对照（仅显示）：命中区间则追加。
        if let Some(alias) = self
            .reign_aliases
            .iter()
            .find(|a| counter >= a.start && a.end.map_or(true, |e| counter < e))
        {
            return format!("{core}（{}）", alias.lunar_label);
        }
        core
    }
}

/// 换算后的年月日。**只用于展示/解析**，不得作为存盘字段。
#[derive(Debug, Clone, Copy, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct CivilDate {
    pub year: i64,
    pub month: i64,
    pub day: i64,
}

impl CivilDate {
    pub fn to_counter(self, calendar: &Calendar) -> Result<i64, CoreError> {
        calendar.day_counter(self.year, self.month, self.day)
    }
}
```

#### 2.2.4 三种历法的代码复用方式（**明确回答复用问题**）

**复用靠"策略钩子"而非"三份实现"**：`civil` / `day_counter` **只写一份**，它俩不直接读常量，而是调用 `self.rule.days_in_year(y)` / `days_in_month(y,m)`。三种历法**只在这两个钩子函数内分叉**：

| 历法 | `days_in_year` | `days_in_month(y, 2)` | `days_in_month(y, 其他)` |
|---|---|---|---|
| `Gregorian` | 366/365（含闰） | 29/28 | 31/30（真实公历） |
| `Simple365` | 恒 365 | 恒 28 | 同上（31/30） |
| `Fixed360` | 恒 360 | 恒 30 | 恒 30 |

- **`Simple365` 与 `Gregorian` 的唯一差别**：前者 `has_leap_year = false`。故 `Simple365` **复用** `Gregorian` 的月长表，只在 `days_in_year` 与二月分支上不查闰年。
- **`Fixed360`**：完全独立，等价第一轮实现。**第一轮全部数字（`100801` / `180360` / `520-12-30`）在 `Fixed360` 下逐字节不变**——已测试 `fixed360_reproduces_previous_round_numbers` 钉死，**旧工程零迁移成本**。
- **新增第四种历法的成本**：改两个 match + 加一个 enum 变体，`civil`/`day_counter` **一行不动**。

#### 2.2.5 排序语义的明确废弃声明

| 项 | v0.2 首稿 | **本轮** |
|---|---|---|
| 排序定义 | `(era, year, day, hour, minute)` 字典序 | **天数计数器数值序** |
| 实现方式 | 手写多字段比较 | `#[derive(Ord)]` 于 `TimePoint(i64)` |
| 附加约束 | "排序恒按字典序，**不依赖** `total_minutes`" | **该约束整条作废** |
| 跨纪元排序 | 需 `era` 参与比较 | `era` 已删除；`prefix` 是名字，**不参与**排序 |
| 跨历法排序 | （未定义） | **历法不改变**一天**这个物理量**，`Ord` 永远按数值——排序语义与历法**正交** |

#### 2.3.2 年号对照的 YAML 位置

**裁决：独立的顶层 `reign_aliases` 列表，挂在 `Calendar` 下（`#[serde(flatten)]` 后即在 `axis.yaml` 顶层）。**

| 方案 | 问题 |
|---|---|
| ❌ `anchors[].alias` | 锚点是"UI 跳转点"，年号是"日期区间的写法"。一个年号跨很多天；塞进锚点会强迫作者为每段年号建锚点，**污染锚点列表** |
| ❌ 独立的 `eras` 表（复用已删结构） | `eras` 承载的是"参与运算的纪元"，而年号**不参与任何运算**（Q1）。复用会**误导**作者 |
| ❌ 换名重开 `display_calendar: {kind, epoch_label, ...}` | 把已存在的 `prefix`/`start_year` **换名重开一套**——正是"为同一语义造两个概念" |
| ✅ **独立顶层 `reign_aliases`** | ① 语义清晰："一段公历区间 ↔ 一个手填写法"；② 不参与运算；③ 天然支持"一个年号跨多年"；④ 与 `anchor` 解耦；⑤ 与已有的 `prefix`/`start_year` 同属一个坐标系，**零多余概念** |

**年号 schema 的七个字段**（同 §2.2.3 的 `ReignAlias`）：

```yaml
# axis.yaml 顶层（经 Calendar flatten 后）
rule: gregorian              # gregorian | simple_365 | fixed_360
reign_aliases:
  - era_name: 道光            # ① 内置表候选；作者可下拉选，也可自定义
    dynasty: 清               # ② 仅显示分组
    gregorian_start: 1821     # ③ 内置表提供 → 支撑"年份级硬校验"
    gregorian_end: 1850       # ④ 内置表提供 → 支撑"年份级硬校验"
    start: 1                  # ⑤ 本段对应的天数计数器区间（含）；工具由公历换算
    end: 4019                 # ⑥ 区间（不含）= 1851-01-01；省略 = 至今
    lunar_label: 道光二十年正月初一   # ⑦ 作者手填，工具不解析
```

**字段分工（诚实边界）**：

| 字段 | 谁提供 | 用途 | 工具是否推算 |
|---|---|---|---|
| `era_name` / `dynasty` / `gregorian_start` / `gregorian_end` | **内置表**（作者下拉） | ① 快速输入 ② **年份级硬校验依据** | 否（静态史实） |
| `start` / `end` | **工具算**（公历起止年 → 计数器，**纯公历运算**） | 显示时定位"哪段显示这个年号" | 是（但**只是公历换算**，非农历） |
| `lunar_label` | **作者手填** | 显示文本 | ❌ **绝不** |

**工具只做两级、不越界**：
> - **年份级**：拿 `gregorian_start/gregorian_end`（静态史实）**硬校验**作者填的公历年份是否落在年号期内 → **自洽则通过，否则报错（红）**。这一步**不需要农历算法**。
> - **月日级**：`lunar_label` 里的"四月初一"**工具绝不推算**，只做显示 → 若与公历日期可能不符，**仅警告（黄），不报错**。**仅月/日级换算才需要农历算法（用户已否决）。**

**未来的自动月日换算（如真需要）**：属**阶段五+ 可选增强**，需引入农历数据表（体积 + 版权 + 精度三重成本）。**当前明确不做**——与 Q1 一致。

#### 2.3.4 YAML 表达选择：**存天数计数器为权威整数**

**裁定**：YAML 存 `day: 100801`（裸整数），**不存** `{year, month, day}`。理由：

| # | 理由 |
|---|---|
| ① | 与内部主表示 **1:1 无损**、天然可比较、可 diff |
| ② | 若 YAML 写 `{year,month,day}`，则加载期要换算、保存期要反算，**两处都可能出错**，且引入"YAML 与内部不一致"的窗口 |
| ③ | 自然语言"无仙1月2日"**无法静态校验**且需解析器 |

**可读性用 CLI 双表示兜底**（见 §2.6.1）：`@day1 (公元 1840-01-01) .. @day73050 (公元 2040-01-01)`。

#### 2.3.5 兼容性：默认 `fixed_360` 保旧工程

`Calendar.rule` 有 `#[serde(default)]` ⇒ **缺 `rule` 字段的 YAML 自动按 `fixed_360` 解析**。这意味着：**上一轮 `Fixed360` 工程的 `axis.yaml` 加不加 `rule: fixed_360` 都能读**。`reign_aliases` 缺省为空、`Timeline` 其他字段不变 ⇒ **纯 360 工程数据可零改动**（前提：`schema_version` 也升级，见 §2.8）。

### 2.4 事件硬下界、故事实体与校验分流（**本轮新增**）

#### 2.4.1 关键问题：`counter = 1` 的事件算不算合法？

**用户原话（S11）**："作者添加事件，填写日期必须检查必须**大于** 1840年1月1号 **0时0分**。"

**逐字拆解**：
- `counter = 1` 的定义就是"起点那天的 0 时"（即 `1840-1-1 00:00`）——这是 `TimePoint::FIRST` 的定义。
- 用户要求事件 `> 起点 0 时`，即 `> counter 1`。
- **故 `counter = 1` 的事件不合法，最小合法事件日期是 `counter = 2`。**

**明确回答二选一**：不是 `counter >= 1`，是 **`counter > 1`（等价 `counter >= 2`）**。

> **与 `TimePoint::from_counter` 的关系**：`from_counter(1)` 仍**合法**（第 1 天本身是合法时间点，可用于锚点显示）；**只是它不能作为"事件起点"**。两件事必须分开——`from_counter` 管"这是不是合法时间点"，事件校验管"事件能不能发生在这"。**故不在 `TimePoint` 上收紧，而在 `Event` 校验层加规则。** 收紧 `TimePoint` 会把锚点、spans 端点一并误伤。

#### 2.4.2 校验代码（已编译）

```rust
/// 事件日期硬下界校验：`from` 必须 **严格大于** 起点 0 时。
///
/// 起点本身 `counter = 1` 就是"起点那天的 0 时"，
/// 用户要求事件**大于**起点 0 时 ⇒ `from == 1` **不合法**，最小合法 `from == 2`。
pub fn check_event_lower_bound(from: i64, start_day: i64) -> Result<(), CoreError> {
    if from <= start_day {
        return Err(CoreError::EventAtOrBeforeStart { day: from, start_day });
    }
    Ok(())
}
```

#### 2.4.3 「故事」实体：**独立模块 `story.rs`，不与 `event.rs` 合并**

**技术裁决（创作语义归属设计侧，此处只给技术后果）**：

| 方案 | 技术后果 |
|---|---|
| **A. 独立 `story.rs` + 独立 `Story` 类型**（**推荐**） | ① 类型系统层面**不可能**给故事写 `day`——无字段可写；② 校验分流靠 `match` 一次，不必散落 `if is_story`；③ 模块边界清晰；④ 代价：多一个文件、`lib.rs` 多一行导出 |
| **B. 并入 `event.rs`，`Event.day: Option<i64>`** | ① 出现 `Option` 语义污染——**`None` 到底是"故事"还是"忘填了"？** 无法区分，需再加 `kind`；② 校验分流变成运行时判断，编译器不帮忙 |
| **C. 并入 `event.rs`，事件 `Event` + 故事 `Story` 两 struct 同文件** | 折中：类型仍分离（好），但语义上挤在一个模块，文档边界会含糊 |

**推荐 A**。理由：**A 把"故事没有日期"这条规范固化成类型系统的硬约束**——想违反都写不出来；B 把它降级成"运行时约定"，靠人记。**能靠编译器兜住的规范就不要靠记忆。**

#### 2.4.4 「故事」完整 Rust 定义（已编译）

```rust
//! 「故事」实体：**无日期**的叙事单元。

use crate::error::CoreError;
use crate::id::Id;
use crate::time::TimeSpan;

/// 故事。**无 day 字段**是规范要求，不是省事。
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct Story {
    pub id: Id,
    pub name: String,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub body: Option<String>,
    #[serde(default)]
    pub tags: Vec<String>,
    /// 可选：它想靠近的锚点（**仅用于显示定位，不赋予任何时间语义**）。
    ///
    /// 只是"指向已有锚点的弱引用"——**不进 `TimePoint`/`TimeSpan`/`TimelineQuery`**，
    /// 不参与排序、不参与校验。加此字段**不破坏"故事无 day"的硬约束**。
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub placements: Vec<Id>,
}

/// 时间的**校验分流**枚举：有日期走 `Dated`，无日期走 `Undated`。
///
/// 这是"事件硬下界 vs 故事不检查"的唯一实现入口——
/// 校验器只需 `match` 一次，不必散落 `if is_story` 判断。
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
#[serde(rename_all = "snake_case", tag = "kind")]
pub enum TimelineItem {
    /// 可排期（事件）：必须 `from > day_counter(start_year,1,1)`。
    Dated {
        #[serde(flatten)]
        span: TimeSpan,
    },
    /// 不可排期（故事）：无日期，恒通过时间校验。
    Undated { story: Story },
}

/// 统一校验入口：按 `TimelineItem` 分流。
pub fn validate_timeline_item(item: &TimelineItem, start_day: i64) -> Result<(), CoreError> {
    match item {
        TimelineItem::Dated { span } => check_event_lower_bound(span.from, start_day),
        // 故事无日期 ⇒ 恒通过。
        TimelineItem::Undated { .. } => Ok(()),
    }
}
```

> **`TimelineItem` 是"校验分流"的载体**，但**不是**新的存盘聚合：`Event` / `Story` 仍各自存各自文件，加载器把两者统一映射成 `TimelineItem` 后过一遍校验。**存盘格式保持"一实体一文件"**，只在**内存校验阶段**收敛。

> **`placements` 的技术后果**：`Story` 从"完全轴外"变成"可挂到锚点旁显示"。**仍然无 `day`、仍不进 `TimelineQuery`、仍不排序**——`placements` 是**展示层弱引用**，不是时间坐标。**模型硬约束零影响。**

#### 2.4.5 两个方案（有 day / 无 day）的技术后果对照

| 维度 | 故事**有 `day`** | 故事**无 `day`**（**采纳**） |
|---|---|---|
| 排序 | 可参与排序，会与事件混排 | **不参与排序**，天然隔离 |
| 校验 | 需与事件走同一套硬下界（否则出现"故事能排到起点前"的漏洞） | **跳过校验**，与用户原话一致 |
| 导航 | 出现在 minimap / 语义跳转里 | 不进时间轴导航（靠搜索/标签/侧栏） |
| 前史区兼容 | 若故事有 day 且早于起点，则**前史区失去意义** | 与"前史区承载不可排期叙事"**完美吻合**：故事 = 前史区的天然实体化 |
| 数据迁移 | 无 | 无 |
| 技术复杂度 | 需 `Option<i64>` + `kind` 区分"无日期"与"未填" | 类型即规范，零运行时判断 |

| **10 万年** | **36,524,250** | **3.96e-12 (≈4e-10 %)** | ✅ |
| 100 万年 | 365,242,500 | 3.96e-11 | ✅ |
| i64 上限 | — | **≈ 25,252,734,927,766,556 年**（2525 万亿年） | ✅ |

> **口径注**：`4e-10 %`（百分比）与 `3.96e-12`（比例）是同一数（`4e-10 % = 4e-12`）。本稿统一写成 **约 `4×10⁻¹²`（即 `4×10⁻¹⁰ %`）**。

#### 2.5.2 架构判断：**i64 溢出不是真瓶颈**

i64 对任何文学创作跨度都是过剩的（10 万年仅占 `4×10⁻¹²`）。**真正的瓶颈是 UI 渲染/导航**：

```text
第一轮：500 年 × 360 天 = 180,000 格 —— 已判定"头号交互痛点"
本轮：  10 万年 = 36,524,250 天 —— 1 天 1 像素 = 3652 万格 = 第一轮的 **202.9 倍**
```

**3652 万格在 1200px 屏需 30436 屏横向滚动。** 这不是"滚动慢"，是**滚动这个方法本身失效**。**故预警由渲染层发出、与整数容量解耦，是正确架构。**

#### 2.5.3 阈值、判层、门禁/降级 —— 三问逐条答

| 问题 | 裁定 |
|---|---|
| **阈值卡在哪？** | 技术侧建议 **1,000,000 天（≈2738 年）** 作**软预警触发点**。**设计侧另有"1 万年 / 20 万年"两档（§1.15）**，两者**不冲突、是同一功能的不同档位**，统一方案见 §4.1 N6 |
| **由哪一层判定？** | **`wv-app`（渲染层）**。判定发生在**渲染前**；`wv-core` / `wv-io` **不判**——它们不知道屏幕多宽 |
| **是门禁还是降级？** | **降级（警告但继续）**。返回 `Some(SpanWarning)`，调用方**照常加载**，只是 UI 挂横幅 + 切骨架占位渲染 + 强制启用 minimap。**从不阻断。** |

#### 2.5.4 与 `timeline_range.last_day` 门禁的**关系：两回事**

| 维度 | `timeline_range.last_day`（§2.7.3） | **跨度预警（本轮）** |
|---|---|---|
| **约束对象** | 作者声明的范围 **vs** 实际引用的实体 | 范围**本身**的宽度 |
| **问题性质** | **静态数据合法性**（越界实体 = 数据错） | **体验问题**（合法但画不出来） |
| **判定层** | `wv-io` 加载器 | `wv-app` 渲染层 |
| **判定时机** | 加载期 | 渲染前 |
| **处置** | **门禁：拒绝加载并报错** | **降级：警告但继续** |
| **阈值** | `counter > last_day` | `last_day - first_day > 阈值` |

> **一句话**：`last_day` 门禁管"**数据有没有越界**"，跨度预警管"**范围宽不宽到画不出来**"。两者**阈值不同、判层不同、处置相反**，**互不替代，也不冲突**。

#### 2.5.5 实现（已编译，`crates/wv-app/src/span.rs`）

```rust
//! 跨度预警：**渲染/体验层**判定，与 i64 整数容量解耦。

use crate::error::CoreError;

/// 建议的单轴跨度上限（天数）。= **1,000,000 天 ≈ 2738 年**（软预警档，见 §4.1 N6）。
pub const RECOMMENDED_MAX_SPAN_DAYS: i64 = 1_000_000;

/// 跨度预警判定。**降级语义**：返回 `Some(Warning)` 时调用方**继续**。
pub fn check_span(
    first_day: i64,
    last_day: i64,
) -> Result<Option<SpanWarning>, CoreError> {
    let days = last_day - first_day;
    if days < 0 {
        return Err(CoreError::InvalidSpan {
            from: first_day.to_string(),
            to: last_day.to_string(),
        });
    }
    if days <= RECOMMENDED_MAX_SPAN_DAYS {
        return Ok(None);
    }
    Ok(Some(SpanWarning { days, approx_years: days as f64 / 365.2425, limit: RECOMMENDED_MAX_SPAN_DAYS }))
}

/// 跨度预警内容（供 UI 渲染横幅文案）。
#[derive(Debug, Clone, Copy, PartialEq)]
pub struct SpanWarning {
    pub days: i64,
    pub approx_years: f64,
    pub limit: i64,
}

impl SpanWarning {
    pub fn message(&self) -> String {
        format!(
            "时间轴跨度约 {:.0} 年（{} 天），超过建议上限 {} 天；\
             渲染将切换为骨架模式，请用语义锚点导航。",
            self.approx_years, self.days, self.limit
        )
    }
}
```

> **注意**：这是**降级类**预算，且**给了可执行动作**（骨架占位 + 横幅 + 强制 minimap），动作里写了真实存在的渲染分支。**没有虚构机制。**

#### 2.5.6 「提示作者跨度太大」的 UI 细节

- **仅在创建/修改 `timeline_range` 时弹一次**，不在每次打开工程时骚扰；
- 弹窗给**两个可执行选项**：①"我知道了，按骨架模式打开"（继续）②"我要改小范围"（跳转到范围编辑）；
- **不自动截断、不自动改作者数据**（与 §2.7.3 门禁的"不静默篡改"原则一致）。

#### 2.6.2 时间区间求值性能门槛

| 区间总数 N | 策略 | 阶段 |
|---|---|---|
| N < 5 万 | 朴素 O(n) 遍历 | 阶段五默认 |
| 5 万 ≤ N < 50 万 | 按 begin 排序 + 二分 + 后缀扫描 | 性能门禁触发时 |
| N ≥ 50 万 | 区间树 | 仅在真出现超大工程 |

> **注意**：新模型端点是**单值 `i64`**，排序键从 5 元组塌缩为单键，比较成本更低 ⇒ 门槛**可上调**（具体数值待实测）。

**拖动优化**：**边界跨越检测**——若新 t 与旧 t 之间无任何区间边界，投影不变，零重算。

#### 2.6.3 `timeline_range.last_day` 的处置（门禁类）

| 项 | 内容 |
|---|---|
| **性质** | **门禁类**（无运行时降级） |
| **归类依据** | 约束的是**加载期的静态数据合法性**。运行期不存在"把范围改小"的降级动作——改小会**丢掉数据语义** |
| **阈值与触发点** | `TimePoint.counter > last_day`（当 `last_day.is_some()`） |
| **卡在哪 / 谁判定 / 后果** | 卡在 **YAML 加载**环节，由 `wv-io` 加载器判定；不达标 = **拒绝加载并报错** |
| **为何不用运行时降级** | 造"自动截断到 last_day"会**静默篡改作者数据**，是过度工程 + 数据危险 |

#### 2.7.2 精度的可逆性（T5，**必须写进 ADR**）

**重新引入时分时的路径**：

1. `TimePoint` 当前 = `i64` 天。要加时分，**最小侵入**方案是再包一层 `struct TimePoint { day: i64, minute_of_day: u16 }`——但会破坏 `#[serde(transparent)]`，YAML 形态从裸整数变成 `{day, minute_of_day}`，**又是一次全量 YAML 迁移**。
2. 替代方案（**推荐**）：把刻度降为**分钟**：`TimePoint(i64)` 语义改为"第 N 分钟"，加常量 `MINUTES_PER_DAY = 1440`。YAML 形态仍是裸整数，但**含义变了**——**仍是破坏性迁移**。
3. **结论**：时分若一定有，**早知道比晚知道便宜**。当前按 S7 删除是正确取舍，但**必须在 ADR 里写明"未来引入 = 一次 schema 迁移"**。

#### 2.7.3 历法可插拔的 ADR 约束（**本轮新增，必须写进 ADR**）

| # | 约束 |
|---|---|
| 1 | **`CalendarRule` 是封闭三值 enum**；加第四种历法 = 改两个 match + 加变体（编译期可见） |
| 2 | **历法分派只允许出现在 `calendar.rs` 的显示层函数内**（`civil` / `day_counter` / `format`）；`TimePoint` / `TimeSpan` / `TimelineQuery` **不得引用 `CalendarRule`** |
| 3 | **换历法不迁移任何数据**（R8 通则）；若未来需要真实迁移，说明有人把历法做进了运算层，是 bug |
| 4 | **年号对照只做年份级硬校验**；月日级永不推算（用户 Q1 边界） |
| 5 | **`year = 0` 映射只在 UI 边界发生一次**（§1.16）；运算层一律天文记年 |

### 2.8 `schema_version` 处置：**必须 `2 → 3`**

| 选项 | 说明 | 裁定 |
|---|---|---|
| 保持 `2` | 无法区分"360 硬编码"与"可插拔历法"两代文件——一个无 `rule` 的 v2 文件到底是"v2 的 360 语义"还是"v3 缺省的 360"？**二义** | ❌ |
| **升 `3`** | `CURRENT_SCHEMA_VERSION = 3`。读到 `schema_version: 2` 时给出提示 | ✅ |

**理由（关键）**：虽然 `rule` 有 `#[serde(default)]` 让 v2 文件**技术上能读**，但：
1. **"能读"不等于"语义相同"**：v2 文件的隐含历法语义是"唯一历法 = 360"，v3 的 `fixed_360` 是"三种历法之一的缺省值"。**这是语义变更，不是纯增量。**
2. **`reign_aliases` 是新增能力**：版本号要反映**能力的引入**。
3. **版本号是最便宜的沟通**。

> **不自动迁移**：v2 → v3 **无需改文件**（`rule` 缺省即 `fixed_360`，`reign_aliases` 缺省即空）。**故本轮迁移是"零操作"**——只需加载器**接受** v3 并**提示** v2 作者"你的文件仍是 360 语义，无需改动"。**这与第一轮 1→2 的"硬迁移"性质不同**（第一轮旧文件用 `{era,year,day}`，格式不兼容无法读；v2 文件格式**完全可读**）。

### 3.4 本轮值得记录的协作质量证据

**技术侧的真实自我纠错（实测抓到，非自述）**：

1. **`Fixed360` serde tag 坑**：`rename_all="snake_case"` 对 `Fixed360` 产出 `fixed360`（数字不产生词边界）。若文档按直觉写 `fixed_360`，作者会解析失败。**已显式 `rename` 修正 + 测试钉死。**
2. **MSRV 违规**：一度用了 `Option::is_none_or`（Rust **1.82** 才稳定），**低于工程 MSRV 1.80**。已替换为 `map_or`。**只写不编译会留下 MSRV 违规。**
3. **手写散文数字错两次**：先写"1818/5/5 = 第 124 天"（实为 **125**），又写"`365000` = 1000 年整"（实为 `1000/12/31`；`1001/1/1` = **365001**）。**技术侧自报"散文数字错误率 50%"**。
4. **示例 A 年号自相矛盾（真实错误）**：原稿把**嘉庆（1796–1820）**挂在 `start_year: 1840` 的轴上——**差 22 年**，违反他自己的 `is_year_consistent` 年份级校验。已替换为**道光（1821–1850）**，并补一条"错误年号必须报红"的反例护栏测试。

**主理人独立复核发现的问题**：

| # | 拦截的问题 | 若放过的后果 |
|---|---|---|
| 1 | 技术侧 `last_day: 73050` 曾被主理人误判为错（主理人心算按 0-based 得 `73049`，并短暂指控技术侧） | **主理人自我纠正**：`73049` 是**上一天** `2039-12-31` 的 counter，`73050` 是 1-based 的正确值。**教训：主理人自己也混淆"span"与"counter 值"——恰是它在纠错的镜像。** |
| 2 | 设计侧 §B3 示例 YAML 同样把**嘉庆（1796–1820）**挂在 `1840` 轴上 | 若照抄进交付稿，示例工程年号全部报红 |
| 3 | 设计侧行文仍残留 `CalendarKind` 旧名（§D2 提醒处） | 文档内部命名不一致，作者困惑 |
| 4 | 设计侧跨度阈值（1 万年/20 万年）与技术侧（100 万天）**未统一** | 作者看到两套文案不知道哪个是准的 |

**协作质量结论**：本轮的错误集中在**"散文里的数字"**与**"跨侧未同步的口径"**。前者已固化为 §2.5.3 的数字纪律（所有示例数字进测试决策表）；后者已固化为 §3.3 的收敛记录 + §4.1 N6 待拍板。
