## 0. 一句话结论

**今天的温度 / 湿度根本不是数据。** 它们是「生成期的一次性派生标量」和「主题层的一对 y 轴切点」，
落盘的只有派生产物 `biome`。所以「给 region 加温度湿度属性」不是加两个字段那么简单——
它要先回答：**区域气候覆盖要作用在哪一层（事实 / 表现 / 两者都做）**。

本文 §1 给出精确现状，§2 给出需求分解，§3 并列三个方案，§4 给出推荐，§5 列待裁问题。

## 1. 现状核查 · 温度与湿度现在到底在哪里

### 1.1 三处「气候」，互不相通

| # | 位置 | 形态 | 落盘？ | 消费方 |
|---|---|---|---|---|
| **A** | `crates/wv-terrain/src/continent.rs:363` `climate_at()` | **归一化浮点**（温度 / 湿度各 0..1）· 生成期派生 | ❌ **不落盘** | 同文件 `lowland_biome()`（:406）→ 低地 biome 分带 |
| **B** | `crates/wv-terrain/src/climate.rs:141` `classify()` | 高度阈值 + 纬度切点 + 东陆干旱带 | ❌ 不落盘（模板落的是 biome） | ADR-0037 世界模板生成（`new_project_dialog` / `ui_shell` / `gen_demo`） |
| **C** | `crates/wv-theme/src/decor.rs:83` `DecorRecipe.climate_cuts: [f32; 2]` | **一对 y 轴切点**（不是温度值！） | 主题 crate 常量 | `crates/wv-render/src/terrain_decor.rs:254` → 森林装饰变体（针叶 / 阔叶 / 稀树） |

> ⚠️ A 与 B 是**两套并存的分类规则**（README §12-50 已登记待裁）：同一张图会给出不同答案。
> C 名义上叫「气候带」，实际是**归一化 y**（0 = 北）的切分，与 A/B 的温度量纲无关——
> 评审 A5 已指出 C 与 A 的纬度轴语义相反（A 南北对称寒带，C「北寒南旱」）。

### 1.2 A 的具体公式（`continent.rs:363-399`）

```
warmth    = 1 − |y_norm − 0.5| · 2            // y_norm = 格心 / 图幅高 → 赤道硬编码在图幅正中
altitude  = clamp(height_m / 4000, 0, 1)
temperature = clamp(0.12 + 0.88·warmth − 0.55·altitude + 0.05·(t_noise − 0.5), 0, 1)
moisture   = clamp(0.08 + 0.95·m_noise + coast_wet, 0, 1)   // coast_wet ≤ 0.06
```

### 1.3 温度 / 湿度真正被「用来决策」的地方

只有一处：`lowland_biome()`（`continent.rs:406-457`），只对**低地（< 300 m）**生效，
高地带（雪线 2600 / 山 1200 / 丘 300）**先于气候判定**短路。

| 决策 | 阈值 |
|---|---|
| 雪原 / 苔原 | `temperature < 0.20` / `< 0.34` |
| 热带雨林 | `temperature > 0.72 && moisture > 0.62` |
| 荒漠（主判据） | `aridity = (1−moisture)·hot > desert_threshold`（`0.50 − 0.40·desert_cover`） |
| 荒漠（斑块判据） | `hot > 0.35 && moisture < 0.40 && dry_patch < desert_patch` |
| 森林 / 草原 | `wet·temperate > forest_threshold`（`0.38 − 0.15·forest_cover`），其余草原 |

### 1.4 落盘的东西里没有气候

- `terrain.bin` format_version = 2 = 每格 `(height: i16, surface: u8, biome: u8)` **三通道**（`docs/BINARY_FORMAT_SPEC.md` §2.1）。
- 温度 / 湿度 / 降水**任何一格都不存**。改了纬度或改了 `ContinentParams`，旧工程的 biome **不会自动重算**。
- `ContinentParams`（八参）本身也**不落盘**——只活在 `GenerateContinentCommand` 里（`wv-edit/src/command.rs:322`），
  撤销时逐格回放旧值，重生成靠「同 seed 重跑」复现。

### 1.5 已经存在的「作者声明覆盖派生结果」的两条先例

| 先例 | 载体 | 覆盖什么 | 落盘 | 机制 |
|---|---|---|---|---|
| **生物群系标记**（ADR-0029） | `Place.biome` + `Place.envelope` | **biome（事实层）** | ✅ 标记写格子；边界环存 `place_geometry` | `wv-terrain/src/marker.rs`：包络内已有 ≥8% 且 ≥4 格目标群系 → **识别**（不写格）；否则 → **生成**（写格 + 提环） |
| **区域覆盖物**（ADR-0045） | `Region.overlay: Option<String>` | **长相（表现层）** | ✅ `regions/<id>.yaml` | 主题拥有词表 → `RegionOverlayRule`；键缺失 → 白底红斜线缺失标记（不回退） |

**「水妖区」若只要表现不同，ADR-0045 的 `overlay` 已经能做**（圈一片 → 选 `conifer` / `sparse` / `boulder`）。
用户提的「温度、湿度」是**另一个维度**：它想表达的是「这片地方的气候状态」，而不是「这片怎么画」。

## 2. 需求分解 · 「水妖区不受全局影响」到底要什么

用户的原话拆成四条可判定的诉求：

| # | 诉求 | 判据 |
|---|---|---|
| **N1** | 区域能**声明**自己的气候状态（温度 / 湿度，可能还有降水、风、霜期……） | `Region` 上有可编辑、可落盘的字段 |
| **N2** | 区域内的气候**与全局不同**（不受图幅纬度 / 海拔派生影响） | 存在「覆盖 / 偏移」语义，且能落到格子上 |
| **N3** | 这个气候**要能反过来影响地图**——否则声明了却什么都不变 | 至少影响 biome 分带或底色或装饰 |
| **N4** | 语义要能扩展（水妖 / 雨妖 / 火妖……），不写死「温度湿度两字段」 | 键表开放或结构可扩展 |

### 2.1 关键判断：数据层 vs 表现层

ADR-0045 D2 立过一条判据，本设计必须沿用：

> `cell.biome` = **本质**（深林 / 沙漠）；`region.overlay` = **表现声明**（针叶 / 阔叶 / 石林）。

温度 / 湿度属于哪一侧？两种读法都有先例支撑：

- **读法甲（表现层）**：气候是「这片地方长什么样」的参数 → 与 `overlay` 同族，作者只调表现。
- **读法乙（事实层）**：气候是「这片地方客观多热多湿」→ 与 `Place.biome` 同族，是地物属性，biome 是它的**投影**。

**建议采纳读法乙（事实层）**，理由：温度湿度是**物理量**，不是画法；ADR-0029 已经证明「作者声明覆盖自然派生的 biome」在本仓库是成立的机制
（marker 的「识别 / 生成」二选一 + 边界环快照）。而且事实层有个硬优势：**下游全都能吃到**——
渲染、诊断、MCP 查询、游戏运行时导出（用户明说「游戏地图」）都读同一份事实，不必各自再推导一次。

### 2.2 与既有纪律的张力点（必须显式处理）

| 纪律 | 张力 | 现有 ADR-0045 待裁 3 已问过同一件事（「覆盖物要不要带时间窗」） |
|---|---|---|
| **P7 时间轴驱动** | 「水妖区」在某个纪元变干、某段时间起雾——气候会不会随时间变？ | v1 建议**不带 span**（与 `overlay` 一致），把 span 化挂账 |
| **P6 非破坏编辑** | 改区域气候 → 要不要覆写已落盘的 `biome`？ | 若走「重算并写格」，biome 会被覆写——但 biome 本身无时间轴（§12-47），覆写不违反 P6 存储层要求（可撤销） |
| **P3 YAML 为主** | 气候若做成**每格栅格** → 那是二进制例外（§5 门槛最高）；做成 **region 字段** → YAML 一行 | 倾向 region 字段（YAML），不做新栅格通道 |
| **§4.2 只存参数** | 别存「这片是雨林」（结论），要存「这片温度 0.3 / 湿度 0.9」（参数） | 采纳：region 存**参数**，biome 是派生产物 |
| **§4.4 ID 可读** | 若新增气候档案实体，ID 要 `[A-Za-z0-9_]` | 若做「气候档案」实体则必须遵守 |

## 3. 三个方案（并列，代价写清）

### 方案 1 · Region 气候字段 + 区域重算 biome（**推荐**）

**做什么**

1. `wv-core::model::region::Region` 增一个可选字段（serde default → **旧 YAML 零迁移**）：
   ```rust
   /// 区域气候覆盖（事实层）：None = 继承全局派生气候。
   pub climate: Option<RegionClimate>,
   ```
   `RegionClimate` 定义在 **wv-core**（wv-terrain 是与 wv-core 平行的叶子，**不能**反向依赖它）：
   ```rust
   pub struct RegionClimate {
       /// 温度覆盖（0..1，与 continent::climate_at 同量纲）。None = 继承。
       pub temperature: Option<f32>,
       /// 湿度覆盖（0..1）。None = 继承。
       pub moisture: Option<f32>,
   }
   ```
2. `wv-terrain` 把 `climate_at` 的「采样」与「分带」拆开：分带入口接受一个
   **每格 override 查询闭包**（`Fn(gx, gy) -> Option<(temp, moisture)>`），
   region 覆盖命中则用覆盖值、未命中则用原派生式。
3. `wv-edit` 新增命令 `ApplyRegionClimateCommand`：
   取 region 掩膜（`wv-terrain::divide::rasterize_ring`，或复用 `region::mask_of_ring_set`）
   → 只重算掩膜内**低地格**的 biome → 逐格记录旧值（可撤销）。
   **语义与 ADR-0029 marker 同款**：作者声明 → 写事实 → 可撤销。
4. 渲染层**不消费** region 气候（装饰仍由 y 轴 `climate_cuts` + `overlay` 决定）。
   气候的唯一产物是 biome——保持「一份事实、一处投影」。

**优点**
- 数据层最小改动（Region 一个字段 + 一个命令）；不改二进制格式、不动 `terrain.bin` 版本号。
- 与 ADR-0029「作者声明覆盖派生 biome」完全同构，评审有先例可依。
- 温度湿度成为**可查询事实**（诊断面板 / MCP / 导出都能读），契合「游戏地图」用途。
- 撤销天然成立（逐格 before 缓存，与 `GenerateContinentCommand` 同款）。
- 未来要扩（降水 / 风 / 无霜期）只需给 `RegionClimate` 加字段，不动机制。

**代价 / 风险**
- 「region 气候」与「cell 已落盘 biome」存在**短暂不一致**：作者改了 region 气候，
  在点「应用」之前 biome 还是旧的。→ 需要一个明确的「应用」动作 + 面板上的脏标记。
- 两次改 region 气候 = 两次重算 = biome 被覆写（作者意图如此，但要有 undo 链）。
- 需要把 `lowland_biome` / `band_surface_biome` 从 `pub(crate)` 提升到可被 `wv-edit` 调用（`wv-edit` 已依赖 `wv-terrain`，方向合法）。
- 继承语义（region 声明 `temperature: None`）在嵌套 region 下要定：最深优先？取最具体？
  （ADR-0045 D8 已有「最深优先」的先例可抄）

---

### 方案 2 · Region 气候字段 · 只影响表现（最轻，但语义弱）

Region 同样增气候字段，但**只**作为渲染期第二来源：改装饰变体（替代 y 轴 `climate_cuts`）、
可选改底色 tint（ADR-0045 待裁 2）。

**优点**：改动最小（wv-core 字段 + 渲染层读 region 掩膜），不覆写任何已落盘事实，无不一致窗口。
**代价**
- 气候退化成「画法参数」，违背 §2.1 的读法乙；下游（诊断 / MCP / 游戏导出）读不到气候。
- 与 `overlay` 功能重叠——作者用 `overlay=conifer` 也能达到类似观感，多一个字段意义不大。
- 未来真要让气候影响 biome，还是得再来一次机制升级。

---

### 方案 3 · 第四通道：全图气候栅格（最"正确"，最贵）

`terrain.bin` 升 **format_version = 3**，载荷变 `(height, surface, biome, temperature, moisture)`；
region 气候覆盖 = 对该栅格的一次批量写（`BatchEditCellsCommand` 同款）。

**优点**
- 气候成为**逐格**的一等事实，精度最高（region 内也可逐格不同）。
- 生成期派生值落盘 → 改 `ContinentParams` 后可**重算而不重生成**（当前 biome 不自动更新的老问题一并解决）。
- 全图气候可做等值线 / 热力图等可视化（游戏地图编辑器很想要）。

**代价**
- **动二进制格式**：§5 门槛最高（`RasterRef` 声明、`format_version` 升级、`docs/BINARY_FORMAT_SPEC.md` 改写、
  `wv-io` 迁移路径 v2→v3）。
- 文件体积涨（三通道 → 五通道）。
- **违反 P3 的例外成本**：气候是「连续标量场」，勉强算栅格数据，但它是**冗余**的
  （可由 biome + 纬度 + 海拔重算）→ 落盘即引入**第二真相源**，与 ADR-0039「派生不落盘」纪律正面冲突。
- 生成期派生值要落盘，作者改纬度口径（§12-49 待裁）后旧栅格如何迁移，是个无解的坑。
- 阶段成本高（schema + IO + 渲染 + 迁移 + 全部测试），与本次「加个 region 属性」的诉求量级不匹配。

## 4. 推荐

**推荐方案 1**，理由三条：

1. **与既有机制同构**：ADR-0029 的 marker 已经是「作者声明覆盖自然派生 biome」的成熟先例
   （识别 / 生成二选一 + 边界快照 + 可撤销）。方案 1 = 把那个机制从「Place + 包络」泛化到「Region + 掩膜」，
   评审时有对照物，不新开机制谱系。
2. **不违反 P3 / 不引第二真相源**：气候参数存 YAML（region 字段），落盘的事实仍然只有 `biome`。
   方案 3 反而会引入「温度既是派生又是落盘」的矛盾。
3. **量级匹配**：用户诉求是「给 region 加环境属性」，方案 1 是最小可闭环；
   方案 3 是另一个项目（且它顺带能解 §12-49 / §12-50，但那要单独开 ADR）。

**但方案 1 有三处必须由用户拍板**（见 §5），拍板前不动代码。

## 5. 待裁问题（拍板清单）

### D1 · 覆盖语义：绝对值 / 偏移量 / 继承三态？

- **D1-a** `temperature: Option<f32>` = **绝对值**（0..1，与 `climate_at` 同量纲）。
  区域气候完全接管，区域内的海拔递减 / 噪声全部不生效。
- **D1-b** `temperature: Option<f32>` = **偏移量**（−1..+1，加到全局派生值上）。
  「水妖区比周围冷 0.3」这种表述更自然，且保留海拔效应（山里的水妖区仍比平原冷）。
- **D1-c** 两者都要 → 需要两个字段（如 `temperature` + `temperature_bias`），复杂度翻倍。

> **建议**：**D1-a（绝对值）+ 字段可缺省表示继承**。理由：语义单一、无歧义、
> 与「不受全局影响」的原话一致。若要表达「比周围冷一点」，作者用绝对值填 0.25 即可。
> 代价：区域内的海拔效应丢失（山里的水妖区与海边的水妖区气候相同）——若这不可接受，
> 改选 D1-b。

### D2 · 区域气候字段的**生效范围**：整片区域，还是只有低地？

- 低地（< 300 m）才有分带（§1.3）→ 区域气候只影响低地 biome，高地带按高度阈值不变（与 continent 生成同款口径）。
- 还是区域气候也该压过高地带（让「水妖区」连山都是竹林）？→ 那要改 `band_surface_biome` 的优先级，
  **破坏「高度带优先于气候带」这条既有规则**（GLOSSARY「低地群系」条目明写）。

> **建议**：**只作用于低地**，与生成路径同款口径。高地带另议（若真要，得单独开 ADR 改优先级）。

### D3 · 嵌套 region 的气候怎么合成？

父区声明了气候、子区也声明了 → 谁的赢？

> **建议**：**最深优先**（子区完全覆盖父区），抄 ADR-0045 D8「最深优先」既有先例；
> 且**不做插值 / 不做部分继承**（避免引入第四种组合语义）。面板上要显示「本区继承自父区 / 覆盖父区」。

### D4 · 改 region 气候后，biome 何时重算？

- **D4-a** 显式「应用」按钮（作者点一下才重算掩膜内 biome）→ 与 marker / 「重生成边界」同款交互，
  代价：有「声明已改、事实未更新」的不一致窗口，需要脏标记。
- **D4-b** 改完自动重算（命令即改即算）→ 无窗口，但撤销链上多一步隐式格改，且「作者只是想试个值」时会反复改格。

> **建议**：**D4-a（显式应用）**，与 ADR-0029 / ADR-0045「重生成边界」的既有交互一致。
> 面板上给「区域气候已改 · 待应用」提示（不阻止保存，V1 精神）。

### D5 · 气候要不要带时间窗（span）？

水妖区可能「只在某个纪元是湿地」。但 cell 本身无时间轴（README §12-47），
`Region` 当前也无 span（ADR-0017 §2.3「v0.1 永久可见」）。

> **建议**：**v1 不带 span**，与 `Region.overlay` 同款；把「region 气候时间化」登记到 README §12 待裁
> （与 §12-47 同源）。

### D6 · 字段名与词汇表：数值字段 vs 开放键？

- **D6-a** 数值字段（`temperature` / `moisture` 两个 `Option<f32>`）→ 简单，但词表封闭，扩字段要改 schema。
- **D6-b** 开放键（`climate: Option<String>`，键如 `swamp_demon` / `rain_spirit`，词表由某处拥有）→
  符合 ADR-0032 的「开放集」教训，但**词表归谁**是难题：主题（表现层）不合适（气候是事实层），
  世界自身（world.yaml）？工程内自建 `climates/` 目录？——这会引入新实体族与新 ID 命名空间。

> **建议**：**D6-a 数值字段起步**。理由：气候是连续物理量，键表化等于把连续量离散化再离散化回去；
> 若后续要「水妖 / 雨妖」这种**命名气候档案**，可作为**上层糖**加在数值之上
> （档案 → 数值预设 → region 字段），不动底层机制。

### D7 · 谁读这份气候？诊断面板 / MCP / 导出要不要同步开？

用户明说「游戏地图」→ 未来很可能要**导出气候给游戏运行时**。
本轮是否只做「写 + 影响 biome」，还是同时开一个查询出口？

> **建议**：本轮**只做写 + 影响 biome + 诊断面板显示**；
> MCP / 导出另开一轮（MCP 那条已知缺口见 memory「mcp-http-server-adr-0014」——感知质量）。
