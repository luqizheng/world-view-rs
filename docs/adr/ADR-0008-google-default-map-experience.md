# ADR-0008：Google Default Map 式地图体验

**状态**：已接受（Accepted）
**日期**：2026-10-13
**决策者**：用户（「大地图尽量模仿 google 地图」；随后确认「直接做」）
**关联**：P1 / P3 / P5 / P7、`docs/ART_STYLE_SPEC_v0.1.md`（地图风格部分被本 ADR 修正）、`docs/STYLE_SWAPPABLE_ARCHITECTURE.md`（地图层可替换原则保留）

---

## 1. 处境（Context）

用户对既有大地图呈现方式与地图制作工具不满意。此前的落地路径经历了 JRPG 瓦片图、深海色板、轮廓图、以及一份 Retro JSON 派生的暖棕色「谷歌风」色板，但仍然更像美术底图，而不是作者熟悉的地图浏览 / 整理工具。

问题的核心不是某个色值偏暖，而是**信息层级与交互模型**不像 Google Maps：

1. 默认左键被笔刷占用，作者不能先像看地图一样拖动浏览；
2. 地形栅格的硬边格子感太强，缺少普通地图的平滑边界；
3. 道路是单色单线，没有 Google 式「灰 casing + 白 fill」路缘；
4. 视觉默认入口不是普通地图，作者要先理解视图模式才能开始；
5. 缺少贴边、小体量、常驻的缩放 / 工具控件。

## 2. 决策（Decision）

采用 **Google Default Map 式地图体验**作为大地图的第一入口：

1. **默认视图 = `ViewMode::GoogleMap`**，UI 显示为「地图」；真实地形、色块地形、势力、事件、轮廓仍作为显式分析视图保留。
2. **离线模仿视觉语言，不接入在线瓦片**：近白陆地 `#f8f9fa`、淡水 `#aadaff`、公园绿 `#c9e7c7`、深灰标签、红点白环 POI、白路灰缘。数据仍来自本地 `TerrainData` / YAML 工程。
3. **普通地图折叠地形分带**：沙、草、丘陵、山地、雪等陆上类在 Google 视图中折叠为基础陆地；水、公园 / 森林、湿地保留低信息量色块。高度分析仍走「真实地形」视图。
4. **底图边界使用亚像素渲染**：Google 模式在没有图集时也按 4–8 亚像素 / 逻辑格合成，并在 chunk 纹理上使用线性采样；专题色块视图保持最近邻与清晰格界。
5. **道路双层化**：每条地点边渲染浅灰 casing（6px）+ 白色 fill（3.5px），宽度按屏幕像素定义并随缩放换算。
6. **默认手势改为 Google 式**：左键拖动平移；笔刷默认关闭，作者显式开启「笔刷模式」后才用左键涂抹。右键 / 中键仍始终平移，作为精确编辑的兜底。
7. **右下角常驻小控件**：拖动 / 笔刷切换、`+` / `−` 缩放、全图复位。控件不进入浮动面板体系，不遮挡地图主体。

## 3. 理由（Rationale）

- **用户意图**：用户明确要求「尽量模仿 google 地图」，这指向浏览优先的普通地图体验，而不是 JRPG 美术或专题分析图。
- **P1 / P3**：本方案只模仿视觉与交互语言，不引入 Google 在线瓦片、账号、网络服务或专有数据；世界数据仍是本地 YAML / 已声明二进制栅格。
- **P5**：底图、道路、地点、事件、势力仍是图层化叠加，Google 式底图不吞并其它图层。
- **P7**：底图渲染仍从 `WorldProjection` / `ProjectionFrame` 消费某时刻投影，渲染层不做时间比较。
- **可用性**：先浏览、后编辑的手势顺序符合地图工具直觉；显式开启笔刷可避免打开项目后第一拖动就误改世界。

## 4. 代价与影响（Consequences）

- Google 视图的信息量低于地形分析视图：高度分带被折叠，作者看海拔必须切「真实地形」。
- 道路从每边一个实体变为 casing + fill 两个实体，可视道路数约增加一倍；换来 Google 式可读路缘。
- 左键语义随工具态切换：拖动模式平移、笔刷模式涂抹。控件与笔刷面板必须始终明示当前状态。
- Google 视图的纹理分辨率提高会增加像素合成与上传量，但仍在既有 4096² 纹理预算内；专题视图保持原预算。
- 视觉模仿是**手工近似**，不承诺逐像素等同 Google Maps，也不使用其商标素材。

## 5. 被否决的备选（Alternatives）

| 备选 | 否决原因 |
|---|---|
| 接入 Google Maps 在线瓦片 / SDK | 违反 P1 单机可运行；引入网络、账号 / API key 与服务端状态 |
| 继续修正 Retro JSON 暖棕色板 | 仍呈羊皮纸 / 美术底图感，无法满足「像 Google 地图」 |
| 只把 Google 设为一个可选模式 | 默认入口仍是地形 / JRPG 式地图，作者的首次体验不变 |
| 完整复刻 Google Maps UI（搜索框、街景小人、图层卡片全量布局） | 会挤压世界观编辑器的时间轴、检视器、校验面板；应只借用地图主体交互模式 |
| 保留左键笔刷默认开启 | 与地图浏览心智冲突，且容易误改世界数据 |
| 用在线前端 / Canvas 重写地图 | 破坏当前 Bevy / wv-core 分层与已有编辑链，成本不成比例 |

## 6. 与旧文档的关系

- `docs/ART_STYLE_SPEC_v0.1.md` 中「地图是画出来的 JRPG 世界」的地图风格结论，在**地图默认视觉与交互**层面被本 ADR 修正；其「软件壳保持工具型、地图风格与软件壳解耦」的架构结论继续有效。
- `docs/STYLE_SWAPPABLE_ARCHITECTURE.md` 的可换风格接口不受否定：Google Default Map 是第一个默认风格实现，不是关闭未来 Theme Pack 的决定。


## 7. 补充测算（2026-10-13）

- **分辨率口径**：4–8 亚像素 / 逻辑格仅适用于不超过 1024 格的地图；更大的地图按 4096² 纹理预算回落到 1–4 亚像素 / 逻辑格。
- **当前内存代价**：既有架构同时保留一张整图 source `Image`（供 minimap / CPU patch）与视口内 chunk `Image`（供主视口分块渲染）。Google 512² 地图在 4096² 分辨率下会持有 source + chunk 至少两份全分辨率 RGBA，再加 chunk mip 链；这不是单张 67MB 预算，而是约两倍以上的峰值内存。
- **为何先接受该代价**：本轮目标是修正默认地图体验且不重构加载/分块架构；chunk 资产已在 despawn / 模式切换后释放，避免继续累积。后续优化方向是“低分辨率 minimap + 由 `TerrainData` 直接生成 chunk”，使主视口不再复制整图 source。

## 8. 落地记录：屏幕像素 → 世界单位的换算方向（2026-10-14）

本 ADR §2 的决策「道路 casing 6px + fill 3.5px，宽度按**屏幕像素**定义并随缩放换算」在首次落地时把换算方向写反了：渲染端一律写成 `world = stroke_px / view.scale`，而 `view.scale` 的单位是**世界单位/像素**（见 `ViewState::scale` 的文档、`terrain_chunks.rs` 的视口换算，以及标签 `font_size = LABEL_PX * view.scale`、POI 半径 `POI_MIN_SCREEN_PX * view.scale` 等按「乘」写且实机显示正确的既有代码），因此恒定屏幕宽度必须**乘** scale。

- **实际效果**：屏幕宽度实际变成 `stroke_px / view.scale²`。世界级（scale ≈ 2.4）下 3.5px 的道路只有约 0.6px，几乎是一条发丝；深缩后（scale ≈ 0.07）同一条道路胀成占屏 40% 的巨带（实测 600px 以上白填充 + 每侧约 160px casing）。**这正是「地图上看不见街道」的直接根因**——不是颜色问题，而是线宽问题。
- **修复**：`vector_layers.rs`（道路 / 街道 fill / 街道 casing / 橡皮筋预览）、`map_frame.rs`（外框 + 参考网格）、`brush_cursor.rs`（笔刷外环 / 内环虚线 / 十字）三处的 `px / view.scale` 统一改为 `px * view.scale`；`ui.rs` 小地图的视口取景框同步改为 `(窗口宽 × view.scale) / 底图世界宽度`，原 `1.0 / view.scale` 的量纲同样是反的（越深缩框越大，深缩时框占满整幅小地图）。
- **判定依据**：同仓内 `brush_cursor.rs` 自相矛盾（同一文件里 `px / view.scale` 与「世界 × view_scale == 像素」两种口径并存），后者的方向才是对的。修复后 `world_thickness / view.scale == stroke_px` 恒定，`road_spec_screen_width_stays_constant_across_zoom` 与 `stroke_world_screen_width_stays_constant` 两个测试改为此断言（原 `..._inverts_with_view_scale` 两个测试断言的是错误方向，已随公式一并改写）。
- **代价**：世界级视图下的城市连线由发丝线变为 3.5px fill + 6px casing 的醒目连线，城市层级内街道为 4.5px。若后续希望远观更含蓄，应新增**按 LOD 分级的线宽常量**（本 ADR 的 6/3.5px 是单一口径，不含分级），而不是再次反转换算方向。
