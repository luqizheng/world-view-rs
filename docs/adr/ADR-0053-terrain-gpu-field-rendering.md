## 1. 处境（Why Now）

**观感问题已连调三轮**（ADR-0016 → 0035 → 0042 → 0048），每轮结论都是「截图好看一点、放大还是糊」。本轮诊断出两个**可复算的物理上限**（已实地复核：`tile_atlas.rs:141` `tile_res_for(1024)=4`；`state.rs:1083` `cell_size=8.0`）：

1. **近观**：烘焙纹理硬上限 4096² ÷ 1024 格 = **4 px/格**；近观一格 ≈32 屏幕px → 放大 8×。规格书 §3.1「描线 = 边长 1/16」在 4px 格上 = 0.25 texel，**物理不可实现**——不是没画，是画不出来。
2. **远观**：fit 时一格 ≈1.56 屏幕px，细节全灭，只能靠大尺度构图（区域色块 / 山链 / 海岸色带 / 纸面材质）——而现行管线没有构图层。

**结论：这不是配色问题（调三轮已证），是「位图有分辨率上限」的架构问题。** 同日的《地图渲染实施方案 v0.1》（柯桥良章）主张「维持 CPU 烘焙 + 补全」，与本方案构成 T0 路线之争；用户裁定 **甲（GPU 路线胜出）**。

## 2. 决策（Decision）

采纳 `TERRAIN_VISUAL_OVERHAUL_PLAN_v1.0` 的 D1–D9，含一处交叉修正（D3）：

| # | 决策 | 类型 |
|---|---|---|
| D1 | 底图默认路径：CPU 烘焙单张整图纹理 → **GPU 逐像素求值**（3 张数据纹理 8MB + `TerrainFieldMaterial` WGSL） | 推翻 |
| D2 | 边界处理：像素级 `wobble_px` 抖动 → **SDF 距离场 + 世界坐标域扭曲**（幅度 `clamp(2×scale, 0.05, 0.)`，远观手绘感 / 近观编辑精度） | 推翻 |
| D3 | 地物：Mesh2d primitive → **图集 Sprite 实例化**，**按 T1 同款双轨修正**：程序化符号保留为 `_default` 基准（甄塑之判「超集/资产」），图集 Sprite 为位图 pack 能力，**不删程序化路径** | 推翻+修正 |
| D4 | 数据模型 `TerrainData{height, surface, biome}` 三通道不动 | 保留 |
| D5 | 色板 `PaletteColors`/`ThemePack` 令牌体系不动，改为 shader uniform 消费 | 保留 |
| D6 | `ViewMode` 七档全保留，改 uniform 分支 | 保留 |
| D7 | 主题可换：换 pack = 换 uniform + 换图集，零代码 | 保留 |
| D3 补充：D8 | 构图：新增「区域层」与「纸材质层」为独立 Z 序图层 | 新增 |
| D9 | 规格书增补 §3.8「渲染实现契约」（屏幕像素口径），原文不改 | 新增 |

**与 T1–T5 待裁基线的合并**（`RENDER_IMPLEMENTATION_PLAN_v0.1.md` 第三部分）：本 ADR 的 D3 修正与 T1（双通道）一致；M2/M-A（色板+文档追记）不受本裁定影响，照常先行。

## 3. 理由（Why This）

1. **位图有分辨率上限，逐像素求值没有**——这是唯一能同时解决「放大糊」与「缩小散」的架构。
2. **被否决备选已穷尽**：提高纹理上限（16384²=1GB 显存）、分块高分辨率烘焙（视口 9 块=600MB）、autotile 47 块（不解决放大糊）、再调色板（三轮已证无效）、全矢量等值线（成本更高且海面仍需栅格求值）。
3. **已验证资产原样迁移**：SeaRecipe / 色板 / soften_keep 0.92 / VEIL 0.12 / mountain #9E9070 等历史调参成果全部搬 uniform，不推翻（R5 处置）。
4. **回退保险**：`FieldRender` 一行开关，关=完整回到现行烘焙路径。

## 4. 代价与风险（Cost）

- 新增 shader 管线（P1 约 900 行含测试）；`cells.rs` 烘焙主路径退役为回退；`terrain_chunks.rs` 从「性能命脉」降级为「可选批处理优化」。
- **Bevy 版本耦合加深**：WGSL import 段随版本变（R1）——P1 第一步先跑官方示例核验 import 路径，不凭记忆写。
- 集显需低配档（R2，fbm 降 octave / bicubic 降 bilinear，uniform 开关）。
- **性能预算**：8MB 显存（vs 67MB+mip）；每像素 ≈20 采样，1600×900 预期 <1.5ms（4060 级），集显 4–6ms；笔刷一格 <0.05ms（vs 重烘脏区 1–8ms）。
- **实施方案柯章 §3.1 主管线描述让位**：M1 中的「CPU 烘焙语境下的斜投影 texture-bake」需重新评估与 GPU 路线的衔接（T3 斜投影在 GPU 路线下改为 shader 内变换，机制简化但需重写实现路径）。

## 6. 被否决的备选

| 备选 | 否决理由 |
|---数字|---|
| 乙案：CPU 烘焙维持+补全（实施方案柯章原案） | 4px/格上限不动，8× 放大仍糊；调参三轮已证该层修不动 |
| 提高烘焙上限至 8192²/16384² | 1024 格仍只 8px/格；1GB 显存；ADR-0020 分块白做 |
| 分块烘焙每格 16px | 视口 9 块 = 600MB 显存 + 重烘时间不可接受 |
| autotile 47 块全集 | 解决拼接不解决放大糊；与 SPEC §3.2.1 冲突 |
| 再调色板（第四轮 ADR-0035 式） | 三轮已证「截图好看一点、放大还是糊」 |
| 全矢量等值线 | 成本更高；海面/颗粒/渐变仍需栅格求值；留作 P5 后可选演进 |

## 7. 落地阶段（P0–P5，每步可验收可回退）

P0 规格锁（数值表+SPEC §3.8，零代码）→ P1 数据纹理+最小 shader（~900 行，解决约 60% 的丑；一行回退）→ P2 手绘化（域扭曲/hillshade/水彩/缩放自适应）→ P3 地物图集（双轨）→ P4 构图层+纸面 → P5 低配档（可选）。

**闸门规则**：每阶段固定机位截图对比，不看图不进下一步。
