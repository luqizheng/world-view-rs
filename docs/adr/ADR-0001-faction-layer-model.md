# ADR-0001：势力层模型（不设层级枚举）

- **状态**：已接受（Accepted）
- **日期**：2026-10-11
- **决策者**：用户裁定 **D2**（原始裁定者）／创意总监 游有方（提出「势力层 = 多边形集合」）／技术架构总监 柯桥良（模型定稿稿）／主理人 范可控（拦下「归属查询被合并」的错误）
- **关联**：`docs/MAP_EDITOR_BASELINE_v1.md` §2.5 / §2.6 / §2.10 / §1.19 / §5.1；`AGENTS.md` §1 P4、P6；`README.md` §3 原则四、原则六；**ADR-0002**、**ADR-0003**

---

## 背景与问题

编辑器需要表达「这块地属于谁」——国界、省份、贵族领、派系据点、教团辖区、行会势力、部落范围……

最初的方案（v0.2）用**枚举**表达层级，例如 `enum FactionLevel { Kingdom, Province, Noble }`。这个方案在用户提出的一个具体场景上直接崩塌：

> 「假设欧洲法国，有贵族控制多个省或者一个省，几个贵族属于一个雅各宾派。那么贵族领地可能不够分。」

枚举方案的三处失效：

1. **枚举是封闭集，而政治归属是开放集。** 国界/省份/贵族领/派系/教团/行会/公司/部落/军阀……作者的设定集可以无限扩张。用有限枚举表达无限世界是**模型设计错误**——每出现一种新势力，都要改代码、改枚举、重新编译。
2. **枚举隐含「层级」，但现实中层级本身是模糊的。** 一个贵族可能既领有省份、又加盟了横跨全国的派系；派系据点可能散落在多个省份内部而**不构成任何连续领土**。「国境 > 省 > 贵族」这种线性层级根本装不下这些关系。
3. **一层只能有一个归属。** 枚举层级下，一块地往往只能标注「属于某国」或「属于某省」（互斥）。而史实上一点同时属于「省 + 某贵族领 + 某派系」是常态。

**若不决策会怎样**：政治数据一旦按枚举落盘，返工需覆盖**全部**政治数据。基线 §7 记录这是一类「最贵的错误」。

---

## 决策

**不设层级枚举。** 统一用**「势力层（Faction Layer）」**这一套机制承载全部政治划分，由**数据**而非**枚举**决定。

用户原话（基线 §0.2 C 组，本轮最重要的一条规格）：

> 「不要用枚举吧。万一有新增其他势力的可能？假设欧洲法国，有贵族控制多个省或者一个省，几个贵族属于一个雅各宾派。那么贵族领地可能不够分。我的想法是：**国界、省份、贵族等等，都叫做势力层。可以命名，然后绘图。**」

### 决策的四个组成部分

**（1）三层概念分离**

```
势力层（FactionLayer）   ← 作者命名的一个「政治划分维度」，如「国界系统」「贵族体系」「派系」
   └── 势力（Faction）      ← 层内的一个实例，如「大陈」「北境省」「镇北侯」「雅各宾派」
          └── 隶属（Membership） ← 有向、多对多、跨层、带时间
```

**关键裁定：「层」与「势力」是两个层级的东西。**
- **层**是「一个划分维度」（作者命名，如「贵族体系」）；
- **势力**是「该维度下的具体条目」（如「镇北侯」）。

`FactionLayer.name` 是**作者自由命名的字符串**，不是枚举值。

**（2）势力层 = 多边形集合（不是单多边形）**

`Faction.territory: Vec<GeometrySpan>` —— **每块领土是一个 span**。

这条是**必须的**，否则「散点式派系」整类用不了：**雅各宾派**不是一个连贯的领土，而是**散布在多个城市的据点网**。单多边形表达不了据点网；「多边形集合」可以。

用 `Vec<GeometrySpan>`（而非新增 `MultiPolygon` 类型）的额外收益：
- 每块可带**独立 `TimeSpan`** → 「A 地块 1800 年割让、B 地块 1820 年并入」可直接表达（**比 `MultiPolygon` 更强**）；
- 每块可带独立 `owner`/`map` → 跨地图领土可表达；
- **无新增枚举变体** → 旧 YAML 兼容（非破坏扩展）；
- 渲染侧「每个 span 转成一段 Mesh」，块数 = `Vec` 长度，自然对应。

**（3）归属是多对多，且带作者自定义的类型标签与时间区间**

`Membership` 是一个**实体**（不是 `HashMap<Id, Vec<Id>>` 的一条边），因为它需要携带属性：

```rust
pub struct Membership {
    /// 上级势力的 ID（被隶属方）。**可为人或势力层**。
    pub to: Id,
    /// 关系类型（自由字符串，**刻意不做枚举**）。
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub kind: Option<String>,
    /// 该隶属关系的时间区间。
    #[serde(flatten)]
    pub span: TimeSpan,
}
```

| 属性 | 取值 | 为什么不能用枚举 |
|---|---|---|
| **`kind`（关系类型）** | `String`，非枚举 | 关系类型同样是**开放集**：效忠/加盟/主从/结盟/纳贡/名义归属/政治派系……与 D2 同一理由 |
| **`span`（时间区间）** | `TimeSpan` | 隶属**随时间变化**：1789 年前属 A，之后属 B。存「当前归属」即违反 P6/P7 |
| **多重性** | 一个势力可有多条 `Membership` | 一个贵族既领有多个省、又加盟一个派系 → 就是**多条边** |
| **跨层** | `to` 可以是任意层里的势力 | 「镇北侯 → 北境省」跨层、「镇北侯 → 雅各宾派」跨层，都合法 |
| **方向** | 有向：`from`（下级）隶属 `to`（上级） | 版本字段内 `Membership` 存于下级势力的 `memberships` 中，`to` 指上级 |

多对多的三种验证场景（基线 §2.5.5，用户的法国例子）：

| 场景 | 数据形态 | 结论 |
|---|---|---|
| A. 一个贵族控制多个省 | 一个势力 → 两条 `Membership` | ✅ 控多省成立 |
| B. 一个省有几个贵族 | 两个势力 → 两条指向同一省的边 | ✅ 一省多贵族成立 |
| C. 几个贵族属于一个雅各宾派（跨层） | 各贵族 → 各自一条指向派系的边，且与「隶属省份」的边共存 | ✅ 跨层多对多成立 |

**（4）「声称（Claim）/ 实控（Control）」两层语义分离**

势力范围有**两层语义**，**必须分开存储**：
- **声称（Claim）** = 纸面上的宣称（地图上这样画）；
- **实控（Control）** = 实际管辖（现实中这里听谁的）。

二者常不一致（一个政权声称某地但实际失控），**合并存储会丢失作者的表达意图**。

> **分期说明（基线 §1.19 K9）**：「声称 / 实控」双语义的**UI 呈现**可延后至阶段二；本节先确认**模型上必须分开**，不设单一「range」字段。

**（5）「无主地（Unclaimed）」不报错，只灰显**

`query_at_point` 返回的归属集合为**空**时：
- **不是错误**，**不抛异常**；
- **不阻塞**任何操作；
- UI **灰显**即可。

理由：世界地图上存在「无人宣称」的区域是**正常状态**（荒野、公海、争议地带），把它当错误会逼作者为了消错而编造归属。

### 重叠与查询规则（定稿）

**原「层内不重叠 → 报错」的规则已废除**，替换为：

| 编号 | 规则 | 内容 |
|---|---|---|
| **R1′** | 一切重叠合法 | 不存在任何「重叠即冲突」判定。任意数量、任意层的势力可覆盖同一点 |
| **R2′** | 查询返回「归属集合」 | 返回 `Vec<(layer_id, faction_id)>`，可含多项（如 3 贵族 + 1 省 + 1 派系） |
| **R3′** | 绘制顺序决定视觉叠压 | 由 `z` 决定；叠压是**渲染语义**，不是**数据冲突** |
| **R4′** | 无归属 = 无主地 | 归属集合为空 → 灰显，不报错 |
| **R5′** | 归属集合按时间过滤 | 每条归属带 `TimeSpan`，查询时先按 `t` 过滤 |

**归属查询必须拆分为三个 API**（基线 §2.5.4，主理人拦下的关键修正）：

| API | 输入 | 输出 | D5 期（无几何）行为 |
|---|---|---|---|
| `query_at_point(map, point, t)` | 地图 + 坐标 + 时刻 | 归属集合 `Vec<(layer_id, faction_id)>` | ⚠️ **返回空**（无几何无法判定） |
| `memberships_of(entity_id, t)` | 任意实体 ID + 时刻 | 该实体的隶属关系列表 | ✅ **完全可用**（纯关系数据） |
| `subordinates_of(entity_id, t)` | 任意实体 ID + 时刻 | 下级势力 ID 列表（反向） | ✅ **完全可用** |

> **为什么必须拆**：`Membership` 是**边**（图数据），`territory` 是**面**（几何数据）。前者回答「谁隶属谁」，后者回答「这块地属于谁」。**数据源不同，API 必须分开。**
> **若合并 → D5 期会把「关系查询」这个零成本功能一起砍掉。** 这是本项目曾经差点犯下的错误（基线 §7 拦截记录 #3）。

**反向索引**：`subordinates_of` 是反向查询，需 `MembershipIndex`：
- 建在 **`wv-core` 的查询辅助结构**，**不进数据模型**（派生数据，存盘即冗余）；
- 由 `wv-io` 加载完后调用 `MembershipIndex::build(&world)` 构建；
- 第一版**每次查询时重建**（N 小），标注 `TODO(阶段X)`。**失效策略见 §「待裁」**。

### 与图层体系（`LayerKind`）的关系

**核心区分：枚举管「怎么画」，数据管「画什么」。**

| 概念 | 是什么 | 数量 | 载体 |
|---|---|---|---|
| **`LayerKind`（图层类别）** | 「这一类图层用什么渲染管线 / 什么编辑工具」（Terrain/Road/**Faction**/Custom…） | **固定** | **枚举**（渲染管线确实是封闭集） |
| **势力层实例** | 「作者命名的那个具体的层」（国界/贵族体系/派系） | **动态、开放** | **数据**（`FactionLayer` 实体） |

- `LayerKind` **只新增一个 `Faction` 变体**（唯一的枚举扩张）。
- **数据驱动生成图层**：作者建 N 个 `FactionLayer` → `wv-io` 加载 → `wv-app` 启动时为每个 `FactionLayer` 生成一个 `Layer` 条目 → 图层树出现 N 个可独立开关的图层（**数量由数据决定**）。

> **边界重申**：枚举的**唯一职责**是「告诉渲染器这段数据要用哪条管线画」。**枚举绝不承载「世界上有哪些势力」这一信息**——那是数据的事。这正是 D2 的本质。

## 硬约束

本 ADR **不承载 A1/A2/A3**（三条硬约束分别归属 ADR-0002 与 ADR-0003）。但本决策受**两条设计原则**的硬约束，一并列出：

| # | 约束（逐字引用） | 如何约束本决策 |
|---|---|---|
| **P4** | **原则四 · 多地图层级**：世界 → 区域 → 城市 → 建筑/室内，逐层引用。层级之间通过 ID 引用，不重复存储。 | `Membership.to`、`territory[].owner/map` 一律用 `Id` 引用，**不复制**被引用对象的内容 |
| **P6** | **原则六 · 非破坏编辑**：笔刷/选区可撤销、可重做、可保存快照。编辑不是覆盖，是可回溯的操作历史。 | 势力边界与归属一律以**带时间区间的 span** 增量追加，**不存「当前归属」字段**。**注意**：P6 约束的是**存储层形态**，不限制作者改历史——见 `AGENTS.md` §7.5 |

以及 `AGENTS.md` §4.1 的落地判据：

> **如果这个字段的值会随时间改变，它就必须是区间化的。**

`Membership` 带 `TimeSpan`、`territory` 是 `Vec<GeometrySpan>`，都是这条判据的直接产物。

---

## 理由

**（1）P4 的正面要求。**

`AGENTS.md` §1 定义 P4 的违反形态为「**子图内容被复制进父图，而非 ID 引用**」。势力模型中：
- 一个势力跨多张地图时，靠 `territory[].map` 引用地图 ID，**不把子图的几何复制到父图**；
- `Membership.to` 引用势力 ID，**不内联被隶属势力的名字/几何**。

**（2）P6 + P7 的直接产物。**

势力范围会随时间改变（《README.md》§2「时间维度」：拖动时间轴，势力范围随之变化）。因此：
- 存「当前疆域」→ 违反 P6（覆盖历史）与 P7（存当前值）；
- 存「带区间的疆域 span 列表」→ 与时间轴驱动天然统一。

**（3）「用数据承载开放集」是一条通用原则。**

D2 的本质（基线 §0.2 C 组按语）：

> **用有限枚举表达无限世界，是模型设计错误。** 政治归属是开放集，必须由**数据**承载，不能由**枚举**承载。

这条原则在本 ADR 中被**应用了两次**：一次在「势力层/势力」（层与条目都是数据），一次在 `Membership.kind`（关系类型也是数据）。ADR-0002 的「事态」再次应用了同一原则。

**（4）主理人的一次拦截（基线 §7 #3）。**

归属查询曾被合并成单一 API，导致柯桥良推导出「D5 期返回空」，**顺手把关系查询也砍掉**。而关系查询**不需要几何**，是 D5 期**唯一还能提供价值**的能力。拦截后拆成三个 API，D5 期作者白得一个零成本功能。**本 ADR 把「必须拆」固化，防止此错误复发。**

## 后果

### 正面

- **无限世界可表达**：新增任何政治实体（公司、教团、部落、公司、军阀…）**零代码改动**——只需新增一份 YAML。
- **用户法国例子三种场景全部成立**（一贵族控多省 / 一省多贵族 / 多贵族跨层属一派系）。
- **散点式派系可表达**（雅各宾派据点网）——这是单多边形方案做不到的。
- **重叠合法**，符合史实（一点可同属省 + 贵族领 + 派系），无需为消解冲突编造数据。
- **非破坏 + 时间轴驱动统一**：疆域与归属都是区间数据。
- **D5 分期不丢功能**：即使第一版砍掉几何绘图，`memberships_of` / `subordinates_of` 仍完全可用。
- **旧 YAML 兼容**：`territory` 用 `#[serde(default)]` 空 `Vec` + `Vec<GeometrySpan>`（无新枚举变体），非破坏扩展。

### 负面 / 代价

- **缺乏「层级」带来的排序/聚合便利**：枚举方案能天然给出「国 → 省 → 县」的树，数据方案不能。**需要靠关系查询（`subordinates_of`）自己聚合**。这是换取表达力的必然代价。
- **作者需要理解「层 / 势力 / 归属」三概念**：概念门槛高于「选一个层级枚举」。**兜底**：属性检查器（P-4）与势力编辑面板（P-6）提供引导。
- **`MembershipIndex` 是派生数据，有失效策略问题**：第一版「每次查询重建」，N 超 1 万时需改增量。**记为待裁**。
- **无主地灰显可能让新手困惑**（「为什么这块没颜色？」）。**兜底**：tooltip 提示「此区域未被任何势力层覆盖」。
- **依赖 `Layer` 新增 `faction_layer` 反向字段**：属非破坏扩展（`#[serde(default)]`），但引入了 `Layer ↔ FactionLayer` 的双向关联，需保证一致性。

### 待裁

| 项 | 状态 | 说明 |
|---|---|---|
| **带洞多边形** | **待裁**（README §12） | 第一版不支持；`GeometryData::Polygon` 是单环扁平点列，无内环概念。作者用多 sub-span 近似（「回」字拆四块）。回退成本低（未来可加 `PolygonWithHoles { outer, holes }` 变体） |
| **反向索引失效策略** | **待裁**（README §12） | 第一版「每次查询重建」，N 超 1 万时改增量 |
| **`default_parent_layer` 的实际用途** | **待裁**（**本 ADR 新增发现**） | 基线 §2.5.2 定义该字段为「本层与其他层的隶属规则（可选，仅作编辑器默认预设）」，但**未说明它如何被消费、与 `Membership` 的优先级关系**。建议先不实现，仅作 YAML 占位 |
| **`territory` 与 `Membership` 的一致性校验** | **待裁**（**本 ADR 新增发现**） | 一个势力有 `territory`（面）又有 `memberships`（边）。**两者是否应互相校验**（如「有领土却无任何上级隶属」是否预警）？基线未规定。第一版建议**不校验**，只做展示 |

## 备选方案（被否决的）

| 方案 | 否决理由 |
|---|---|
| **A. 层级枚举**（`enum FactionLevel { Kingdom, Province, Noble }`） | ❌ 用户 D2 亲自否掉。枚举是封闭集，政治归属是开放集；新增势力需改代码；线性层级装不下「贵族跨省 + 加盟派系」的多对多跨层关系。**最贵的一类错误**（基线 §7 #2） |
| **B. 单多边形势力**（`territory: GeometrySpan`） | ❌ 「雅各宾派」是**散点式据点网**，单多边形表达不了 → 「派系」整类用不了（基线 §7 #4，游有方抓到） |
| **C. 归属用 `HashMap<Id, Vec<Id>>`** | ❌ 归属需要携带属性（`kind`）与自己的时间区间（`span`），必须是**实体**而非一条裸边 |
| **D. `kind` 用具名枚举**（`enum MembershipKind { Vassal, Ally, … }`） | ❌ 与 D2 同一理由：关系类型是开放集，枚举化会再次制造「改代码才能加关系」的僵局 |
| **E. 合并三个归属查询为单一 API** | ❌ 主理人拦截（基线 §7 #3）。`Membership` 是边、`territory` 是面，数据源不同；合并会导致 D5 期连「关系查询」一起丢掉 |
| **F. 用 `MultiPolygon` 表达多边形集合** | ❌ `Vec<GeometrySpan>` 已足够，且**每块可带独立 `TimeSpan`/`owner`/`map`**，强于 `MultiPolygon`；`MultiPolygon` 还要新增类型，破坏旧 YAML 兼容（基线 §2.10） |
| **G. 把「声称/实控」合并为单字段** | ❌ 二者常不一致，合并即丢失作者意图（P-）（基线 §1.19 K9 分期、V31） |
