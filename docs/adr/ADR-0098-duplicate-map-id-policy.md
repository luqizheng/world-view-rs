# ADR-0098: 同 id 双份地图目录的处置——加载留首份 / 保存去重 / 诊断提示

- 状态：已接受（2026-10-31，修「新建图保存后变孤儿」事故时确立）
- 关联：AGENTS §7.5 V1（校验只提示不阻止）、§4.4（ID 可读字符串）、ADR-0096（AI 自验收在该链路上撞见事故）

## 1. 处境（Context）

`maps/` 目录下允许任意子目录名，图节点 id 由 `index.yaml` 的 `id:` 声明——**目录名与 id 可以不一致**。演示工程因此长期存在同 id 双份：`maps/world/` 与 `maps/world_main/` 都声明 `id: world_main`（历史遗留，前者带 icons、后者带 unit_per_km，靠「加载时先命中前者」勉强工作）。

在这个形态下暴露了真实事故（2026-10-31，AI 自验收时实锤）：

1. 全仓一切「按 id 找图」都是 `find(|m| m.id == …)` → 命中**先加载**的那份（目录名排序靠前）；
2. `create_map` 把新图 id 回填进**第一份**的 `children`；
3. 保存时 `save_maps` 按 **id** 定落盘路径（`maps/<id>/index.yaml`），两份都写到同一文件——**后写覆盖前写**；
4. 结果：回填的 `children` 被第二份抹掉 → **新建的图保存后变孤儿**，不可导航且无任何提示。数据丢失级。

## 2. 决策（Decision）

1. **加载侧去重，保留先加载的一份**（目录名排序靠前）。理由：让内存与「按 id 查找」的既有语义完全一致——否则去重规则与查找规则不一致，会制造新的隐性歧义。
2. **保存侧去重**（防御纵深）：同 id 只写第一份，不再互相覆盖。
3. **磁盘上的重复由 `diagnose` 报 Error**（指纹 `duplicate-map-id:<id>:<目录>`），文案指明两个目录并建议删除/改名其一。**只提示、不阻止保存**（V1）。
4. **演示工程数据修正**：把 `maps/world/` 的 `icons` / `unit_per_km` 并入 `maps/world_main/index.yaml`，删除 `maps/world/`；其地形（声明校验和指向的那份）移到 `maps/world_main/terrain.bin`（行为逐位不变）。

## 3. 理由（Rationale）

- **为什么不在加载时报错拒绝**：V1 明确「悬空与矛盾只提示不阻止」——作者要能打开工程修它；拒绝加载等于让人连修的机会都没有。
- **为什么保留首份而不是「合并两份」**：合并需要字段级冲突裁决，规则必然比「先到先得」复杂且不可预测；先到先得与既有 `find` 语义同构，作者也容易理解（改了前面的那份才生效）。
- **为什么保存也要去重**：加载去重后内存理论上无重复，但 `create_map` / 命令层可能构造出内存级重复（如未来批量导入），保存层兜底可把「静默覆盖」变成「确定只写一份」。

## 4. 代价（Consequences）

- 作者的重复目录里，**后一份的编辑不会生效**（加载即丢弃）——由 Error 级诊断明确告知，可接受；
- 诊断每次都会报直到作者清理目录（无「已忽略」以外的静默路径）；
- **被否决的备选**：
  - 保存时按目录名而非 id 定路径：会让 `index.yaml` 里的 `id` 与目录脱钩，`maps/<id>/` 的直觉失效，且需同步改 loader 与一切路径假设，成本大；
  - 加载报错拒绝：违反 V1，弃。
