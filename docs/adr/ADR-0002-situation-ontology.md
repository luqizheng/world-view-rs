# ADR-0002：事态本体（Situation + 时间升序派生）

- **状态**：已接受（Accepted）
- **日期**：2026-10-11
- **决策者**：创意总监 游有方（事态本体与排序语义）／用户裁定 **D1**（`Situation` 命名、时间派生、可选 `narrative_order`）／技术架构总监 柯桥良（`Situation`/`SituationStep`/`Track` 结构定稿）／主理人 范可控（拦下「链可手动排序」的冲突）
- **关联**：`docs/MAP_EDITOR_BASELINE_v1.md` §1.1–§1.9、§1.18、§1.19、§2.7、§2.9、§2.14、§5.1；`AGENTS.md` §1 P4/P6/P7、§3（数据与渲染分离）；**ADR-0001**、**ADR-0003**；硬约束 **A1 / A2**

---

## 背景与问题

用户提出了一个「我不知道如何定义」的东西：

> 「还有一个我不知道如何定义，如**四渡赤水**，我想播放他的**整个事态的进程**」

这是一个**真实且普遍**的创作需求：作者脑中存在「一段时间内、一件有始有终的大事」，它由**几个先后发生的关键事件**组成，主角在其中**移动**（行军、出使、游历）。现有模型只有扁平的 `Event`（事件维度），无法承载：

1. **组织层**：把多个事件串成「一件大事」；
2. **播放**：让作者「看着这件事怎么发生的」；
3. **运动轨迹**：事件之间「谁、怎么动」。

### 需要解决的六个子问题

| # | 子问题 | 不解决的后果 |
|---|---|---|
| Q1 | 「这件大事」是什么实体？ | 无处承载「链」 |
| Q2 | 它与既有 `Event` 是什么关系？ | 要么改 `Event`（破坏既有数据），要么平列（丢失节点语义） |
| Q3 | 链上节点按什么排序？ | 时间与序号两个真相打架 |
| Q4 | 「谁怎么动」记在哪里？ | 挂在角色身上 → 变成终身属性；挂在事件上 → 丢失地图/主体上下文 |
| Q5 | 轨迹的时间戳是否必填？ | 逼作者给每个点标日期 = 把创作变成打卡 |
| Q6 | 「播放」是什么？ | 若做成独立播放器实体 → 时间语义分裂（违反 P7） |

**若不决策会怎样**：若按「扩展 `Event`」方案实现，链元数据无处安放，且链不能跨地图、时间范围要遍历算；若按「可手动排序」方案实现，则**链顺序与时间轴成为两个真相**，作者不再信任工具的时间排序（🔴 高风险）。

---

## 决策

**新增「事态（Situation）」作为事件之上的组织层。** 三个不可分割的部分：

### （1）事态 = 事件链，链的回答是「发生了什么、为什么」

| 项 | 值 |
|---|---|
| 中文名 | **事态**（口语可叫「事态进程」，实体名是「事态」） |
| 英文名 | **Situation** |
| 代码 ID 前缀 | **`sit_`**（如 `sit_four_crossings_chishui`） |
| YAML 路径 | `timeline/situations/<id>.yaml`（与 `events/` 平行，**不进** `events/`） |
| 所属维度 | 事件（事件维度内的**组织层**） |

**为什么叫「事态」**：用户自己的用词就是「事态」——**这是最省概念的命名**（不造新词，把用户的词正式化）。

**作者语言定义（可做成 tooltip）**：

> **事态 = 「一段时间内，一件有始有终的大事，拆成几个先后发生的关键事件。」**
>
> 判定口诀：是不是有头有尾的大事 → 建**事态**；有没有先后的关键节点 → 事态的**链**；其中一个节点要不要画出怎么动的 → 挂**轨迹**。

**四渡赤水的对号入座**：

| 概念 | 实例 |
|---|---|
| 事态 | 「四渡赤水」（1935 年 1–3 月，红军在川黔滇边界的机动作战） |
| 第 1 个节点（事件） | 一渡赤水（土城失利 → 西渡赤水入川南） |
| 该节点的轨迹 | 土城 → 扎西 的行军点列（带逐段时间） |
| 后续节点 | 二渡赤水 / 三渡 / 四渡 + 若干伴生事件 |
| 归属地图 | 世界地图（行军），「占遵义」可下钻到城市地图（入城） |
| 参与方 | 红军（势力层）、若干人物 |

### （2）事态 vs 故事（Story）的边界（必须钉死）

| 判定问题 | 建**事态** | 建**故事（Story）** |
|---|---|---|
| 它有确定的时间范围吗？ | ✅ 有（`from..to` 都是真实天数） | ❌ 没有 |
| 它要参与四维校验吗？ | ✅ 要 | ❌ 不要 |
| 它能被播放吗？ | ✅ 能 | ❌ 不能（无轴位置） |
| 它能下钻到地图吗？ | ✅ 能 | ❌ 不能 |
| 典型例子 | 四渡赤水、赤壁之战、玄武门之变 | 创世神话、上古传说、家族史散文 |

> **口诀**：**「能排期 → 事件；能播、能下钻 → 事态；只用来讲故事 → 故事。」**

### （3）事态与既有 `Event` 的关系：Event **之上**的一层

| 方案 | 评价 | 裁定 |
|---|---|---|
| A. `Event` 的扩展（加 `chain_id` 字段） | 链属性无处安放；链不能跨地图；链时间范围要遍历算 | ❌ 否 |
| **B. `Event` 之上新的一层（`Situation` 聚合 `Event`）** | 链元数据有家；可跨地图；与 P4 一致；**`Event` 一个字都不用改** | ✅ **采纳** |
| C. 并列的新实体 | 链上节点是事件就失去了 | ❌ 否 |

**事态节点（`SituationStep`）只引用 `EventId`，不复制事件内容。**

### 五条关键不变式

| # | 不变式 | 违反时的表现 |
|---|---|---|
| **I1** | `Situation` **不复制 `Event` 内容**，只引用 `EventId`（P4） | 事件内容出现两份，改一处另一处不同步 |
| **I2** | `Situation` **不引入第二种时间顺序**：链排序 = 节点的时间顺序 | 作者要解释「为什么链上第一个事件是 3 月，第二个是 1 月」 |
| **I3** | **`Event` 可以不属于任何 `Situation`**（孤立事件合法，一等公民） | 逼作者「每写个事件都要先建链」——极大抬高入门门槛 |
| **I4** | **一个 `Event` 可以属于多条 `Situation`** | 逼作者复制事件（违反 P4），且史实上多归属是常态 |
| **I5** | `Situation` 必须有时间范围（`span`），且**必须覆盖其全部节点的时间** | 播放时出现「链已结束但还有节点」 |

> **I3 的创作理由（最重要）**：作者写稿顺序**不是**「先规划链再写事件」——他通常**先想起某个具体事件**，后来才串成链。**强制「事件必须属于链」= 把工具的痛苦转嫁给作者。**

### 数据结构（基线 §2.7 定稿）

```rust
/// 事态。U1 的「链实体」（原 `Campaign`，按 D1 改名）。
pub struct Situation {
    pub id: Id,
    pub name: String,
    pub summary: Option<String>,
    /// 事态包含的事件引用（**无序**，播放顺序由事件 `span.from` 升序派生）。
    pub steps: Vec<SituationStep>,
    /// 可选的**叙事顺序**覆盖（D1 补充）：供倒叙/插叙编排。
    /// 为空时用时间派生；有值时按此列表顺序播放。
    pub narrative_order: Option<Vec<Id>>,
    pub maps: Vec<Id>,
    pub protagonist: Option<Id>,
}

/// 事态的一步。**不含序号**（D1：顺序派生）。
pub struct SituationStep {
    pub event: Id,
    pub focus: bool,
    pub pause_secs: Option<f32>,
    pub caption: Option<String>,
    /// 本节挂载的轨迹（游有方语义：轨迹是「事态节点」的属性）。
    pub tracks: Vec<Id>,
}

/// 轨迹。独立实体（避免 P4 复制——同一条轨迹被两条事态引用时不重复存储）。
pub struct Track {
    pub id: Id,
    /// 轨迹所属主体（角色或势力）。
    pub owner: Id,
    /// 轨迹发生的地图（决定坐标系与 LOD）。
    pub map: Id,
    /// 轨迹的时间区间（半开 `[from, to)`）。
    pub span: TimeSpan,
    /// 途经点序列。
    pub waypoints: Vec<Waypoint>,
    /// 轨迹的几何表达（用于渲染连线）。可选。
    pub path: Option<GeometryData>,
}

/// 轨迹上的一个途经点。
pub struct Waypoint {
    /// 到达该点的时间（天数计数器）。**可选**（无 = 顺序点，不参与校验）。
    pub day: Option<i64>,
    /// 该点在 `map` 内的局部坐标。与 `place` 二选一（place 优先）。
    pub pos: Option<Point>,
    /// 该点对应的地点（可选）。若有，则与 `Place` 图对齐，可用于距离校验。
    pub place: Option<Id>,
}
```

### （4）链的排序依据：时间，且只能时间（D1 / I2 的落地）

| 候选依据 | 评价 | 裁定 |
|---|---|---|
| **时间**（节点事件的 `span.from`） | 唯一能从数据推出的、无歧义的顺序 | ✅ **唯一排序依据** |
| 序号（`order: 1,2,3`） | **会和时间打架**：两个真相 = 必然有一个是假的 | ❌ 由时间**派生**，不单独存储 |
| 因果依赖 | 需要完整的因果图 + 环检测，**本轮不做** | ❌ 见 K2 |

- **节点展示顺序 = 按节点事件时间升序**。作者**不需要也不允许**手排顺序。
- **UI 上节点列表只读**（可拖动改变的是「事件的时间」，不是「列表的位置」）。
- **两个节点时间相同**：按 `EventId` 字典序兜底（确定性排序）。
- **倒叙编排**：由可选的 `narrative_order` 承载，它**不影响时间轴的任何求值**。

**排序派生规则**：

| 情况 | 播放顺序 |
|---|---|
| `narrative_order == None` | 按 `step.event` 对应 `Event.span.from` **升序** |
| `narrative_order == Some(list)` | 按 `list` 顺序；未覆盖的 step 追加其后（按时间升序） |

> **实现位置**：`wv-core` 提供纯函数 `Situation::playback_order(&self, events: &[Event]) -> Vec<Id>`（可单测）。`wv-app` 只调用它。**不在渲染层排序。**

> **主理人拦截（基线 §7 #1）**：曾出现「只能时间派生」（游有方）与「可手动排序」（柯桥良）的冲突。若采纳后者，则正中游有方标的 🔴 高风险（两个真相）。**裁定：倒叙是呈现技法，不是事件顺序**——所以用独立的 `narrative_order` 承载倒叙，而**链本身仍只由时间派生**。

### （5）轨迹（Track）：谁怎么动

**裁定：轨迹挂在「事态节点」上**（不是 `Event` 的属性，也不是 `Character` 的终身属性）。

**为什么**：轨迹是「**在这个节点上，谁怎么动的**」——它需要同时知道：
① 属于哪个事态节点（语境）；② 谁在动（主体）；③ 在哪张图（坐标系）。
**只有事态节点同时持有这三个上下文。**

时间戳三条规则（对应硬约束 **A2**）：

| # | 规则 | 理由 |
|---|---|---|
| **T1** | 有 `day` 的点 → 该主体在该天确定在此位置（参与四维校验） | 四维互相校验在事态上的落点 |
| **T2** | 无 `day` 的点 → 视为「顺序点」，由插值决定，**不参与校验** | **「未声明 ≠ 矛盾」**（沿用第四态哲学） |
| **T3** | **只填两端点的轨迹，其时间由两端点事件的时间范围给出** | 让「粗略轨迹」零成本可用 |

**四级地图的轨迹形态**：

| 层级 | 轨迹是否存在 | 典型形态 | 推荐写法 |
|---|---|---|---|
| **World** | ✅ 主要战场 | 大跨度折线（跨州跨国） | 坐标点列（荒野无 `Place` 可引用） |
| **Region** | ✅ 存在 | 中等跨度 | 坐标点列 |
| **City** | ✅ **用户明确要求** | 街道级路径 | **地点序列（`PlaceId` 列表）** |
| **Interior** | ✅ 存在，形态不同 | 房间级路径点 | **地点序列**，且默认只画起终点 |

**两种写法的取舍**：

| 写法 | 形态 | 适用 | 优点 |
|---|---|---|---|
| **坐标点列** | 直接给 x,y 点 | World / Region | 表达任意路径 |
| **地点序列** | `PlaceId` 有序列表 | City / Interior | ✅ **强烈推荐**：可校验「路走不通」、可自动算耗时、**作者不用画坐标** |

> **这是 P4 与距离维度的自然复用**：城市/室内图上的「南门、主街、衙门」天然是 `Place`。**用 `Place` 序列表达轨迹 = 免费得到距离校验。**（这正是 ADR-0003 的 `Place` 层级引用在轨迹上的应用。）

### （6）「播放（Playback）」的定义

**裁定：`播放 = 时间轴以固定速率自动推进`。工具里没有独立的「播放器」实体。**

| 项 | 内容 |
|---|---|
| 播放 = 什么 | **自动拖时间轴** |
| 播放速率 | `1 天/秒` / `5 天/秒` / `30 天/秒`（**跨度自适应**：链多长都让它 ~20 秒播完） |
| 控件 | 播放 / 暂停 / 上一节 / 下一节 |
| 播放对象 | **不是整条时间轴，而是某个事态**——播放时锁定在该链的 `span` 内循环 |
| 播放中可否编辑 | ❌ **只读**（避免「边播边改」的 Undo 混乱） |

> **为什么必须锁定在事态内**：作者的意图是「我要看四渡赤水是怎么走的」。**若播放整条 500 年时间轴，作者要等 500 秒。**

**渲染机制（基线 §2.14，必须走 `TimelineQuery::at`）**：

```
用户拖时间轴 / 点播放 → 更新 PlaybackState.current_day: i64
    ↓（拉动式刷新）
每帧：for situation in situations {
        let active_events = TimelineQuery::at(situation_event_spans, current_day);
      }
      对 tracks：插值出每个 track 在 current_day 的位置
    ↓
把结果写入 Bevy 资源（EventHighlights / TrackPositions）
    ↓
渲染 System 只读资源，不做任何时间判断
```

> **关键区分**：`current_day` 是**视图状态**（Bevy Resource），**不是世界数据**。世界数据里的时间一律是 `TimeSpan`。**禁止在渲染层做时间比较**（`AGENTS.md` §3.2）。

**事态 vs `Story` vs `Event` 的最终定位**：

| 实体 | 时间范围 | 参与校验 | 可播放 | 可下钻 |
|---|---|---|---|---|
| `Event` | 有（`span`） | ✅ | 单独事件否 | 否 |
| `Situation` | 有（覆盖全部节点） | ✅（汇总） | ✅ | ✅ |
| `Story` | 无 | ❌ | ❌ | ❌ |

## 硬约束

本 ADR 承载 **A1** 与 **A2**。以下**逐字引用**基线 §6.3（第 1538–1539 行）原文。

### A1

| # | 硬约束 | 违反后果 |
|---|---|---|
| **A1** | **链的顺序只能由时间派生，不能存序号** | 两个真相 → 作者不再信任工具的时间排序 |

**它如何约束本决策**：

- `SituationStep` 结构里**没有** `order` / `index` / `seq` 字段——这是**结构性保证**，不是纪律。
- 排序的唯一来源是 `Situation::playback_order()`，它读 `Event.span.from` 升序；相同时间用 `EventId` 字典序兜底。
- `Situation.steps: Vec<SituationStep>` 在 YAML 里的**书写顺序无关紧要**（它被声明为「无序」）——避免作者误以为顺序有意义。
- **`narrative_order` 不违反 A1**：它承载的是「**倒叙/插叙这个呈现技法**」，**不影响时间轴的任何求值**，也不改变链的时间顺序。链的时间顺序永远是时间派生的；`narrative_order` 只覆盖**播放列举顺序**。

### A2

| # | 硬约束 | 违反后果 |
|---|---|---|
| **A2** | **轨迹必须可选、可粗略（只两端点）** | 把小说作者逼成测绘员 |

**它如何约束本决策**：

- `SituationStep.tracks: Vec<Id>`，**默认为空**（`#[serde(default)]`）。事态的节点**可以完全没有轨迹**——「加轨迹」是**次要按钮**，不是必填项（基线 §1.19 风险兜底）。
- `Waypoint.day: Option<i64>` **可选**（T2）：无时间戳的点是「顺序点」，不参与校验。
- **T3 保证「粗轨迹」零成本**：只填两端点即可，其时间由两端点事件的 `span` 给出。粗轨迹与精轨迹**同视觉待遇**（仅加空心起点 + 极淡 `≈` 标识）。
- **反面**：若把 `tracks` 设为必填、或把 `day` 设为必填，就会**把小说作者逼成测绘员**——作者写小说时「他沿着赤水河走了六天」比「他第 3 天在古蔺」重要得多。**逼作者标每一点的日子 = 把创作变成打卡。**

## 理由

**（1）P4（多地图层级）的正面要求。**

I1（不复制 `Event` 内容）、I4（一事件可属多事态）都是 P4 的直接产物：`SituationStep` 引用 `EventId`，`Track` 是独立实体（被多条事态引用时不重复存储）。`AGENTS.md` §4.3「只存引用，不重复存储」在本决策中被应用了两次。

**（2）P6 + P7 的产物。**

事态的时间范围、事件的 `span`、轨迹的 `span` 一律区间化，不存「当前处于哪一步」。

**（3）`AGENTS.md` §3「数据与渲染分离」的产物。**

「播放」被定义为**时间轴自动推进**（`PlaybackState.current_day` 是 Bevy Resource），而**不是**新的数据实体或播放器组件。这直接对应 §3.4「视图刷新是拉动式的」，避免「数据变了自动通知渲染」的反向耦合。

**（4）「数据承载开放集」原则的第三次应用。**

`Situation` 本身是**数据实体**（不是 `Event` 的枚举字段），与 ADR-0001 的「势力层」同源：**用有限结构表达无限世界是模型设计错误**。

**（5）最关键的创作理由（I3）。**

作者**先想起某个具体事件**，后来才串成链。**强制「事件必须属于链」= 把工具的痛苦转嫁给作者。** 孤立事件是一等公民，这是降低入门门槛的决定性设计。

## 后果

### 正面

- **事态可作为独立实体存在**：`Event` 零改动（`Event` 的所有既有 YAML/代码不受影响）。
- **链顺序无歧义**：结构性排除「序号 vs 时间」两个真相（A1）。
- **粗轨迹零成本**（A2）：小说作者不必成为测绘员。
- **轨迹自动获得距离校验**：City/Interior 用 `Place` 序列时，免费得到「路走不通」校验与耗时计算。
- **播放锁定在事态 span 内**：作者不用等 500 年（对 500 年时间轴）。
- **跨地图事态可播放**：`Situation.maps` 内有城市图时，播放器自动切换当前渲染地图。
- **孤立事件合法**：入门门槛低。

### 负面 / 代价

- **一个新实体 + 一个新 YAML 目录**（`timeline/situations/`、`tracks/`），概念数增加。
- **`narrative_order` 引入了「链顺序」与「播放列举顺序」的区分**：作者需要理解「链永远是时间序，倒叙只是讲述顺序」。**兜底**：事态面板（P-7）节点列表只读，并标注「顺序由事件时间决定」。
- **轨迹挂在事态节点上 → 一条运动跨越两个节点时需拆成两条轨迹**（或归入其中一个节点）。**兜底**：`Track.maps` + 节点 `map` 字段可表达跨图；**跨节点轨迹的表达方式记为待裁**。
- **`I5`（span 必须覆盖全部节点）需要校验**：若校验缺失，会出现「链已结束但还有节点」。**兜底**：记入校验面板（P-8）。
- **分支/因果的缺位**：本轮只做线性主链（K1/K2 现在就砍），并行支线只能以「并列多个节点」呈现，**不画分支树**。

### 待裁

| 项 | 状态 | 说明 |
|---|---|---|
| **一条运动跨越多个事态节点时，轨迹归谁** | **待裁**（**本 ADR 新增发现**） | 基线 §1.6 说「轨迹挂在事态节点上」，但未规定「土城→扎西→遵义」这种跨两节点的连续行军如何归属。建议方案：**按事件拆分多条 `Track`**，各挂对应节点；但这会让作者重复输入。**需用户裁定** |
| **`Situation.span` 是否显式字段** | **待裁**（**本 ADR 新增发现**） | 不变式 I5 要求「事态必须有时间范围且覆盖全部节点」，但基线 §2.7 的 `Situation` 结构中**没有 `span` 字段**——推断是由节点事件的 span 计算得出。**是否显式存储 span（冗余但可直接读）需裁定**。若派生，则需在加载时计算 |
| **`focus` / `pause_secs` / `caption` 的语义边界** | **待裁**（**本 ADR 新增发现**） | 基线 §2.7 定义了这三个字段，但 `focus`（是否聚焦）到底聚焦什么（相机？高亮？）、`pause_secs` 在「播放速率自适应」下如何生效（§1.8 说速率自适应让链条 ~20 秒播完，与固定 pause 冲突）**未说明** |
| **分支父子关系的存储形态** | **待裁**（K1，现在就砍） | §1.5 说「数据形态可有分支（轻量父子关系）」，但 §2.7 的 `SituationStep` 结构中**并无父子字段**。当前结构与「本轮只做线性」一致；分支是**预留但未落地** |
| **`narrative_order` 与校验的关系** | **待裁**（**本 ADR 新增发现**） | 若 `narrative_order` 覆盖了播放顺序，四维校验是否仍按时间序？推断「校验永远按时间序，narrative_order 只影响播放」，但基线未明写 |
| **`Campaign` 旧名迁移路径** | **待裁** | §5.2 已把 `Campaign`/`CampaignStep` 作废，但**旧工程若已有 `campaigns/` 目录是否自动迁移**未定（参照 §2.16 `schema_version` 1→2 的「不做自动迁移」策略，倾向不迁移） |

## 备选方案（被否决的）

| 方案 | 否决理由 |
|---|---|
| **A. `Event` 扩展（加 `chain_id`）** | ❌ 链属性无处安放；链不能跨地图；链时间范围要遍历算（基线 §1.3） |
| **B. 并列的新实体（与 `Event` 平级，不再复用事件）** | ❌ 链上节点是事件就失去了；且会制造事件数据的第二份（违反 P4） |
| **C. 链存 `order` 序号** | ❌ **违反硬约束 A1**。序号与时间会打架 → 两个真相（基线 §1.4） |
| **D. 链按手动排序（柯桥良早期提案）** | ❌ 主理人拦截（基线 §7 #1）。倒叙是呈现技法，不是事件顺序；采纳它会正中「两个真相」的 🔴 高风险 |
| **E. 轨迹挂在 `Character` 上（终身属性）** | ❌ 轨迹需要地图上下文与事态语境，角色不持有；且会导致「同一段运动在多事态间复制」（违反 P4） |
| **F. 轨迹作为 `Event` 的属性** | ❌ 轨迹是「事态链视角下谁怎么动」，不是事件的固有属性；挂事件会丢失「链语境」 |
| **G. 需要独立「播放器」实体** | ❌ 播放 = 时间轴自动推进，独立播放器会分裂时间语义（违反 P7） |
| **H. `Waypoint.day` 必填** | ❌ **违反硬约束 A2**。把小说作者逼成测绘员 |
| **I. 因果依赖 / 条件表达式进本轮** | ❌ K2，**现在就砍**。条件表达式引擎本身仍是待裁问题（README §12-3） |
| **J. `Situation` 必须有 span 字段（显式存储）** | ⚠️ 见「待裁」。基线未定义 span 字段，推断为派生；显式存储是冗余（违反派生数据不落盘的精神） |
