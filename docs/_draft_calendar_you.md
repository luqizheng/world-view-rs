## 0. 一句话结论（结论先行）

> **本轮变更把"时间"从"一个写死的 360 天历"升级为"一个可插拔的显示层"，并把"故事"从事件里剥离出来。**

## A. 「故事」实体的创作语义（本轮核心）

### A1. 边界裁定：**「故事」= 轴外的叙事卡；「事件」= 轴上的一格**

用**作者的语言**（不说引擎词）给出一条可当场判定的规则：

| 作者在问自己… | 建 **事件** | 建 **故事** |
|---|---|---|
| 我能说清它"**发生在哪一天**"吗？ | ✅ 能 → 事件 | ❌ 不能 / 不重要 → 故事 |
| 它需要和其他东西**对时间**吗？（人物在不在、路通不通、谁先谁后） | ✅ 需要 → 事件 | ❌ 不需要 → 故事 |
| 它是**可被排期**的吗？（"这天他在哪"） | ✅ 是 → 事件 | ❌ 不是 → 故事 |
| 典型例子 | 建城、战役、加冕、抵达、出生 | 创世神话、上古传说、世界观设定、家族史散文、地理志节选 |

**一句话口诀（可直接做成 UI 的 tooltip）**：

> **"能排期 → 事件；只用来讲故事 → 故事。"**

> **为什么这条规则是硬的而不是软的**：它不是"内容分类"审美，而是**工具能力边界**。事件进四维校验（§1.3 四态、§1.4 移动可达性），故事不进——**混用会让作者对校验结论失去信任**（"我明明写了一个故事，为什么工具说角色不可达？"）。

### A2. 故事**有没有 `day`**？——**裁定：无 `day`（与主理人技术倾向一致，但从创作语义给独立理由）**

**结论：故事没有 `day`。**

| 方案 | 创作语义评价 | 裁定 |
|---|---|---|
| **有 `day`**（轴上一点，只是不校验下界） | 这是**伪精度**。用户原话"没必要检查"，其意图**不是**"允许跑出界"，而是"**这东西本来就没有精确日期**"。给一个"填了但可以不合法"的字段，等于给作者一个**可以填错的洞**——工具不知道它是真是假，作者自己也不知道。 | ❌ 否 |
| **无 `day`**（游离于时间轴之外的纯文本卡） | 诚实地表达"这段叙事没有精确时间"。与既有 §1.9「前史区」的**同一哲学**：能算的进主轴，不能算的进旁边。 | ✅ **采纳** |

**四条独立理由（不止"技术倾向"）**：

| # | 理由 | 说明 |
|---|---|---|
| 1 | **无 day 就没有"非法日期"这个错误类** | 用户要的"没必要检查"由**结构**满足，而不是由"校验开关"满足——开关会被忘记，结构不会 |
| 2 | **有 day 会污染排序与四维查询** | 一个"轴外 day"的故事，会让 `TimelineQuery::at(t)` / `in_range` 的**边界语义变复杂**（等于在轴上开一个洞）。无 day = 零交互 |
| 3 | **有 day 会让作者对"轴"失去心智模型** | 轴的契约是"**第 1 天起、每天 +1、往前不存在**"（§1.9）。轴上出现一个排在"第 0 天"的东西 → 契约立刻破 | 
| 4 | **与「前史区」是同一件事的两种粒度** | 前史区 = 起点**之前**的无日期叙事；故事 = **任意位置**的无日期叙事。二者应**共用一套机制**（见 A3），不要造两个概念 |

> **给技术侧的边界明确**（不写代码，只定语义）：故事**不是** `TimePoint`、**不是** `TimeSpan`、**不进** `TimelineQuery`、**不参与**排序。它是 `id + 标题 + 正文 + （可选）它想靠近的锚点`。

### A3. 故事的存放与呈现

**存放位置裁定：放独立的 `stories/` 目录，不放 `timeline/`。**

```
world/
├── timeline/
│   ├── axis.yaml            # 历法 + timeline_range + anchors
│   ├── bookmarks.yaml
│   └── events/              # ← 只有"能排期"的东西
│       └── evt_*.yaml
├── stories/                 # ← 新增：轴外叙事
│   ├── story_creation.yaml      # 创世神话
│   └── story_ancient_war.yaml   # 上古战争传说
├── characters/
├── distances/
└── maps/
```

**为什么独立目录**（三条）：

| 理由 | 说明 |
|---|---|
| **目录即心智模型** | `timeline/` 下的东西作者会默认"它有日期"。故事放进去 = 用**目录结构撒谎**。独立 `stories/` 让作者一眼知道"这里的东西不排期" |
| **避免与 `events/` 的加载器混用** | 事件加载器做**硬下界校验**（A4）；故事加载器不做。同一目录会让加载逻辑分叉、且错误信息混乱 |
| **`前史区` 是它的视图，不是它的家** | 前史区（§1.9）应该**读 `stories/` 里带 `before_axis: true` 标记的那些**。这样"前史"不必有独立存储，避免第 3 个概念 |

**Story 实体语义（给技术侧的意图，非 schema）**：

| 字段语义 | 说明 |
|---|---|
| `id` | 可读 ID（沿用工程约定 `[A-Za-z0-9_]`） |
| `title` | 作者可见标题 |
| `text` | 正文（Markdown 富文本） |
| `placements`（**可选、可多值**） | 它**想靠近哪个轴上的点/锚点**。这是**纯导航提示**，不是时间语义 |
| `before_axis`（可选） | 若为 true → 归入"前史区"（§1.9） |

> **关键区分**：`placements` 是"**我推荐你在这里读它**"，不是"它发生在这里"。它的类型应是 `Vec<AnchorId>`（**只能引用已有锚点**，不能填裸数字）—— 这样**结构上无法表达"一个精确但非法的日期"**（A2 理由 1 的落地）。

**UI 呈现（ASCII，侧栏便签方案）**：

```
┌───────────────┬──────────────────────────────────────────────────┐
│  侧栏 Stories │  时间轴（正常）                                    │
│  ───────────  │  ─────────────────────────────────────────────   │
│  📜 创世神话   │   [前史区] ┊ 无仙20年 ──●建城──●──● 无仙30年        │
│  📜 上古战争   │           ┊            ↑ 锚点                     │
│  📜 家族史     │           ┊       ┌──────┐                        │
│               │           ┊       │📜便签│← placements 指向"建城" │
└───────────────┴──────────────────────────────────────────────────┘
```

- **主视图是侧栏列表**（不是时间轴上的元素）—— 表达"它不在轴上"。
- **带 `placements` 的故事**在时间轴对应锚点旁显示一枚**便签图标（📜，虚线边框）**，悬停/点击跳出**侧注浮层**。视觉上**必须**与事件卡（实线、有色块）**明显区分**——否则作者会误拖。
- **不带 `placements` 的故事只在侧栏**（不进轴），与前史区之外的叙事也一致。
- **禁止拖拽**：便签不能被拖到轴上的新位置（因为轴位置对它无意义）。要改 `placements` 请走侧栏的属性面板。

### A4. 关于"有 day"路径的备选说明（**不采纳，但记录风险**）

若团队最终选择"有 day"（**我不推荐**），则"没必要检查"必须被精确定义为下列二者之一，且二者都有明确代价：

| 解释 | 含义 | 引入的风险 |
|---|---|---|
| 解释①：**可以填轴外的日期** | 故事能排到第 1 天之前（如 `day: -30`） | 直接摧毁 §1.9「往前不存在」契约。且 `TimePoint` 是 `counter >= 1` 硬约束（§2.2.2 R3）——为它开后门 = 整个时间模型出现一个**豁免区**，后续每个查询都要处理"可能为负" |
| 解释②：**可以不填日期** | `day` 是 `Option` | 那它 90% 情况下就是 `None`，而这个 `Option` 的存在只让"有时有、有时无"——**等价于无 day，只是多一个可空字段**。既然如此，不如诚实用无 day |

> **创作体验判断**：两种解释下，"有 day"都**不比"无 day"更好**，且解释①有真实伤害。坚持无 day。

## B. 三种「显示扩展方式」的作者体感

### B0. 先钉一个前提：**历法是「显示层」，不是「运算层」的重定义**

用户原话"**只是显示问题**"必须被当作**硬约束**：

| 层 | 唯一内容 | 是否可插拔 |
|---|---|---|
| **运算层** | 内部 = **天数计数器**（整数，第 1 天起，每天 +1）；排序 = 计数器数值序 | ❌ **不可插拔**（永远一种） |
| **显示层** | 计数器 ⇄ 年月日的**换算与格式化** | ✅ **可插拔**（三种内置 + 现实自定义） |

> **大白话**：不管作者选哪种历法，**引擎里那个 `day` 永远是同一个数**。换历法 = 换一副眼镜，不是换一个世界。**这是本轮最关键的一条纪律**——一旦历法渗进运算层，用户上一轮刚砍掉的复杂度（多纪元/可配天数）就全部长回来。

### B1. 三种内置显示方式 + 自定义（作者体感表）

| # | 名称（作者看到） | 规则 | 作者心里的例子 | 换算类 |
|---|---|---|---|---|
| 1 | **公历（真实，含闰年）** | 1 年 = 365/366 天，12 月，月长 28/29/30/31，真实公元纪年 | `1980-1-1` | 格里高利 |
| 2 | **简化历（365 天）** | 1 年 = 365 天，**无闰年**，12 月，月长固定 | `第 3000 天 = 8 年 3 月 15 日` | 固定 365/12 分月 |
| 3 | **架空历（360 天 / 30 天月）** | 1 年 = 360 天，12 月 × 30 天，**无闰年** | 现 §1.10 S4 的表（20 年 1 月 1 日…） | 固定 360/30 |
| 4 | **（现实小说：选第 1 种 + 加年号对照）** | 不是独立历法——是"**公历 + 年号显示文本**"的组合 | 中国历史小说 | 公历换算 + 年号文本 |

> **修订说明**：原第 4 项"自定义历法 `custom`"在 B5.1 已**取消**。现实小说作者用 **` Gregorian` + `reign_aliases`**，不需要第四种历法。**仍是三值封闭枚举。**

**默认 = 哪一种？**
> **默认第 3 种（架空 360 天）**，理由：本工具的**既有规格**（§0.2 S3、§2.2.4 `Calendar`）就是 360 天，且《World View》的定位是**架空世界创作工具**。若默认公历，"架空作者每次新建工程都要改一次"——摩擦放错了地方。
> 现实小说作者选**第 1 种（公历）** + 加年号对照（见 B3 / B5.2）。

### B2. 作者**怎么选**、**怎么知道**自己选的是哪种

**选法（YAML）**：不是让作者选"历法名"，而是让作者**填一个 `rule` 字段**（经 B5.2 与技术侧统一，不用 `display_calendar` 命名——那会为已有的 `prefix`/`start_year` 重开一套）。

```yaml
# timeline/axis.yaml
prefix: 公元            # 显示前缀（= 已存在的字段，不另起名）
start_year: 1840        # 第 1 天 = 公元 1840-01-01
rule: gregorian         # gregorian | simple_365 | fixed_360（缺省 fixed_360）
# 年号对照（可选；仅现实小说需要，见 B3）：
reign_aliases:
  - era_name: 嘉庆
    dynasty: 清
    gregorian_start: 1796
    gregorian_end: 1820
    start: 125
    end: 490
    lunar_label: 嘉庆二十三年四月初一
```

**「怎么知道自己选的是哪种」——三级保险（按强制度）**：

| 级 | 手段 | 呈现 |
|---|---|---|
| ① **必须** | **时间轴首尾刻度直接显示完整日期**，含历法特征 | 选公历时看到 `公元 1840-01-01`；选架空时看到 `无仙 20 年 1 月 1 日`。**月份名/年份写法本身就在告诉作者** |
| ② **必须** | **Inspector 顶部常驻一枚"历法徽标"**（不是藏进设置） | `[日历图标] 公历（含闰年）· 公元纪年`，点击可换 |
| ③ 建议 | **新建工程向导**一屏选择（第 3 种默认高亮） | 三张卡片 + 一句"随时可改，改的是显示不改数据" |

> **关键体感设计**：切换历法后，**弹一个非模态提示条**：
> `显示历法已切换为「公历（含闰年）」。轴上所有事件位置未变，只是显示的日期文字变了。`
> —— 这句话**必须在作者第一次切换时出现一次**，因为作者最怕的就是"我换个历法会不会把数据改了"。

### B3. 年号对照（`1818-5-5 ↔ 嘉庆二十三年四月初一`）——**本轮第二大裁定**

**裁定三条（结论先行）**：

| 议题 | 裁定 | 一句话理由 |
|---|---|---|
| **① 手填 vs 内置朝代年号表** | **内置「年号表」作为"输入辅助"，但作者必须逐条确认**（不是全自动） | 只要给**辅助**，不要给**代填**——见下 |
| **② 工具是否校验自洽** | **校验，但分级**：**年份级**校验 → 报错（红）；**月日级**校验 → 仅警告（黄） | 年号干支纪年是**历史常识**，年份错=作者真的错了；月日级换算工具不做（用户已明确"只做公历换算"） |
| **③ 哪种更能避免"以为自己填对了但实际错了"** | **内置年号表 + 给出"该年号起止年" + 年份级硬校验** | 这是唯一能兜住"作者记错年号年份"的组合 |

**为什么"内置年号表"是必要的，而不是加负担**：

> 一个作者想写"嘉庆二十三年"这件事，**他自己都得查**（他要查"嘉庆是从哪年算的"）。工具**替他查**，是**降低**负担，不是增加。
> 但工具**绝不能**替他**换算月日**——因为那要接农历算法（用户明确否决）。

**年号表的数据形态（= B5.2 的 `reign_aliases` 字段；作者可从下拉里挑，不需自己敲）**：

```yaml
# 内置表提供的静态史实（作者下拉候选，公历区间仍由作者确认）：
- era_name: 嘉庆
  dynasty: 清
  gregorian_start: 1796      # 嘉庆元年 = 公元 1796（静态史实，支撑年份级校验）
  gregorian_end: 1820        # 静态史实
```
> **与 B5.2 合并说明**：上列即 `reign_aliases[]` 的字段子集。`start`/`end`（天数计数器）由工具**用公历区间换算**（纯公历运算），`lunar_label` 由作者手填。**完整七字段见 B5.2。**

**作者的输入流（UI，一手操作）**：

```
┌─ 添加「年号显示」────────────────────────────────┐
│  年号 [嘉庆 ▾]（下拉，含"自定义…"）  dynasty: 清  │
│  年号年 [23]   → 公元范围 1818 （自动填/校验）    │
│  ── 以下作者手填（工具不推算农历）──              │
│  月 [四月 ▾ 或手填]   日 [初一 ▾ 或手填]          │
│  公历对照 [1818-05-05]  ← 作者填，工具只查范围     │
│  ⚠ 提示：工具不推算农历，农历月日由你填写          │
│  ✅ 年份自洽：嘉庆二十三年 ⊆ 嘉庆(1796–1820)       │
└──────────────────────────────────────────────────┘
```

**校验分级（②）的判定表**：

| 作者填的内容 | 工具行为 | 文案 |
|---|---|---|
| 年号年**落在**该年号起止年内 | ✅ 绿，通过 | 无（或淡字"年份自洽"） |
| 年号年**超出**该年号起止年（如"嘉庆二十三年"但公历填 1820 之后） | 🔴 **报错**（阻止保存） | "嘉庆只到二十五年（公元 1820）。你写的『嘉庆二十三年』对应的是 1818 年，不是 1820 年。" |
| 年号**不在**内置表（作者编的） | 🟡 **提示**（不阻止） | "『XX 年号』不在内置表里。已按自定义处理，年份不做校验。" |
| 农历**月日**与公历对照是否吻合 | 🟡 **只警告** | "工具不推算农历月日。请自行确认『四月初一』是否对应 1818-05-05。" |

> **为什么不把月日级也做成报错**：用户明确"**只做公历换算**"，工具**没有**农历能力。它若对月日级报错，就是在**假装自己会**——这是最坏的情况（作者会信它）。**警告 + 明确声明"我不算农历"** 是诚实的设计。

**③ 的最终回答**：**内置表 + 年份硬校验**最能防错。理由：
- **纯手填**：作者会写错年份（"嘉庆二十三年" 有人以为是 1823），且**他自己意识不到**。→ 错的静默通过。
- **纯自动**：工具必须会农历，用户已否决；且一旦工具算错，作者**全盘信任** → 大面积错误。
- **内置表 + 年份硬校验**：工具**只做它真能做的**（年号起止年是公开史实），**不碰它不能做的**（农历月日）。**边界清晰 = 不会骗人**。

### B4. `14634年` 这类超远期架空的 UI 呈现

**签发：年份显示不设宽度上限，但时间轴刻度**必须**按尺度切换单位（不是挤字，是换刻度）。**

| 尺度 | 刻度主标 | 例子 |
|---|---|---|
| 1~999 年 | 年份数字 | `146 年` `520 年` |
| 1000~9999 年 | 年份（4 位） | `1840 年` `9999 年` |
| **≥ 10000 年** | 年份（5 位）+ **刻度变稀**（每 5 年、10 年、50 年一格，按缩放自适应） | `14634 年` |

**排版溢出防护（三条硬规则）**：

1. **刻度标签永不重叠**：按当前缩放计算"标签可容纳宽度"，**自动降密度**（10 年一格 → 50 年一格 → 世纪一格）。**宁可少标，不可叠字**。
2. **年份数字等宽字体**：5 位数不会因为比例字体造成视觉跳动。
3. **超长年份在窄栏（侧栏/Inspector）里可换行，时间轴刻度里强制单行 + 省略号**（`1463…`，悬停看全）。

> **创作意图**：`14634 年` 是奇幻长篇的正常写法，**不该被工具"看不惯"**。工具要做的是**让刻度自己变稀**，而不是拦作者。

### B5. 与技术侧的两点对齐裁定（回应柯桥良 2026-10-11 询问）

> 技术侧 `_draft_calendar_ke.md` 提了两个必须统一的分歧。以下为**设计侧终裁**，技术侧无条件采纳任一命名，故以**我侧裁定 + 技术侧建议**合并成一份。

#### B5.1 历法枚举命名统一 —— **采纳技术侧的下划线命名，并取消 `custom` 变体**

**裁定：枚举 = 封闭三值，命名统一为下划线式。**

| 分歧点 | 我原稿 | 技术侧 | **终裁** |
|---|---|---|---|
| enum 名 | `CalendarKind` | `CalendarRule` | **`CalendarRule`**（技术侧名，更贴"规则"语义） |
| 值 1 | `gregorian` | `Gregorian` | **`Gregorian`**（无分歧） |
| 值 2 | `simple365` | `Simple365` | **`Simple365`**，serde tag = **`simple_365`** |
| 值 3 | `fantasy360` | `Fixed360` | **`Fixed360`**，serde tag = **`fixed_360`** |
| 值 4 | `custom` | （无） | **❌ 取消** |

**三条裁定理由**：

| # | 裁定 | 理由 |
|---|---|---|
| 1 | **采纳下划线 serde tag**（`simple_365` / `fixed_360`） | 技术侧实测的坑是真的：`rename_all="snake_case"` 对 `Fixed360` 产出 `fixed360`（数字不产生词边界）。**若文档写 `fixed_360` 而实际产出 `fixed360`，作者按文档写会解析失败**——这是"文档骗作者"的典型事故。**统一为下划线式，文档与实现同源。** |
| 2 | **`fantasy360` → `Fixed360`** | `Fixed360` 更准确：它描述的是**机制**（固定 360 天/30 天月），不是**genre**（奇幻）。工具不该按类型学命名机制——现实小说作者也可能用一个"一年 360 天的虚构星球"。 |
| 3 | **取消 `custom` 变体** | **技术侧提醒完全正确**：若 `custom` 只是"公历 + 年号对照"，那它就是 **`Gregorian` + `reign_aliases`**，**不需要独立变体**。为同一语义造两个概念，正是我上一轮反复砍的东西（K1）。**故 `custom` 不成立。** |

**`custom` 取消后的补充裁定（我的创作判断）**：

> 我原稿把 `custom` 描述为"作者自定义月表/月名"——**这是我把两件事混在一起了**。重新拆开：
> - **"现实小说用公历 + 年号"** → = `Gregorian` + `reign_aliases`（B3）。**不需要 `custom`。**
> - **"作者真自定义月表（13 个月、月长不等）"** → 这是**真 `custom`**，但它**触发技术侧 §1.2 的翻案路径**（enum → trait），且**当前无此需求**。
> **终裁：本轮不做 `custom`。** 若未来真出现"作者自定义月表"，按技术侧 §1.2 翻案抽 trait——那时是**加能力的破坏性变更**，而不是现在为它预留一个空变体。

**合并后的 enum（文档与实现同源）**：

```rust
#[serde(rename_all = "snake_case")]
pub enum CalendarRule {
    Gregorian,
    #[serde(rename = "simple_365")]
    Simple365,
    #[default]
    #[serde(rename = "fixed_360")]
    Fixed360,
}
```

#### B5.2 年号 schema —— **采纳技术侧的"完整 schema + 最小 UI"策略，但 schema 字段须含技术侧列的完整形态**

**裁定：两张稿不冲突，合并为一。存盘按完整形态定，UI 先做最小值。**

| 事项 | 我原稿 | 技术侧 | **终裁** |
|---|---|---|---|
| YAML 键名 | `display_calendar: {kind, epoch_label, epoch_year, era_table}` | 复用 `Calendar`：`rule` + `reign_aliases` | **采纳技术侧**：`rule` + `reign_aliases` 挂在 `Calendar` 下（`flatten` 到 axis.yaml 顶层） |
| 年号表 | 内置朝代年号表 | `reign_aliases: [{start, end, label}]`（最小） | **两者合并**（见下） |
| 校验分级 | 年份级红 / 月日级黄 | 可实现 | **保留我的分级**（B3 判定表不变） |

**为什么采纳技术侧的键名**：我原稿的 `display_calendar.kind` 与 `epoch_label/epoch_year` 其实是把已存在的 `prefix` / `start_year` **换了个名字重开一套**——这正是我 B0 里警告的"为同一语义造两个概念"。技术侧的 `Calendar{prefix, start_year, rule, reign_aliases}` **是同一套坐标系加两个字段**，**更省概念**。**我主动撤回 `display_calendar` 命名。**

**年号 schema 的最终形态（合并两侧）**：

```yaml
# axis.yaml 顶层（经 Calendar flatten 后）
rule: gregorian              # gregorian | simple_365 | fixed_360
reign_aliases:
  - era_name: 嘉庆            # ① 内置表候选；作者可下拉选，也可自定义
    dynasty: 清               # ② 仅显示分组
    gregorian_start: 1796     # ③ 内置表提供 → 支撑"年份级硬校验"
    gregorian_end: 1820       # ④ 内置表提供 → 支撑"年份级硬校验"
    start: 125                # ⑤ 技术侧最小形态：本段对应的天数计数器区间（含）
    end: 490                  # ⑥ 区间（不含）；省略 = 至今
    lunar_label: 嘉庆二十三年四月初一   # ⑦ 作者手填，工具不解析
```

**这七个字段的分工（诚实边界）**：

| 字段 | 谁提供 | 用途 | 工具是否推算 |
|---|---|---|---|
| `era_name` / `dynasty` / `gregorian_start` / `gregorian_end` | **内置表**（作者下拉） | ① 快速输入 ② **年份级硬校验的依据** | 否（静态史实数据） |
| `start` / `end`（计数器区间） | **工具算**（由公历起止年 → 计数器，纯公历运算） | 显示时定位"哪段显示这个年号" | 是（但**只是公历换算**，非农历） |
| `lunar_label` | **作者手填** | 显示文本 | ❌ **绝不** |

**关键澄清（对齐技术侧"不违反 Q1"）**：
> 技术侧说"内置表 + 年份级校验不需要农历算法"——**正确**。`gregorian_start/end` 是**静态史实**（嘉庆元年 = 1796 是公开常识），年份级校验只是**比较两个公历年份**。**月日级才需要农历**，而那一级我们**只警告、不推算**（B3）。**两侧口径完全一致。**

**"完整 schema + 最小 UI"策略——我同意，并补创作侧理由**：
> 技术侧建议"阶段一存盘按完整形态定、UI 先做最小值"——**我采纳**，理由：**schema 的二次迁移成本远高于 UI 的增量开发**。存盘结构现在定全，作者写的 YAML 永不返工；UI 从"只让作者手填 `lunar_label`"起步，逐步加"下拉选年号 / 自动填公历区间 / 年份校验"，**全程不改数据**。

**对技术侧"长年号表维护成本"提醒的回应（B3 补充）**：
> 技术侧提醒："内置年号表一旦入库，就有**表要不要更新/维护**的长期成本。"**这个提醒我接受，并明确边界**：
> - 表**只覆盖到清**（中国历史主要朝代）→ 是**封闭、不增长的史实集合**，不是"需要持续追新的数据"。
> - **不做"自动代填公历"**：表只提供**下拉候选 `era_name`**，公历区间**仍由作者确认**（技术侧建议的"仅下拉候选、不自动填公历"，**成本最低，我采纳**）。
> - 表**可以是外部数据文件**（不进二进制），作者可自行扩展，工具不背维护包袱。

#### B5.3 一个我坚持的创作侧边界（回应技术侧"我照做"）

技术侧说"`custom` 到承载什么、命名如何，你定我照做"——**我定，但同时明确一条不许动的边界**：

> **无论枚举怎么命名、年号表多丰富，运算层（`TimePoint`/`TimeSpan`/`TimelineQuery`/排序/下界）一个字都不许动。** 技术侧 §3.1 的裁定（**"`TimePoint` 不改"**）与我的 B0 纪律**完全同源**——**这是两侧最重要的一致点，也是本项目上轮砍复杂度的成果，必须守住。**

### B6. `year = 0` 的纪年口径（技术侧 U5，设计侧终裁）

> 技术侧转来 **U5**：`year = 0` 是"公元 1 年"还是"公元前 1 年"？技术侧倾向**天文记年**（0 年是闰年），UI 层做映射；需设计侧 + 用户确认。**这是创作体感问题，以下为设计侧终裁。**

**裁定：运算层用天文记年（技术侧已实现，不动）；但"公元 0 年"四个字永远不许出现在作者眼前。**

| 层 | 口径 | 理由 |
|---|---|---|
| **运算层**（`is_leap_year`、换算、`i64` 计数器） | **天文记年**（`year = 0` 存在，是闰年；`-1` = 公元前 2 年） | 技术侧已实现且正确。**这是数学坐标系，不是给作者看的。** |
| **显示层 / 输入层**（作者看到与输入的） | **历史纪年**（**没有公元 0 年**；`1` → "公元 1 年"，`-1` → "公元前 1 年"） | 现实小说作者的常识里**不存在公元 0 年**。若作者看到"公元 0 年"，会**怀疑工具算错了**——信任一旦破，全盘皆输。 |

**为什么必须做这层映射（而不是"让作者习惯 0 年"）**：

> 用户本轮原话的例子是"**公元 1840 年**""**1818 年 5 月 5 日**"——**作者是写现实/历史小说的人**。对这类作者，"公元前 1 年"的**下一年**就是"公元 1 年"，中间**没有 0**。这是**人类历史的通行纪年**。
> 让作者看到"公元 0 年"，等于**要求作者学一套"天文年号"**才能用这个工具。这与 §1.1 北极星（缩短"作者意识到矛盾→完成修改"的路径）**直接冲突**——作者会花时间去想"0 年是几几年"，而不是写小说。

**映射规则（输入 ⇄ 运算，一处转换，作者永不可见 0）**：

| 作者输入 | 运算层 `year` | 作者看到 |
|---|---|---|
| 公元 1 年 | `0` | 公元 1 年 |
| 公元 2 年 | `1` | 公元 2 年 |
| 公元前 1 年 | `-1` | 公元前 1 年 |
| 公元前 2 年 | `-2` | 公元前 2 年 |
| **（不存在）** | — | 作者**无法**输入"公元 0 年"（输入框直接拒绝） |

**关键边界（给技术侧的明确契约）**：

| # | 规则 |
|---|---|
| 1 | **映射只在"作者 ↔ 工具"的边界发生一次**（UI 输入解析 / 显示格式化各一处）。**运算层、`is_leap_year`、计数器一律用天文记年，不感知映射。** |
| 2 | **闰年判定仍按天文年**（`is_leap_year(0) == true`）——**不改**，因为闰年周期是数学事实，与显示口径无关。 |
| 3 | **作者不可输入"公元 0 年"**：输入框对"公元 0 年"直接拒绝并提示"纪年中没有公元 0 年，公元前 1 年之后就是公元 1 年"。 |
| 4 | **非公历历法（`Fixed360`/`Simple365`）不做此映射**：架空历的世界观里，作者可能真有"第 0 年/元年"的设定，**是否映射由作者自定**（默认：架空历按作者填的字面年号显示，不套公历纪年规则）。 |

> **一句话**：**"0 年"是引擎的内部数学，不是作者的日历。** 技术侧的天文记年实现**保留不动**，只需在 UI 层加一道"输入/显示映射"——**成本极小，避免作者对工具的核心信任崩塌**。

**对技术侧 U5 的回应**：你的"天文记年 + UI 映射"**方案正确，我采纳**。补三条边界（上表 1–4）：映射只在边界发生一次、闰年判定不动、作者不可输入 0 年、非公历历法不套此规则。**若主理人/用户不反对，此条即定，无待裁。**

### C1. 重新评估三层导航：**不够。L1 先崩，需补第 4 层**

**先算账（用 §1.5 的同一把尺）**：

|---|---|---|---|
| **L1 全局条**（minimap，1 格 ≈ 1 天） | 18 万格已需压缩显示 | 需**压缩 3 万倍**才能进一屏 minimap。一屏 1200px 装 3650 万天 → **1px = 3 万天 = 83 年**。**一天都看不见**，滑动窗口变得极小（滑块宽度 = 视窗/全长 ≈ 1/30000 px，**画不出来**） | 🔴 **先崩。必须补 L4** |

### C2. 「提示作者跨度太大」——何时说、说什么

**裁定：不说"别写这么大"，说"这么大，建议开启某模式"。是引导，不是劝阻。**

**触发时机（三档，渐进式）**：

| 时机 | 触发条件 | 形态 | 文案 |
|---|---|---|---|
| **① 实时（软）** | 作者在年份框里**正在输入**、且当前值 ≥ 5 位数 | 输入框下方一行**灰字**（不打断） | `这是个超长跨度（14634 年 ≈ 534 万天）。时间轴会自动切到「纪元鸟瞰」显示。` |
| **② 保存时（中）** | 保存 `axis.yaml`、且轴跨度 > 1 万年 | **非模态提示条**（可一键忽略 / 记住） | `轴跨度 10 万年。已为你启用「纪元鸟瞰」简化显示——按世纪聚合，仍可精确跳转到任意一天。` |
| **③ 门槛（硬）** | 轴跨度 > **20 万年**（≈ 7300 万天 ≈ i64 的 4 亿分之一，仍可容纳但 UI 无意义） | **弹窗，需要作者确认** | `跨度已达 20 万年，时间轴上的每一天无法逐格显示。继续可以，但建议：① 拆成多工程 ② 或接受「纪元鸟瞰」为唯一导航。` |

**明确不做的事**：
- ❌ **不在任何档位阻止作者保存**——一人开发的创作工具，**作者主权**优先（§1.1 北极星）。
- ❌ **不弹"i64 装不下"的报错**——用户已算过，**装得下**（10 万年占 i64 的 0.0000000004%）。**报"数值太大"是错误的技术叙事**，会误导作者以为"引擎有硬上限"。真正的限制是 **UI 导航**，文案必须说**导航**，不说**容量**。

**文案的唯一职责**：**把"技术瓶颈"翻译成"作者能做的动作"**。
- ❌ `跨度超出推荐值` → 作者不知道怎么办。
- ✅ `已启用纪元鸟瞰，你仍可跳到任意一天` → 作者知道"我的目标没被剥夺"。

### C3. 事件硬下界的**引导式报错**

**当前问题**：作者想写"建国前的战役"，填了轴外日期 → 工具说"日期非法" → **作者卡住，不知道正确解法**。

**裁定：报错必须"说出正确的另一条路"，而不是否定作者。**

**三级引导文案（按作者意图分岔）**：

| 作者的真实意图（工具可推断） | 报错文案 | 一键动作 |
|---|---|---|
| **意图 A：我想让这个事件早点发生**（数值接近起点，如比起点早几天/几个月） | `这个日期在时间轴起点之前。如果你希望这段时间也能排期，请把「起点年份」前移（当前起点：公元 1840 年）。` | 按钮：**[把起点前移到 1839 年]**（自动改 `start_year` + 保留所有既有事件相对位置，§1.9 方案 A） |
| **意图 B：这是远古的叙事，不需要精确日期** | `如果是传说、神话、历史背景这类"没有确切日期"的内容，建议建为「故事」——它不排期，也不会和其他事件对时间。` | 按钮：**[转成故事]**（把当前内容搬进 `stories/`，清掉日期字段） |
| **意图 C：这是世界开始之前的事** | `如果你的世界在起点之前还有一段历史，可以放进「前史区」（起点左侧，只承载叙事，不参与排期）。` | 按钮：**[放进前史区]** |

**文案骨架（三选一，按作者输入自动挑最可能的）**：

```
┌─ 日期在时间轴起点之前 ──────────────────────────────┐
│  你填的：公元 1835-03-02                             │
│  时间轴起点：公元 1840-01-01（第 1 天）               │
│                                                      │
│  想写"起点之前的事"？有三种做法：                      │
│   ○ 把起点前移（让这段时间能排期）  [立即前移]        │
│   ○ 建为「故事」（不需要日期）      [转成故事]        │
│   ○ 放进「前史区」（起点左侧叙事）  [放进前史区]      │
│                                                      │
│                                   [取消]  [我知道了]  │
└──────────────────────────────────────────────────────┘
```

> **核心原则**：**报错是"岔路口的路牌"，不是"此路不通的墙"。** 作者撞到下界这件事本身**是世界观信息**（"我的世界从 1840 年开始"），工具应帮他**看清楚这个边界**，并给出**跨过去的三条正路**，而不是让他删掉想写的内容。

### D2. 受影响的 R 组（§2.2.1，技术侧，我提创作侧意见）

| 编号 | 原裁定 | 本轮结论 | 处置 |
|---|---|---|---|
| **R1** `TimePoint(i64)` | 单字段 newtype | **不变**，且本轮**更强**：三种历法都只改"这个 i64 怎么显示"，**证明 R1 是对的**（若当初留了 5 元组，换历法就要改数据） | ✅ 强化 |
| **R3** 无负年份 | `counter >= 1` | **不变**。故事"无 day"是**这条约束的配套**（A2/A4） | ✅ 强化 |
| **R5** 排序 = 计数器数值序 | 数值序 | **不变**。故事不进排序 | ✅ 不变 |
| **R6** 历法常量 `const` 360/30 | **硬约束** | **🔴 修订**：常量不能再是全局 `const`——必须**按历法分派**（360/30 vs 365/闰年 vs 公历）。原 R6 的"`const` 常量"是**基于"只有一种历法"**的裁定，**前提已变**。**运算层仍是"计数器数值序"（不变），但"计数器 ⇄ 年月日"的换算函数必须按历法多态** | 🔴 **必须改**（本稿最重的技术侧冲击） |

> **给技术侧的关键提醒（我不写代码，只提语义）**：R6 的修订是**本轮唯一必须动到 `wv-core` 语义的项**。请务必区分：
> - **运算层**：`TimePoint(i64)`、排序、区间、下界 → **一律不变**
> - **显示层**：`Calendar::civil()` / `day_counter()` / `format()` → **改为按 `CalendarKind` 分派**
> 若把历法分派做进运算层，用户上一轮砍掉的复杂度会**全部长回来**（B0 的纪律）。

## F. 一句话交回主理人

> **本轮我改了三件事的"性质"**：把**历法**从"世界的属性"降级为"眼镜"（B0）、把**故事**从"有日期的事件"升级为"没有日期的叙事"（A2）、把**"0 年"从作者的日历赶回引擎内部**（B6）。
> 技术侧唯一必须跟着改的是**历法常量按历法分派**，**运算层一个字都不许动**。
> 用户担心的"i64 装不下"是**假警报**（装得下，占 0.0000000004%）；真正的坑是 **10 万年导航**（L1 会崩，补 L4）和 **年号自动换算**（会骗人，必须拒绝）。
> **两处与技术侧的分歧已终裁统一**（B5）：命名采纳技术侧（下划线 tag）、`custom` 取消、年号 schema 两侧合并为 `Calendar.reign_aliases` 七字段。
