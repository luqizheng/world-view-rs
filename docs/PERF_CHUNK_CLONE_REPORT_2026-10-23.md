## 0. 路线裁定补记（2026-10-24，后于正文）

**用户看过本文后裁定：跳过"继续优化 chunk 管线"的中间方案，直接执行 [ADR-0053](../../adr/ADR-0053-terrain-gpu-field-rendering.md) 的 GPU 场渲染接线。** 因此正文的定位与量级测算仍然成立（它解释了"为什么必须离开这条路"），但**处置方案的定位要随之修正**：

| 正文条目 | 裁定后的状态 |
|---|---|
| §4 ① 拆两相（去整图 clone） | 脏区 patch 路径两相（`copy_patch_pixels` / `apply_chunk_patch`）**已落地并保留**；**spawn 路径的整图 clone 不再修**——chunk 管线降级为回退路径 |
| §4 ③ 生成预算化（每帧 ≤3 块） | **取消**，不再投入 |
| §5 验收判据 | **作废**（那套是为"继续优化 chunk"设的）；chunk 路径的验收改为"回退路径行为不变 + 资产不泄漏" |
| §6「不做 GPU 侧架构重构」 | **已推翻**——C 路线的接线正在做，见 ADR-0053；这条只在本报告撰写时点有效 |

**一处口径修正（与本文无关，但同一批事实）**：C 路线的显存预算按 **≈12 MB** 记（四张数据纹理：height / coast / attr / `line_dash`），不是 ADR-0053 §4 与规格锁 T4 里写的 8 MB（三张）——ADR 已另加追记，规格锁 T4 同步订正。

**为什么 67 MB 依然值得写下来**：它不是"还没修的 bug"，而是一条**被结构逼出来的**成本。chunk 管线留在仓里当回退路径，它的这个性质就仍然存在，任何人回头读代码时都需要知道"这 64 MiB 拷贝不是为了性能，是为了绕开借用冲突"。

## 1. 一页结论

| 问题 | 答案 |
|---|---|
| **是什么** | `sync_terrain_chunks` 在"有块需要生成、或有脏区相交"时，把**整张地形纹理**（lod-demo：64 MiB）`clone` 一份再往下用。 |
| **为什么会有** | 不是性能疏忽，是 **Rust 借用冲突下的正确性妥协**：像素来源是不可变借用，同一作用域内又要向资产表 `add` 新纹理（可变借用），二者不能共存 → 作者用"整图拷一份"解除冲突。 |
| **什么时候发生** | 缩放 / 大幅平移导致视口变化、边缘块进出时；**静止时一次都不发生**（`needs_src == false`）。 |
| **代价多大** | 64 MiB 内存拷贝 + 一次大块分配。按有效内存带宽 20 GB/s 估 ≈ **3.4 ms 纯拷贝**，叠加分配与首次触页常见 **5–10 ms**；这还只是拷贝，真正的块生成（每块 3 级 mip）另算。占 60 FPS 预算（16.7 ms）的 30%–60%。 |
| **为什么现在做** | ① 它是"移动/缩放仍会掉帧"里**唯一还没被解释的大头**；② **与地图面积成正比**——当前 1024 格栅格已 64 MiB，2048 格就是 256 MiB/帧，直接不可用；③ 修法是"删掉一次不必要的拷贝"，不改行为、不引入新机制，收益/风险比高。 |
| **风险** | 中低，且**可证伪**：要求新路径与旧路径的 mip0/mip1/mip2 **逐字节相同**，否则不予合入。 |

## 2. 事实：它到底在哪、为什么绕不开

### 2.1 代码位置（`crates/wv-render/src/cellmap_bridge.rs`）

| 行 | 作用 |
|---|---|
| `:913` | `sync_terrain_chunks` 入口（每帧跑） |
| `:1012-1029` | 判定 `needs_src`：**视口内任一块尚未生成**，或**有脏矩形与之相交** → 置真 |
| `:1034-1037` | `let src_data = if needs_src { images.get(&tex.handle).data.clone() }` ← **本文的主角** |
| `:1077-1175` | 两个消费者：脏区补丁 `patch_chunk_mips(...)`、新块生成 `copy_chunk_pixels(...)` + `build_mip_chain(...)` |

### 2.2 为什么"绕不开"——借用冲突的最小解释

```rust
let src = images.get(&tex.handle);      // 不可变借用，活的
// ... 稍后同一循环里 ...
let handle = images.add(chunk_image);   // 需要可变借用 → 编译失败：borrow conflict
```

Rust 不允许"一边读资产一边改资产"。作者选择了最省事的解法：**先把整图拷成自己的 `Vec<u8>`，借用立刻结束**，随后随便改资产表。

这个解法在正确性上没问题，在成本上有一个致命性质：**拷贝量与地图尺寸成正比，与"这一帧真正需要多少像素"无关**。

### 2.3 量级（lod-demo 实测配置）

| 项 | 数值 | 算式 |
|---|---|---|
| 栅格 | 1024 × 1024 格 | `examples/lod-demo/maps/map_world/index.yaml` |
| 每格像素 `res` | 4 | `tile_res_for(1024) = 4` |
| **整图纹理** | **64 MiB / 67.1 MB** | `(1024×4)² × 4 B` |
| 块尺寸 | 256 格/边 | `CHUNK_SIZE = 256` |
| 单块纹理 | 4 MiB | `(256×4)² × 4 B` |
| 单块 mip 链总量 | ≈ 5.25 MiB | mip0 4 MiB + mip1 1 MiB + mip2 0.25 MiB（`MIP_LEVELS = 3`） |
| 整图块数 | 16 | 1024 / 256 = 4 × 4 |

也就是说：**这一帧可能只需要 1 块（4 MiB）的像素，却先付了 64 MiB 的拷贝。**

## 3. 为什么值得做（而不是"过度优化"）

### 3.1 它随地图规模线性恶化

| 栅格 | 整图纹理 | 每帧拷贝上限 |
|---|---|---|
| 512² | 8 MiB | 可忽略 |
| **1024²（当前示例）** | **64 MiB** | 已到 5–10 ms 量级 |
| 2048² | 256 MiB | 不可用 |
| 4096² | 1 GiB | 完全不可用 |

本项目的地图是分层世界（世界 → 国家 → 城市 → 街道），世界级栅格继续变大是可预期的路线。**这不是"某个示例图上的偶发问题"，而是一条随规模必然恶化的结构性成本。**

### 3.2 3.4 ms 这个数怎么来的（假设写明）

- 64 MiB = 67.1 MB；
- 假设有效内存带宽 20 GB/s（DDR5 双通道的理论值一半左右，扣掉非连续访问与写分配）；
- 67.1 MB / 20 GB/s ≈ **3.4 ms**；
- 未计入：分配器寻找 64 MiB 连续块、首次触页缺页中断、随后 `copy_chunk_pixels` 的二次拷贝与 mip 降采样。
- **诚实声明：这条路径的墙钟时间我们没有单独测过。** 上表是机制与量级估算；专项探针在本轮改动完成后补测（见 §6）。这也是为什么本轮判据一律用**计数器**（`src_clones`、`bytes_copied`）而不是毫秒——计数器不受机器与构建档影响，能跨环境复现。

### 3.3 为什么放在现在做

本轮已完成的三个热点（构建档位、网格重建、光标/群系视图）都有实测或断言兜底：

| 已完成项 | 证据 |
|---|---|
| 构建档位（全栈 opt-level 0 → 分层 1/2/3） | 整图合成 581 ms → 16.6 ms（34.9×） |
| 网格逐档重建 | 12 档缩放重建 13 → **0**；改为单 quad + 屏幕空间 1px 线宽 |
| 鼠标移动掉帧 | `sync_candidate_input` 12.74 ms → **0.07 ms**（同一连通区内移动） |
| 群系视图 26 FPS | 稳态重算 **0**；200 区与 10 区同阶 |

**在这之后再没有"已知的大头"能解释剩余卡顿——除了这条 64 MiB/帧。** 所以它是下一个该动的，不是"顺手优化"。

## 4. 方案（三件事，都是结构性的）

### ① 拆两相：让只读发生在写之前

```
相 A（只读）：images.get(&handle)   → 只为「要生成的块」拷它自己的 4 MiB；
                                    → 只为「脏区命中的块」算脏矩形那一份像素；
相 B（写）  ：借用已结束 → 再 images.add(...) / 写 mip。
```

**效果**：整图拷贝从"每帧一次"变成 **0 次**；拷贝量从"与地图面积成正比"变成"与本帧真正要生成/修补的块数成正比"。

### ② 脏区补丁不整块重传

现状用整图去 patch。改为只算「块 ∩ 脏矩形」的那份像素，写回时只动那些行。
（此路径的两相函数 `copy_patch_pixels` / `apply_chunk_patch` 已落地；生成路径待同法处理。）

### ③ 生成预算化：把一次大卡顿摊成几帧小步

视口一次变大可能要生成十几块、每块还要建 3 级 mip。改为：

```
每帧最多生成 3 块（CHUNK_SPAWNS_PER_FRAME = 3），按到相机中心距离优先，其余下帧继续。
```

代价：极远端边缘块可能晚 1–2 帧出现（肉眼通常不可见，需真人确认）。
收益：缩放时的最差帧从"十几块一次性生成"降到"3 块"。

## 5. 验收判据（全部可复跑）

| # | 判据 | 口径 |
|---|---|---|
| 1 | 静止 60 帧：`src_clones == 0`、`chunk_spawns == 0`、`bytes_copied == 0` | 计数器 |
| 2 | 缩放 30 帧（全图适配 → 最远）：**`src_clones == 0`** | 计数器（本轮核心） |
| 3 | `bytes_copied` ≤ 新生成块像素总量 × 1.5（上限由块尺寸独立手算，不引用实现常量） | 计数器 |
| 4 | **新旧路径 mip0/mip1/mip2 逐字节相同** | 等价性（防"快了但画错了"） |
| 5 | 任一帧 `chunk_spawns ≤ 3`；30 帧后可见块数 == 应有块数（预算化不许留洞） | 计数器 |

## 6. 风险、边界、不做的事

- **不改数据格式、不改分层、不改构建档位、不动示例资产**：改动局限在 `sync_terrain_chunks` 与两个像素工具函数。
- **不做"常驻 CPU 副本"**：那会长期多占 64 MiB 内存，属于用空间换时间的另一种偷懒，且不解决"拷贝量与地图面积成正比"这个本质。
- **不做 GPU 侧架构重构**（整图采样 + 视口裁剪，不建 per-chunk 纹理）：收益不确定、需改渲染架构，另有立项价值，本轮不碰。
- **视觉风险**：预算化后远边缘块可能晚 1–2 帧出现；真人验收看"缩放时画面外侧是否出现短暂空白"。
- **未做真人验证**：本轮所有 FPS 数字均由使用者在真机读取，团队侧（无窗口/无 GPU 呈现）只做计数器与门禁复核。

## 7. 如果有人追问（三问三答）

**Q：这是不是在给一个感觉不到的地方做优化？**
A：不是。它有两个性质：(a) 与地图面积严格成正比——2048 格栅格就是 256 MiB/帧，届时不是"感觉"而是不可用；(b) 它是**一次纯粹多余的拷贝**，删掉不改变任何产品行为（由逐字节等价断言保证）。这是"删复杂度"，不是"加复杂度换性能"。

**Q：为什么之前没发现？**
A：因为它是一次**合理的正确性妥协**——借用冲突下最省事的解法，且只在缩放/平移时触发，静态截图与常规测试都看不出来。它是被计数器（`src_clones`）抓出来的，不是被肉眼抓出来的。

**Q：为什么不干脆把整张图放到 GPU、按视口裁剪采样？**
A：那是渲染架构变更（会动到分块、mip、材质绑定三处），收益上限更高但对当前阶段不划算：现有方案能在**一个函数内部**拿到绝大部分收益。若后续世界级栅格继续上 2048²+，这条路值得单独立项评估。

## 8. 名词表（给非渲染背景的读者）

| 词 | 含义 |
|---|---|
| 分块（chunk） | 把大地形切成 256×256 格的方块，只为视口内的块建纹理与实体，离开视口就回收 |
| mip 链 | 同一块纹理的 3 级分辨率副本（1× / 1/2 / 1/4），缩得越远用越小的那级，省显存带宽 |
| `res` | 每格地形占几个像素。1024 格地图用 `res = 4`，故纹理是 4096×4096 |
| 全图适配（fit） | 让整张地图刚好填满窗口的缩放值；lod-demo 世界级约 5.12 |
| 借用（borrow） | Rust 的所有权机制：同一时刻要么多个只读引用，要么一个可写引用 |
