> 配套技术设计：[2026-11-01-design-doc-to-worldmap-design.md](2026-11-01-design-doc-to-worldmap-design.md)。
> 执行入口：用户说「执行」后，按 design §9 里程碑顺序动工；动工前先读
> `AGENTS.md`（尤其 §13 先分支/worktree 后写码、§6 留痕纪律）。

## 1. 意图（为什么做这件事）

用户在 wv 之外维护游戏设定文档（首个实例：`D:\kudi-project\monster\design\world\`，
含六国档案、地理与节点等 Markdown 章节）。这些文档里已经写清了**势力格局、
地貌气候、城市/要塞/村落清单、地理关系与距离刻度**——但都是叙述文字，
要变成 wv 里的地图仍需人工逐项搬。

本方案把这条搬运链自动化一半：**外置 LLM agent 读设定文档 → 产出结构化
中间表示 → 经 wv 的 HTTP 工具面（`127.0.0.1:8732`，MCP `2025-03-26` 工具面）
写入世界地图 → 截图复核 → 落盘**。wv 本体**不内嵌任何 LLM 调用**，只把
既有的地形生成 / 势力切蛋糕 / 建点编辑命令暴露为 HTTP 工具。

一句话：**设定文档是 source of truth 的一份输入，wv 保持单机纯净（P1），
智能在外、执行在内。**

## 2. 用户故事（用户口述的流程，验收按此对照）

1. 用户启动 world-view，打开或新建一个工程；
2. 用户对 AI 助手说「我要制作一个地图」（可附设定文档路径或直接贴内容）；
3. 助手（agent）加载 `wv-worldmap` skill，先 `list_maps` 检查工程里
   **是否已有世界地图**：
   - 无 → 提案新建；
   - 有 → **停下来问用户**：新建一张 / 在现有地图上增量更新 / 放弃。
     **禁止静默覆盖**（对齐 AGENTS.md §7.5 V1「校验只提示不阻止」的精神：
     工具让作者看见将要发生什么，不代替作者做决定）；
4. 用户确认后，agent 按设定内容生成/更新世界地图：地形（大陆 + 山脉
   河流）→ 势力（国界）→ 节点（城市/要塞/村落/营地等 Place）；
5. 每个阶段 `screenshot` 复核，最终 `save_project` 落盘；
6. 后续设定文档改了，同一链路重跑 → **按 ID 对齐增量更新**已有地图的
   **Place 集**（见 §6-D2/D6）；势力边界与地形的变更 v1 不做增量
   （加法语义 + 无删除工具），skill 话术 = 新建一张图或 GUI 手工改。

**范围限定（用户明示）：暂时只做世界地图（单张根图），不做城市子图钻入。**

## 3. 术语

| 术语 | 定义 |
|---|---|
| **设计直通管线** | 本方案全称：设定文档 → LLM 提取 → HTTP 工具 → wv 世界地图的整条链路 |
| **地理中间表示 / manifest** | LLM 从设定文档提取出的结构化 YAML（地图尺寸/地形包络/势力/节点），是生成动作的单一依据（M2 落盘进工程） |
| **按 ID 对齐增量更新** | 覆盖语义：重跑时以 manifest 的 ID 清单与工程现状求差集，只新增/更新，不删除（详见 design §6） |

（以上术语执行时登记 `GLOSSARY.md`，AGENTS.md §6.1。）

## 4. 目标 / 非目标 / 反目标

### 目标
- G-1 用户拿两份设定章节（六国档案 + 地理与节点），一句「做地图」得到
  一张含地形、七势力（六国+魔军）、约 130 个命名节点的世界地图，落盘成
  标准 wv 工程（YAML，P2/P3）。
- G-2 全程可复核：agent 每阶段截图，用户中途可打断、改参数重跑。
- G-3 重跑幂等（v1 范围 = Place 集）：同一 manifest 重跑，节点不重复、
  ID 不漂移；manifest 变了，只动变化的节点。势力边界/地形重做不在 v1
  （§6-D6）。
- G-4 wv 侧改动全部是**既有能力的暴露**（HTTP 薄封装 + 枚举扩展），
  不写新算法、不引新依赖。

### 非目标（本轮明确不做）
- N-1 城市/区域子图（P4 的钻入层级）——只做单张世界根图。
- N-2 草原 20 营地的**迁徙路线**（时间区间化位移，P7）——v1 落成 20 个
  静态 Place，迁徙列待裁（§7）。
- N-3 距离/速度参数落图（`PlaceEdge` + `Vehicle`，设定文档 §6.11 的
  速度表）——manifest 预留字段，M2 可选启用。
- N-4 LLM 命名类功能（自然区命名已有 `set_nature_names` 走确认闸，不碰）。
- N-5 删除已有地图/节点的 HTTP 工具（覆盖语义不需要删，见 D2）。

### 反目标（做了就算失败）
- A-1 wv 任何 crate 引入网络客户端 / LLM SDK（P1 红线；C 方案已被否决）。
- A-2 agent 未经用户确认就覆盖已有世界地图的内容。
- A-3 生成的地图数据绕过 `wv-edit` 命令直接改世界（AGENTS.md §3.3）。

## 5. 输入约定

设定文档没有固定 schema，就是 Markdown 章节。skill 里约定 LLM 的提取义务：

| 提取物 | 来自文档的什么 | 首个实例的落点 |
|---|---|---|
| 地图尺寸 | 「大陆尺寸（草案）」表 | 1200×1500 km（文档自标待裁，作为初始值） |
| 地形包络 | 各国「地貌与气候」叙述 + §6.10 方位示意图 | 北境高原 / 钟壁山 / 南方沃野大河 / 东部海岸链 / 草原 / 西线魔土 / 极北塔链 |
| 势力 | 六国档案 + 魔军控制区 | 7 个 Faction（含 DivisionMode 切蛋糕包络） |
| 节点 | 各国城市/要塞/村落/营地/坑口清单 | 约 130 个 Place（kind/rank 映射见 design §5） |
| 失地 5 处 | §6.3 失地表 | Place 正常建立（归属魔军面），「失地」语义进 note，不做特殊机制 |

提取时**文档与 manifest 的字段对不上不硬造**：缺的就留空并在汇报里说明
（对齐 V1：提示不阻止）。

## 6. 已裁定决策（用户 2026-11-01 拍板，执行时不再议）

| # | 决策 |
|---|---|
| D1 | **架构 = 外置 agent + skill + HTTP 工具**（A 起步）；M2 把提取结果固化为 `world_manifest.yaml` 落进工程（B 终态），换取 Git 留痕、人可改、重跑一致 |
| D2 | **覆盖语义 = 按 ID 对齐增量更新**，不引入删除工具；manifest 里没有而工程里有的 Place/势力**保留不动**，只在回执里提示用户 |
| D3 | 三个特例 v1 最简表现：**灯塔浮空** = 极北塔链 5 个 Place（主塔+三副塔+塔基市），无地形；**矿邦地底** = 地表仅 2 坑口 + 2 地表营地，国土面照常参与切蛋糕；**草原迁徙** = 20 静态 Place |
| D4 | M0（零代码实测）先行：现有 19 工具 + skill 草稿跑通「检查→确认→建图→批量建点→截图→保存」，用 monster 文档当第一份实测输入，验证映射规则后再进 M1 |
| D5 | **栅格引导**：扩展现有 `create_map`（可选 `cell_size`，world 级按 GUI 同配方全海预填充），不新增初始化工具——仍是 `AddMapCommand` 直译（builder check 问题 1） |
| D6 | **增量范围 v1 = Place 集**：势力边界重切 / 地形重做走「新建一张图」话术；彻底重切面（`UpsertFactionGeometry` 等）列 M2 候选（builder check 问题 2） |
| D7 | **贴图失效走代码**：HTTP 排水对 `terrain.bin` 脏路径失效 `TerrainTexture`，不走 skill 的视图往返绕行（builder check 问题 3） |
| D8 | **工具面 19 → 26**：T5 拆为 `update_place`（name/rank/x/y）+ `set_place_kind`，另补读工具 `list_factions`——diff 与 kind 转正的前提（builder check 问题 4） |
